    Chapter-13: Compose the Whole System

    Sample code

    The complete, tested code for this chapter is in samples/microservices: compose.yaml and .env.example. Use it to compare against your own work. The sample code shows the finished store after Chapter-16, so it has no compose.dev-ports.yaml (create that file yourself in Step-6, as shown there), and it has more services: keycloak and keycloak-db from Chapter-16, and rabbitmq and notification-worker from Chapter-17.

    Introduction

    Up to now, we have built every part of the online store on its own: two APIs, two websites and two databases, each with its own Dockerfile, and in Chapter-12 a small compose file for each API and its database. That's a good way to learn one service at a time, but it is not yet a system. To run the whole store you would have to start six containers by hand, in the right order, with the right passwords and network settings.

    In this lab, I will guide you through describing the whole store in one compose file. One command starts every service, each in its own container, on one private network, with health checks that tell you when the store is ready. This is the moment the book becomes a microservices book: several independent services, each with its own name, its own data and its own failure, running together.

    Technical Scenario

    As a Developer, you have been asked to make it easy for anyone on the team to run the complete store on their laptop. A new team member should be able to clone the repository, copy one settings file and type one command. The team agreed on these rules:

    • One file describes the system. Every service, database, network and volume of the store is in compose.yaml, in the folder that holds the service folders.
    • Configuration comes from the environment. Passwords and connection strings reach the containers from a git-ignored .env file at run time. If a value is missing, compose stops with a clear message instead of starting a broken store.
    • Nothing is published by default. The services talk to each other on a private network. Later, one API gateway will be the only door into the store; until then, a separate, temporary file publishes a port per service for testing.
    • Every service reports its health, and a service starts only after the database it needs is healthy.

    Objective

    In this exercise, our objective is to accomplish and learn the following tasks:

    • Step-1: Understand why one compose file.
    • Step-2: Create the .env file.
    • Step-3: Write the compose file for the whole store.
    • Step-4: Start the store.
    • Step-5: Use service names to reach other services.
    • Step-6: Add temporary development ports.
    • Step-7: Use the everyday compose commands.
    • Step-8: Try it: stop one database.
    • Step-9: Start again from scratch.

    Prerequisites

    Before starting this lab, ensure you have the following prerequisites in place:

    • The four services from Chapter-4 to Chapter-7 and the two database images from Chapter-8 and Chapter-9, connected to their databases as in Chapter-12. In the sample code they are the folders product-api, order-api, admin, storefront, sqlserver and postgresql under samples/microservices.
    • Docker Desktop (or Docker Engine 25 or later) with Docker Compose v2 or later. Check with docker compose version.
    • At least 4 GB of memory for containers: SQL Server alone needs about 2 GB.
    • curl (see the note on Windows in Chapter-4).

    Stop the Chapter-12 labs first (docker compose down in the product-api and order-api folders), so you don't run two SQL Servers at once.

    The services don't call each other yet: the Order API still keeps its own price list, and the two websites show static data. The next chapter connects them, and adds a PRODUCT_API_URL setting to order-api and admin in this compose file, so the compose file in the sample code has those few extra lines. Chapter-15 then adds the API gateway to it, and Chapter-16 adds Keycloak and its database, with Keycloak on a second published port, 127.0.0.1:8081, because browsers sign in there. Chapter-17 adds the message broker RabbitMQ, which publishes only its management UI, on 127.0.0.1:15672, and the notification worker, which publishes nothing. Notice that there is still no line from order-api to product-db: each service owns its data.

    Step-1: Understand why one compose file

    A compose file describes a set of containers that belong together: which images to build or pull, how to configure each container, which networks connect them and where their data lives. You have already used small ones for Keycloak in Chapter-10 and for each API in Chapter-12. The compose file in this chapter describes the whole store, and that brings some real benefits:

    • One command for everyone. docker compose up starts the same system on every laptop and on the build server. No wiki page with twelve docker run commands that drift out of date.
    • The system is code. The file lives in Git next to the services. When a service gets a new setting or a new dependency, the change is reviewed with the code that needs it.
    • Names instead of addresses. Compose puts the containers on one network and gives each one a DNS name: its service name. The Product API finds its database at product-db, whatever IP address Docker gives it today.
    • Start-up order and health. Compose knows that product-api needs product-db, waits until the database is healthy, and tells you when every service is ready.

    Compose is a development and test tool here. In production, the same images run on a container platform such as Kubernetes (see the companion book Building Scalable Kubernetes Infrastructure for Microservices), but the ideas you meet in this chapter (one description of the system, service names, health checks and configuration from the environment) carry over directly.

    Step-2: Create the .env file

    The store needs two passwords: one for SQL Server and one for PostgreSQL. As in Chapter-12, they never go into an image or into Git. Create an .env.example file next to where compose.yaml will live (in the sample code, samples/microservices). It is committed, and it lists every variable the compose file reads, with placeholders only:

    .env.example
    # Copy this file to .env and change the values. .env is git-ignored; never commit it.
# compose.yaml reads every value below and stops with a message if one is missing.

# Password of the Product DB (SQL Server), also used in the Product API's connection string.
# SQL Server rejects weak passwords: use at least 8 characters from three of
# uppercase, lowercase, digits and symbols, or the database will not start.
# Avoid ; and quotes: the value is also used inside a connection string.
MSSQL_SA_PASSWORD=Replaceme-1a

# Password of the Order DB (PostgreSQL), also used in the Order API's DATABASE_URL.
# The value is used inside a URL, so stick to letters, digits and - _ . ~
# or URL-encode other characters.
POSTGRES_PASSWORD=replaceme

    The SQL Server placeholder is Replaceme-1a rather than replaceme because SQL Server enforces a password policy for the sa login (see Chapter-12). Copy the example to .env and put your own values in it:

    cd samples/microservices
cp .env.example .env      # Windows PowerShell: Copy-Item .env.example .env

    Check that Git ignores it:

    git check-ignore -v .env

# output
.gitignore:33:samples/**/.env   .env

    Step-3: Write the compose file for the whole store

    Create compose.yaml in the same folder. compose.yaml is the preferred file name today; docker compose looks for it first, and still accepts the older docker-compose.yml that the earlier labs use. Here is the whole file:

    compose.yaml
    # The whole online store in one file (chapter 13).
#
#   cp .env.example .env        # then set your own passwords in .env
#   docker compose up -d --build --wait
#
# This file publishes no ports: the services reach each other on the store
# network by service name. Until the store has an API gateway, add the
# temporary compose.dev-ports.yaml to reach the services from your machine:
#
#   docker compose -f compose.yaml -f compose.dev-ports.yaml up -d --build --wait
name: store

services:
  product-api:
    build: ./product-api
    image: sample/product-api
    environment:
      ConnectionStrings__ProductDb: "Server=product-db;Database=ProductDb;User Id=sa;Password=${MSSQL_SA_PASSWORD:?copy .env.example to .env and set it};TrustServerCertificate=True"
    depends_on:
      product-db:
        condition: service_healthy
    healthcheck:
      # The .NET runtime image has no curl or wget, so bash sends the request itself
      test:
        - CMD
        - bash
        - -c
        - >-
          exec 3<>/dev/tcp/127.0.0.1/8080 &&
          printf 'GET /health/ready HTTP/1.0\r\n\r\n' >&3 &&
          head -n 1 <&3 | grep -q ' 200 '
      interval: 10s
      timeout: 5s
      retries: 3
      start_period: 30s
      start_interval: 2s
    restart: unless-stopped
    networks: [store]

  order-api:
    build: ./order-api
    image: sample/order-api
    environment:
      DATABASE_URL: "postgres://orders:${POSTGRES_PASSWORD:?copy .env.example to .env and set it}@order-db:5432/orderdb"
    depends_on:
      order-db:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "node", "-e", "fetch('http://127.0.0.1:3000/health/ready').then(r => process.exit(r.ok ? 0 : 1), () => process.exit(1))"]
      interval: 10s
      timeout: 5s
      retries: 3
      start_period: 30s
      start_interval: 2s
    restart: unless-stopped
    networks: [store]

  admin:
    build: ./admin
    image: sample/admin
    healthcheck:
      # Same bash check as product-api; the admin site has only /health/live so far
      test:
        - CMD
        - bash
        - -c
        - >-
          exec 3<>/dev/tcp/127.0.0.1/8080 &&
          printf 'GET /health/live HTTP/1.0\r\n\r\n' >&3 &&
          head -n 1 <&3 | grep -q ' 200 '
      interval: 10s
      timeout: 5s
      retries: 3
      start_period: 30s
      start_interval: 2s
    restart: unless-stopped
    networks: [store]

  storefront:
    build: ./storefront
    image: sample/storefront
    healthcheck:
      # The alpine-based nginx image has BusyBox wget
      test: ["CMD", "wget", "-q", "--spider", "http://127.0.0.1:8080/"]
      interval: 10s
      timeout: 5s
      retries: 3
      start_period: 10s
      start_interval: 2s
    restart: unless-stopped
    networks: [store]

  product-db:
    build: ./sqlserver
    image: sample/sqlserver
    environment:
      ACCEPT_EULA: "Y"
      MSSQL_SA_PASSWORD: ${MSSQL_SA_PASSWORD:?copy .env.example to .env and set it}
    volumes:
      - product-db-data:/var/opt/mssql
    healthcheck:
      # Healthy once the entrypoint has run the scripts and SQL Server answers a query
      test: ["CMD-SHELL", "test -f /tmp/ready && SQLCMDPASSWORD=\"$$MSSQL_SA_PASSWORD\" /opt/mssql-tools18/bin/sqlcmd -S localhost -U sa -C -b -Q 'SELECT 1' > /dev/null"]
      interval: 5s
      timeout: 5s
      retries: 30
      start_period: 30s
    restart: unless-stopped
    networks: [store]

  order-db:
    build: ./postgresql
    image: sample/postgresql
    environment:
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?copy .env.example to .env and set it}
    volumes:
      - order-db-data:/var/lib/postgresql/data
    healthcheck:
      # -h 127.0.0.1: during first-start initialization the server only listens
      # on a local socket, so a TCP check passes only once the scripts have run.
      test: ["CMD", "pg_isready", "-h", "127.0.0.1", "-U", "orders", "-d", "orderdb"]
      interval: 5s
      timeout: 5s
      retries: 10
    restart: unless-stopped
    networks: [store]

networks:
  store:
    name: store

volumes:
  product-db-data:
  order-db-data:

    It looks long, but every service follows the same pattern. Let's walk through the parts.

    The project name. name: store names the compose project. Compose puts it in front of everything it creates, so the containers are called store-product-api-1, store-order-db-1 and so on, and the volumes store_product-db-data and store_order-db-data. Without it, the project would be named after the folder.

    Services. There is one entry per container, and the service names are the ones from the store's design: product-api, order-api, admin, storefront, product-db and order-db. Each service runs from its own image, so each one can be built, changed and restarted without touching the others.

    Build contexts and images. Every service here has both build and image:

    • build: ./product-api is the build context: the folder whose Dockerfile compose builds, the same folder you ran docker build in for Chapter-4. That's why compose.yaml sits in the folder that holds the service folders.
    • image: sample/product-api is the name compose gives the image it builds. It is the same name the Chapter-12 labs use, so both build the same image.
    • A service with only image and no build is pulled from a registry instead, as the Keycloak lab did with quay.io/keycloak/keycloak. Later chapters add services like that, such as Keycloak in Chapter-16 and the message broker RabbitMQ in Chapter-17. In a team, CI builds the service images once and pushes them to a registry, and compose pulls them by tag.

    Configuration from the environment. The compose file fills in ${...} values from .env before it starts anything:

    • ${MSSQL_SA_PASSWORD:?copy .env.example to .env and set it} means "use the value of MSSQL_SA_PASSWORD; if it is empty or missing, stop with this message". The Chapter-12 labs used :- with a fallback value instead; for the whole system we would rather fail fast than quietly start with a placeholder password.
    • The same variable feeds the database and the connection string of the API that owns it, so they always match.
    • ConnectionStrings__ProductDb and DATABASE_URL are built here, from .env values, and nowhere else. The images contain no configuration about where their database is.
    • The admin and storefront services need no settings yet.

    Try it without an .env file and compose refuses to start:

    docker compose up -d --build --wait

# output
Error while interpolating services.order-api.environment.DATABASE_URL: required variable POSTGRES_PASSWORD is missing a value: copy .env.example to .env and set it

    The network. networks: [store] puts each service on the user-defined network store, and name: store under networks: gives that network the plain name store instead of store_store. On a user-defined network Docker runs a small DNS server, so every container can reach every other container by its service name. That's why the connection strings say Server=product-db and @order-db:5432.

    Volumes. product-db-data and order-db-data are named volumes. They keep the database files when containers are removed and recreated, as you saw in Chapter-12. Only docker compose down -v deletes them.

    Health checks. A healthcheck is a command Docker runs inside the container every interval. If it fails retries times in a row, the container is marked unhealthy. During start_period failures don't count, and Docker checks every start_interval instead (Docker Engine 25 and later), so a service that starts quickly is reported healthy quickly. Each check uses a tool that already exists in its image, because the slim runtime images have no curl:

    Service Image based on Check
    product-api dotnet/aspnet:10.0 (no curl or wget) bash opens a TCP connection with its built-in /dev/tcp, sends GET /health/ready, and looks for 200 in the status line
    order-api node:24-alpine a one-line Node.js script calls /health/ready with fetch and exits with 0 or 1
    admin dotnet/aspnet:10.0 the same bash check against /health/live, the only health endpoint the admin site has so far
    storefront nginx-unprivileged:alpine BusyBox wget --spider asks nginx for the home page
    product-db mssql/server:2022 the /tmp/ready file from the entrypoint, then SELECT 1 with sqlcmd (from Chapter-12)
    order-db postgres:17 pg_isready over TCP (from Chapter-12)

    The APIs are checked with /health/ready, not /health/live, so "healthy" in compose means "can do its job, database included". The checks call 127.0.0.1 rather than localhost, because in some images localhost resolves to the IPv6 address first while nginx listens on IPv4 only.

    Start-up order. depends_on with condition: service_healthy makes compose start product-api only after product-db is healthy, and order-api only after order-db is healthy. Without the condition, compose would only wait until the database container had started, and SQL Server needs another 10 to 30 seconds before it accepts connections. The APIs also retry their first connection (Chapter-12), because a database can restart at any time, not only at start-up.

    Restart policy. restart: unless-stopped restarts a container that crashes, and also brings the store back after Docker itself restarts, unless you stopped the container on purpose. Note that Docker doesn't restart a container just because it is unhealthy; that's a job for an orchestrator such as Kubernetes.

    What is published. Nothing. There is no ports: section in this file, so no service can be reached from your machine, only from the other containers on the store network. The databases in particular stay private: only the API that owns a database can reach it. We come back to this in Step-5 and Step-6.

    Step-4: Start the store

    From the folder with compose.yaml, build the images and start the store:

    docker compose up -d --build --wait

# output (trimmed)
 Image sample/storefront Built
 Image sample/admin Built
 Image sample/postgresql Built
 Image sample/order-api Built
 Image sample/sqlserver Built
 Image sample/product-api Built
 Network store Created

 Container store-order-db-1 Started

 Container store-product-api-1 Started
 Container store-storefront-1 Healthy

 Container store-admin-1 Healthy

    • -d runs the containers in the background.
    • --build builds the images first. Without it, compose builds an image only when it doesn't exist yet, so after you change a service's code, add --build (or run docker compose build).
    • --wait waits until every service is healthy, and fails if one becomes unhealthy. That makes it easy to use in scripts and CI.

    Look at the order of the lines: the two APIs started only after their databases were Healthy. The first build takes a few minutes; later builds reuse the cached layers.

    List the services and their health:

    docker compose ps --format 'table {{.Service}}\t{{.Image}}\t{{.Status}}\t{{.Ports}}'

# output
SERVICE       IMAGE                STATUS                    PORTS
admin         sample/admin         Up 19 seconds (healthy)   8080/tcp
order-api     sample/order-api     Up 13 seconds (healthy)   3000/tcp
order-db      sample/postgresql    Up 19 seconds (healthy)   5432/tcp
product-api   sample/product-api   Up 5 seconds (healthy)    8080/tcp
product-db    sample/sqlserver     Up 19 seconds (healthy)   1433/tcp
storefront    sample/storefront    Up 19 seconds (healthy)   8080/tcp

    Every service is healthy. The PORTS column shows only container ports such as 8080/tcp, with no 0.0.0.0:...-> part: nothing is published to your machine.

    SQL Server needs memory

    SQL Server needs about 2 GB of memory and takes 10 to 30 seconds to start the first time. If product-db stops right after it starts, or --wait fails on it, check how much memory Docker has with docker info --format '{{.MemTotal}}' and raise it in Docker Desktop under Settings > Resources (on Windows with WSL 2, in the .wslconfig file). docker compose logs product-db shows the reason; a password policy error means the value in .env is too weak.

    Step-5: Use service names to reach other services

    The services can't be reached from your machine, but they can reach each other. Run wget inside the order-api container (its alpine image has BusyBox wget) and call the Product API by its service name:

    docker compose exec order-api wget -qO- http://product-api:8080/products/1

# output
{"id":1,"sku":"MUG-001","name":"Coffee mug","description":"Ceramic mug, 350 ml.","price":9.99}

    product-api is a DNS name on the store network, and 8080 is the port inside the Product API container. No port mapping is involved. This is how the services call each other from Chapter-14 on.

    You can see all the containers on the network:

    docker network inspect store --format '{{range .Containers}}{{.Name}}  {{.IPv4Address}}{{println}}{{end}}'

# output
store-product-db-1  172.20.0.3/16
store-product-api-1  172.20.0.7/16
store-order-api-1  172.20.0.6/16
store-order-db-1  172.20.0.4/16
store-admin-1  172.20.0.2/16
store-storefront-1  172.20.0.5/16

    The IP addresses change every time the containers are recreated, which is exactly why services use names, never addresses.

    From your machine, on the other hand, there is nothing to connect to:

    curl http://localhost:5001/products

# output
curl: (7) Failed to connect to localhost port 5001 after 2242 ms: Could not connect to server

    That's on purpose. In a real system, clients don't call each service directly. They go through one entry point, an API gateway, which forwards each request to the right service. Chapter-15 adds that gateway, and it will be the only service in compose.yaml with a published port. Keeping the services and especially the databases private means fewer doors to secure.

    Step-6: Add temporary development ports

    Until the gateway exists, we still want to try the services from a browser or with curl. Instead of adding ports to compose.yaml, put them in a second file, compose.dev-ports.yaml, next to it:

    compose.dev-ports.yaml
    # TEMPORARY (chapter 13): publishes each service on its own port of your
# machine, so you can try the store before it has an API gateway. The API
# gateway chapter replaces this file with one public port, 8080; delete it then.
#
#   docker compose -f compose.yaml -f compose.dev-ports.yaml up -d --build --wait
#
# 127.0.0.1 keeps the ports on your machine, out of reach of your network.
services:
  product-api:
    ports:
      - "127.0.0.1:5001:8080"
  order-api:
    ports:
      - "127.0.0.1:5002:3000"
  admin:
    ports:
      - "127.0.0.1:5003:8080"
  storefront:
    ports:
      - "127.0.0.1:5004:8080"

    When you pass several files with -f, compose merges them in order: the second file adds to, or overrides, the first. So compose.yaml stays the clean description of the system, and the dev ports are easy to remove later. Each service gets its own host port (5001 to 5004), so the four services don't fight over port 8080 the way the samples from the earlier chapters do. The databases get no port at all.

    Temporary

    compose.dev-ports.yaml is a stepping stone for this chapter and the next. When we add the API gateway in Chapter-15, the gateway becomes the single public entry point on port 8080, and this file is deleted. That's why the sample code doesn't have it.

    Start the store with both files. Compose recreates only the four services whose settings changed; the databases keep running:

    docker compose -f compose.yaml -f compose.dev-ports.yaml up -d --build --wait
docker compose ps --format 'table {{.Service}}\t{{.Status}}\t{{.Ports}}'

# output
SERVICE       STATUS                    PORTS
admin         Up 5 seconds (healthy)    127.0.0.1:5003->8080/tcp
order-api     Up 4 seconds (healthy)    127.0.0.1:5002->3000/tcp
order-db      Up 47 seconds (healthy)   5432/tcp
product-api   Up 4 seconds (healthy)    127.0.0.1:5001->8080/tcp
product-db    Up 47 seconds (healthy)   1433/tcp
storefront    Up 5 seconds (healthy)    127.0.0.1:5004->8080/tcp

    The other commands (ps, logs, exec, stop, down) find the containers by project name, so they work without the second -f. Only up needs both files every time; a plain docker compose up would recreate the four services without their ports.

    Now call the Product API, which reads from SQL Server:

    curl http://localhost:5001/products/2

# output
{"id":2,"sku":"TEE-001","name":"T-shirt","description":"Cotton T-shirt with the store logo.","price":19.99}

    and place an order with the Order API, which writes to PostgreSQL:

    curl -i -X POST http://localhost:5002/orders \
  -H "Content-Type: application/json" \
  -d '{"items":[{"productId":2,"quantity":1},{"productId":4,"quantity":2}]}'

# output (trimmed)
HTTP/1.1 201 Created
Location: /orders/54010135-3522-4c46-b0d2-7197c8de7cd4
Content-Type: application/json; charset=utf-8

{"id":"54010135-3522-4c46-b0d2-7197c8de7cd4","customerId":"anonymous","status":"Placed","total":43.99,"createdAt":"2026-11-15T22:58:08.750Z","items":[{"productId":2,"name":"T-shirt","unitPrice":19.99,"quantity":1},{"productId":4,"name":"Tote bag","unitPrice":12,"quantity":2}]}

    Your id and date will be different. Open http://localhost:5003 for the admin site and http://localhost:5004 for the storefront. Both still show their own static product list; Chapter-14 makes them ask the Product API.

    Step-7: Use the everyday compose commands

    These are the commands you'll use every day with the store. Run them in the folder with compose.yaml:

    Command What it does
    docker compose up -d --build --wait Build what changed, create or update the containers, wait until all are healthy
    docker compose ps List the services with their status and health
    docker compose logs -f order-api product-api Follow the logs of one or more services (Ctrl+C to stop following)
    docker compose logs --tail 20 --since 5m The last lines of every service, from the last five minutes
    docker compose exec order-db psql -U orders -d orderdb Run a command inside a running service's container
    docker compose stop order-db / start order-db Stop and start one service, keeping its container
    docker compose restart product-api Restart one service with its current settings (after changing .env, run up -d instead: it recreates the containers whose settings changed)
    docker compose build product-api Rebuild one service's image
    docker compose config Show the final configuration, with the .env values filled in and all -f files merged
    docker compose down Stop and remove the containers and the network; keep the volumes
    docker compose down -v The same, and delete the volumes with all the data

    docker compose config prints your passwords from .env, so don't paste its output anywhere public. Use docker compose config --quiet to only check that the file is valid.

    Reading logs from several services. With a system, a problem often shows up across services, so it helps to read their logs together. Compose prefixes each line with the service name and gives each service its own color:

    docker compose logs --tail 2 order-api product-db

# output
product-db-1  | entrypoint: database is ready
product-db-1  | 2026-11-15 22:57:30.60 spid55s     The tempdb database has 8 data file(s).
order-api-1   | order store: PostgreSQL
order-api-1   | order-api listening on port 3000

    Add -f to keep following new lines, and -t to add a timestamp to every line, which helps when you line up events from different services. In the storefront's log you'll also see a request every 10 seconds from Wget: that's the health check.

    Running commands inside a service. exec runs a command in the service's running container, for example a query against the Order DB:

    docker compose exec order-db psql -U orders -d orderdb -c "SELECT count(*) AS orders FROM orders;"

# output
 orders
--------
      2
(1 row)

    That's the example order from 002-seed.sql and the one you placed in Step-6.

    Step-8: Try it: stop one database

    Independent services should also fail independently. Let's prove it. Stop only the Order DB:

    docker compose stop order-db

# output
 Container store-order-db-1 Stopping
 Container store-order-db-1 Stopped

    The Order API is still running, but it can't do its job, and its readiness check says so:

    curl -i http://localhost:5002/health/ready

# output (trimmed)
HTTP/1.1 503 Service Unavailable
Unhealthy

curl -i http://localhost:5002/health/live

# output (trimmed)
HTTP/1.1 200 OK

    The Product API doesn't care at all. It has its own database, which is still running:

    curl -i http://localhost:5001/health/ready

# output (trimmed)
HTTP/1.1 200 OK

curl http://localhost:5001/products/3

# output
{"id":3,"sku":"CAP-001","name":"Baseball cap","description":"Adjustable cotton cap, one size.","price":14.50}

    After a few health checks, compose shows the same picture:

    docker compose ps -a --format 'table {{.Service}}\t{{.Status}}'

# output
SERVICE       STATUS
admin         Up About a minute (healthy)
order-api     Up About a minute (unhealthy)
order-db      Exited (0) 45 seconds ago
product-api   Up About a minute (healthy)
product-db    Up About a minute (healthy)
storefront    Up About a minute (healthy)

    This is failure isolation, one of the main reasons for microservices and for a database per service. Customers can't place orders right now, but they can still browse products. With one shared database, the same outage would have taken down the whole store.

    Placing an order now fails, with a general error:

    curl -i -X POST http://localhost:5002/orders \
  -H "Content-Type: application/json" \
  -d '{"items":[{"productId":1,"quantity":1}]}'

# output (trimmed)
HTTP/1.1 500 Internal Server Error
{"type":"about:blank","title":"Internal Server Error","status":500,"detail":"Something went wrong. Try again later."}

    The API fails safely (nothing half-saved, no crash), but 500 doesn't tell the caller that trying again later could help. The chapter on resilience comes back to this with timeouts, retries and clearer errors.

    Start the database again. The Order API's connection pool reconnects on its own, and within one or two health checks the API is healthy again, with your order still there, because the data lives in the order-db-data volume:

    docker compose start order-db
# about 20 seconds later
docker compose ps --format 'table {{.Service}}\t{{.Status}}'

# output
SERVICE       STATUS
admin         Up About a minute (healthy)
order-api     Up About a minute (healthy)
order-db      Up 23 seconds (healthy)
product-api   Up About a minute (healthy)
product-db    Up 2 minutes (healthy)
storefront    Up About a minute (healthy)

curl -i http://localhost:5002/health/ready

# output (trimmed)
HTTP/1.1 200 OK
Healthy

    Try the same with product-db: this time the Product API reports 503 and the Order API keeps taking orders, because it still prices them from its own list. That changes in Chapter-14, when the Order API starts asking the Product API, and we'll have to decide what an order should do when the Product API is down.

    Step-9: Start again from scratch

    Sometimes you want a completely fresh store, for example after changing a database script. docker compose down -v removes the containers, the network and the volumes:

    docker compose down -v

# output (trimmed)
 Container store-order-api-1 Removed
 Container store-admin-1 Removed
 Container store-product-api-1 Removed
 Container store-storefront-1 Removed
 Container store-order-db-1 Removed
 Container store-product-db-1 Removed
 Volume store_order-db-data Removed
 Volume store_product-db-data Removed
 Network store Removed

    Warning

    -v deletes all the data in the store's databases. Leave it out (docker compose down) when you only want to stop the store and keep the data for next time.

    Start the store again and look at the database logs. With empty volumes, both databases run their numbered scripts again, once each:

    docker compose up -d --wait
docker compose logs product-db | grep entrypoint
docker compose logs order-db | grep "initdb.d/"

# output
product-db-1  | entrypoint: waiting for SQL Server and its databases to come online
product-db-1  | entrypoint: applying 001-schema.sql
product-db-1  | entrypoint: applying 002-seed.sql
product-db-1  | entrypoint: database is ready
order-db-1  | /usr/local/bin/docker-entrypoint.sh: running /docker-entrypoint-initdb.d/001-schema.sql
order-db-1  | /usr/local/bin/docker-entrypoint.sh: running /docker-entrypoint-initdb.d/002-seed.sql

    The Order DB is back to just the seeded order:

    docker compose exec order-db psql -U orders -d orderdb -c "SELECT count(*) AS orders FROM orders;"

# output
 orders
--------
      1
(1 row)

    When you are done for the day, run docker compose down (keeps the data) or docker compose down -v (deletes it).

    Troubleshooting

    Problem What to do
    required variable ... is missing a value Copy .env.example to .env in the folder with compose.yaml
    port is already allocated on 5001 to 5004 Another container or program uses the port; docker ps lists containers, stop the one that uses it
    --wait fails on product-db, or it keeps restarting SQL Server is short of memory (it needs about 2 GB) or rejected the password; see the note in Step-4 and docker compose logs product-db
    product-db takes long to become healthy Normal on the first start: SQL Server needs 10 to 30 seconds, plus the scripts
    An API is unhealthy docker compose logs <service> shows why; usually its database is down or the password in .env changed after the volume was created
    You changed a password in .env and the APIs or the SQL Server entrypoint can no longer log in The databases set the password only on their first start, with an empty volume. Put the old password back, or run docker compose down -v to start fresh (this deletes the data)

    Conclusion

    In this chapter, we described the whole store in one compose.yaml: six services, one private network where service names are DNS names, two named volumes for the data, health checks that use each image's own tools, and depends_on conditions that start each API after its database is healthy. Passwords and connection strings come from a git-ignored .env file, and compose refuses to start without them. No port is published by the main file; a temporary compose.dev-ports.yaml lets us test the services until the API gateway arrives in Chapter-15. Finally, stopping one database showed failure isolation in action: the Order API reported that it wasn't ready, while the Product API kept serving.

    The services now run side by side, but they don't talk to each other yet. In the next chapter, the Order API asks the Product API for prices, the websites get their data from the APIs, and we look at what can go wrong when one service calls another over the network.
