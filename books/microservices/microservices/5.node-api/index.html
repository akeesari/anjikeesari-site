    Chapter-5: Build the Order API with Node.js

    Sample code

    The complete, tested code for this chapter is in samples/microservices/order-api. Use it to compare against your own work.

    Introduction

    Welcome to the second service of our online store. In Chapter-4 we built the Product API with .NET. In this lab, I will guide you through building the Order API with Node.js and Express, the most widely used web framework for Node.js.

    Using a different technology on purpose shows one of the promises of microservices: each service can use the stack that suits its team, as long as it speaks HTTP and JSON like the others. We will write the API from an empty folder, test it, and package it as a Docker image.

    Technical Scenario

    As a Backend (BE) developer, you have been asked to build the Order API, the service that owns the store's orders. When a customer checks out, the Storefront sends the contents of the cart to the Order API, which:

    1. checks that the request makes sense (at least one item, sensible quantities),
    2. looks up the name and current price of every product,
    3. works out the total, saves the order, and returns it with a new order id.

    The Order API copies each product's name and price into the order at the moment it is placed. That copy is a snapshot: if the price of the coffee mug changes next week, last week's orders still show what the customer actually paid.

    In the finished store, the Order API gets those names and prices from the Product API, saves orders in its own PostgreSQL database, and announces every new order with an event. In this chapter we build it to run on its own: it keeps orders in memory and uses a small price list of its own. The later chapters replace those pieces one by one, without changing the endpoints.

    Objective

    In this exercise, our objective is to accomplish and learn the following tasks:

    • Step-1: Setup repository in Azure DevOps.
    • Step-2: Create a new Node.js API project.
    • Step-3: Add the order endpoints.
    • Step-4: Run and test the Order API.
    • Step-5: Add a Dockerfile to the Order API.
    • Step-6: Docker build and run locally.
    • Step-7: Push docker container to ACR (optional).

    Architecture Diagram

    The following diagram shows what we build in this chapter: the Order API running in its own container on port 3000.

    flowchart LR
  you([You: curl]) -->|"POST /orders, GET /orders, GET /orders/id<br/>GET /health/live, /health/ready"| api
  subgraph container ["Container: sample/order-api"]
    api["Order API<br/>Node.js 24, Express 5<br/>port 3000"] --> orders[("In-memory<br/>orders")]
    api --> prices[("Price list<br/>(temporary)")]

    The API we are building has these endpoints:

    Method Path Result
    POST /orders 201 with the new order; 400 for invalid input; 422 for an unknown product
    GET /orders 200 with the customer's orders
    GET /orders/{id} 200 with one order, or 404
    GET /health/live, /health/ready 200 when the service is up and ready

    A customer places an order by sending the product ids and quantities:

    { "items": [ { "productId": 1, "quantity": 2 } ] }

    and gets back the order, with names, prices and the total filled in by the API:

    {
  "id": "<uuid>",
  "customerId": "anonymous",
  "status": "Placed",
  "total": 19.98,
  "createdAt": "<date and time>",
  "items": [ { "productId": 1, "name": "Coffee mug", "unitPrice": 9.99, "quantity": 2 } ]
}

    The store has no sign-in yet, so every order belongs to the customer anonymous. When we secure the services with Keycloak, the customer id comes from the signed-in user.

    Step-1: Setup repository in Azure DevOps.

    We keep all the services of the store in the same microservices repository we used in Chapter-4. If you haven't cloned it yet, clone it now:

    git clone https://dev.azure.com/<organization>/<project>/_git/microservices
cd microservices

    Step-2: Create a new Node.js API project

    We start from an empty folder and add only what we need. From the root of the repository, create a folder for the service and a package.json file:

    mkdir order-api
cd order-api
npm init -y

    npm init -y writes a package.json with default values. Now install Express 5:

    npm install express@5

# output
added 65 packages, and audited 66 packages in 2s

30 packages are looking for funding
  run `npm fund` for details

found 0 vulnerabilities

    npm downloads Express and the packages it depends on into node_modules, adds Express to package.json, and records the exact versions in package-lock.json. Commit package-lock.json: it makes every install, including the one in the Docker image, use the same versions.

    Open package.json and change it to this:

    package.json
    {
  "name": "order-api",
  "version": "1.0.0",
  "description": "Order API for the online store",
  "private": true,
  "type": "module",
  "main": "src/server.js",
  "scripts": {
    "start": "node src/server.js",
    "dev": "node --watch src/server.js"
  },
  "dependencies": {
    "express": "^5.3.0"
  }
}
    • "type": "module" lets us use the modern import and export syntax in our JavaScript files.
    • "private": true stops the package from being published to the npm registry by accident.
    • npm start runs the API, and npm run dev runs it with --watch, which restarts it every time you save a file.

    Add a .gitignore file so that the downloaded packages stay out of Git:

    .gitignore
    node_modules

    Step-3: Add the order endpoints

    Create a src folder. We split the code into small files, each with one job:

    File Job
    server.js Starts the web server and shuts it down cleanly
    app.js Creates the Express app: JSON parsing, routes, error handling
    orders.js The /orders endpoints and the input validation
    catalog.js Looks up product names and prices
    store.js Keeps the orders
    problem.js Sends errors in a standard JSON format

    The server

    src/server.js
    import { app } from './app.js';

const port = Number(process.env.PORT ?? 3000);

const server = app.listen(port, (error) => {
  if (error) throw error;
  console.log(`order-api listening on port ${port}`);
});

// `docker stop` sends SIGTERM and Ctrl+C sends SIGINT. Node.js running as
// the container's main process ignores both unless we handle them, so stop
// accepting new requests, let open ones finish, then exit.
for (const signal of ['SIGTERM', 'SIGINT']) {
  process.on(signal, () => {
    console.log(`${signal} received, shutting down`);
    server.close(() => process.exit(0));
  });
}

    The port comes from the PORT environment variable, with 3000 as the default. Reading settings from environment variables is how containers are configured, so we get into the habit from the start.

    The signal handlers matter more than they look. Inside a container, our Node.js process is the main process, and Linux gives the main process no default handling for stop signals. Without these lines, docker stop would wait 10 seconds and then kill the API in the middle of whatever it was doing.

    The app

    src/app.js
    import express from 'express';
import { ordersRouter } from './orders.js';
import { sendProblem } from './problem.js';

export const app = express();

app.disable('x-powered-by');
app.use(express.json());

// Health endpoints: live = the process is up, ready = it can serve requests.
// The Order API has no dependencies yet, so both always answer 200.
app.get('/health/live', (req, res) => res.type('text').send('Healthy'));
app.get('/health/ready', (req, res) => res.type('text').send('Healthy'));

app.use('/orders', ordersRouter);

// Any other path
app.use((req, res) => sendProblem(res, 404, `No route for ${req.method} ${req.path}.`));

// Errors: a body that is not valid JSON, or anything unexpected.
// Express 5 also sends errors thrown in async handlers here.
app.use((err, req, res, next) => {
  if (err.type === 'entity.parse.failed') {
    return sendProblem(res, 400, 'The request body is not valid JSON.');
  }
  const status = err.status ?? err.statusCode ?? 500;
  if (status < 500) {
    return sendProblem(res, status, err.message);
  }
  console.error(err);
  sendProblem(res, 500, 'Something went wrong. Try again later.');
});
    • express.json() reads JSON request bodies into req.body.
    • app.disable('x-powered-by') stops Express from announcing itself in every response header; there is no reason to tell the world which framework we use.
    • The health endpoints answer the same questions as the Product API's: is the process alive, and is it ready for traffic?
    • app.use('/orders', ordersRouter) sends every request under /orders to the router we write next.
    • The last two app.use calls catch everything else: a path that doesn't exist, and errors. An error handler in Express is recognised by its four parameters (err, req, res, next). Express 5 also sends errors from async route handlers here, which Express 4 did not do.

    Errors as problem details

    The Product API returns errors in the problem details format (RFC 9457). The Order API uses the same JSON shape, so a client can handle errors from both services with the same code:

    src/problem.js
    import { STATUS_CODES } from 'node:http';

// Sends an error as "problem details" (RFC 9457), the same JSON shape
// the Product API uses, so clients handle errors from both APIs alike.
export function sendProblem(res, status, detail, extra = {}) {
  res
    .status(status)
    .type('application/problem+json')
    .json({ type: 'about:blank', title: STATUS_CODES[status], status, detail, ...extra });
}

    Product prices

    src/catalog.js
    // Product names and prices the Order API needs to price an order.
// For now it keeps its own copy; a later chapter asks the Product API instead.
const products = [
  { id: 1, name: 'Coffee mug', price: 9.99 },
  { id: 2, name: 'T-shirt', price: 19.99 },
  { id: 3, name: 'Baseball cap', price: 14.5 },
  { id: 4, name: 'Tote bag', price: 12.0 },
  { id: 5, name: 'Water bottle', price: 24.95 },
];

// Async on purpose: looking a product up will become a network call.
export async function findProduct(id) {
  return products.find((product) => product.id === id);
}

    This price list is a stand-in, so we can build and test the Order API on its own. The Product API owns product data, so Chapter-14 replaces this file's contents with an HTTP call to it. findProduct is already async, so the code that calls it barely changes.

    Keeping the orders

    src/store.js
    // Keeps orders in memory, keyed by id. They are lost when the process stops.
const orders = new Map();

export function saveOrder(order) {
  orders.set(order.id, order);
  return order;
}

export function getOrder(id) {
  return orders.get(id);
}

export function listOrders(customerId) {
  return [...orders.values()].filter((order) => order.customerId === customerId);
}

    The order endpoints

    src/orders.js
    import { randomUUID } from 'node:crypto';
import { Router } from 'express';
import { findProduct } from './catalog.js';
import { sendProblem } from './problem.js';
import { getOrder, listOrders, saveOrder } from './store.js';

export const ordersRouter = Router();

// The store has no sign-in yet, so every order belongs to one customer.
function currentCustomerId(req) {
  return 'anonymous';
}

// Checks the shape of a POST /orders body and returns a list of problems.
export function validateOrder(body) {
  if (typeof body !== 'object' || body === null || Array.isArray(body)) {
    return ['The request body must be a JSON object.'];
  }
  if (!Array.isArray(body.items) || body.items.length === 0) {
    return ['items must be a non-empty array.'];
  }
  if (body.items.length > 50) {
    return ['An order can have at most 50 items.'];
  }
  const errors = [];
  body.items.forEach((item, i) => {
    if (!Number.isInteger(item?.productId) || item.productId < 1) {
      errors.push(`items[${i}].productId must be a positive whole number.`);
    }
    if (!Number.isInteger(item?.quantity) || item.quantity < 1 || item.quantity > 100) {
      errors.push(`items[${i}].quantity must be a whole number from 1 to 100.`);
    }
  });
  return errors;
}

// POST /orders: place an order
ordersRouter.post('/', async (req, res) => {
  const errors = validateOrder(req.body);
  if (errors.length > 0) {
    return sendProblem(res, 400, 'The order is not valid.', { errors });
  }

  // Copy each product's name and price into the order, so later price
  // changes don't alter orders that were already placed.
  const items = [];
  for (const { productId, quantity } of req.body.items) {
    const product = await findProduct(productId);
    if (!product) {
      return sendProblem(res, 422, `Product ${productId} does not exist.`);
    }
    items.push({ productId, name: product.name, unitPrice: product.price, quantity });
  }

  // Add up in cents to avoid floating-point rounding errors
  const totalCents = items.reduce(
    (sum, item) => sum + Math.round(item.unitPrice * 100) * item.quantity, 0);

  const order = saveOrder({
    id: randomUUID(),
    customerId: currentCustomerId(req),
    status: 'Placed',
    total: totalCents / 100,
    createdAt: new Date().toISOString(),
    items,
  });

  res.status(201).location(`/orders/${order.id}`).json(order);
});

// GET /orders: the current customer's orders
ordersRouter.get('/', (req, res) => {
  res.json(listOrders(currentCustomerId(req)));
});

// GET /orders/:id: one order
ordersRouter.get('/:id', (req, res) => {
  const order = getOrder(req.params.id);
  if (!order || order.customerId !== currentCustomerId(req)) {
    return sendProblem(res, 404, `Order ${req.params.id} was not found.`);
  }
  res.json(order);
});

    A few design decisions are worth pointing out:

    • Never trust the client. validateOrder checks every field before we use it, and the client sends only product ids and quantities. Names and prices come from our own catalog, so nobody can order a coffee mug for one cent.
    • 400 versus 422. A request with the wrong shape (no items, a quantity of zero) is a 400 Bad Request. A well-formed request for a product that doesn't exist is a 422 Unprocessable Content: the JSON is fine, but we can't act on it. (Node.js still uses the status code's older name, Unprocessable Entity.)
    • Money in cents. In JavaScript, 0.1 + 0.2 is 0.30000000000000004. Adding up whole cents and dividing by 100 once at the end avoids those rounding errors.
    • Ids. randomUUID() creates a random, unique order id, so ids can't be guessed by counting up.
    • Customers see only their own orders. GET /orders and GET /orders/:id filter on the customer id. Today that is always anonymous; once sign-in arrives, currentCustomerId is the only function that changes.

    Step-5: Add a Dockerfile to the Order API

    Create a Dockerfile in the order-api folder:

    Dockerfile
    FROM node:24-alpine

WORKDIR /app

# Install dependencies first so this layer is cached until the package files change
COPY package.json package-lock.json ./
RUN npm ci --omit=dev

COPY src/ ./src/

ENV NODE_ENV=production
EXPOSE 3000
USER node
CMD ["node", "src/server.js"]

    Here is what the Dockerfile does:

    • FROM node:24-alpine uses the official Node.js 24 image, built on the small Alpine Linux distribution.
    • WORKDIR /app creates /app and makes it the current folder.
    • COPY package.json package-lock.json ./ followed by RUN npm ci --omit=dev installs the dependencies. npm ci installs exactly the versions in package-lock.json, and --omit=dev skips packages only needed during development. Because we copy the package files before the source code, Docker caches this layer and only reinstalls packages when the package files change, not on every code change.
    • COPY src/ ./src/ copies the application code.
    • ENV NODE_ENV=production tells Express and other libraries that this is a production environment, which turns on their production optimizations.
    • EXPOSE 3000 documents the port the API listens on.
    • USER node runs the API as node, a non-root user that the official image provides, instead of root.
    • CMD ["node", "src/server.js"] starts the API. We call node directly instead of npm start, so that the stop signals from Docker reach our process and the shutdown code in server.js runs.

    Next to the Dockerfile, create a .dockerignore file. It keeps your local node_modules folder out of the build context: the image installs its own clean copy with npm ci, and a node_modules folder built on Windows or macOS may not even work on Linux.

    .dockerignore
    node_modules
npm-debug.log

    Step-7: Push docker container to ACR

    This step is optional. It pushes the image to Azure Container Registry (ACR), the same way as in Chapter-4; replace the example registry name acr1dev and resource group rg-acr-dev with your own.

    # Azure login
az login

# set the azure subscription
az account set -s "<subscription-name>"

# Log in to the container registry
az acr login --name acr1dev

# Tag and push the image
docker tag sample/order-api:1.0 acr1dev.azurecr.io/sample/order-api:1.0
docker push acr1dev.azurecr.io/sample/order-api:1.0

    Output (example; layer ids and digest differ on your machine):

    The push refers to repository [acr1dev.azurecr.io/sample/order-api]
<layer-id>: Pushed
...
1.0: digest: sha256:<digest> size: <size>

    Verify the image and its tag in the registry:

    az acr repository show-tags --name acr1dev --repository sample/order-api --output table

    The output lists the tag 1.0.

    Conclusion

    In this chapter, we built the Order API, the second service of our store, with Node.js and Express 5. It validates every order, prices it from a product list, keeps a snapshot of names and prices in each order, and reports errors in the same problem details format as the Product API. We packaged it into a small Alpine-based image that runs as a non-root user and shuts down cleanly when Docker stops it.

    We now have two services written in two different languages that follow the same conventions: JSON over HTTP, the same error format, and the same health endpoints. In the next chapter, we will build the Admin site, the website the store's staff use to manage products. Later, Chapter-12 moves the orders from memory into the Order API's own PostgreSQL database.
