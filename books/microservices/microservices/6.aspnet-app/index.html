    Chapter-6: Build the Admin Site with ASP.NET Core MVC

    Sample code

    The complete, tested code for this chapter is in samples/microservices/admin. Use it to compare against your own work.

    Introduction

    In the previous two labs, we built the store's two APIs: the Product API and the Order API. APIs return JSON for other programs; people need websites. Our store has two: the Storefront for customers, which we build in the next chapter, and the Admin site for the store's staff, which we build in this lab.

    The Admin site is a server-rendered website built with ASP.NET Core MVC: the server builds every page as HTML and sends it to the browser, so the browser needs no JavaScript framework. We will create the project, give it a product list page and a runtime information page, prepare it to run behind a gateway, and package it as a Docker image.

    Technical Scenario

    As a Frontend (FE) developer, your task is to build the Admin site, the website the store's staff use to manage the products in the catalog. It is a separate service with a single job, so it can be developed, deployed and scaled independently of the Storefront that customers use.

    The Admin site owns no data. The product catalog belongs to the Product API, so the Admin site will read and change products only through that API, never through a database of its own. In this chapter, the site shows a fixed list of products so that you can build and run it on its own; Chapter-14 connects it to the Product API.

    Is this a micro-frontend?

    A micro-frontend is a piece of user interface, owned by one team, that is combined with other pieces into one page in the browser, for example a product panel and a cart panel built by different teams. The Admin site is not one: it is a complete, separate website with its own pages and its own address. Splitting a store into a customer website and a staff website is simply two services, each with one job.

    Objective

    In this exercise, our objective is to accomplish and learn the following tasks:

    • Step-1: Create a new ASP.NET Core MVC project
    • Step-2: List the products on the home page
    • Step-3: Add a runtime information page
    • Step-4: Prepare the site for a gateway
    • Step-5: Run and test the Admin site
    • Step-6: Containerize the Admin site
    • Step-7: Push docker container to ACR (optional)

    Prerequisites

    Before starting this lab, make sure you have the following prerequisites in place:

    • The microservices repository from Chapter-4, cloned locally
    • .NET 10 SDK
    • Docker Desktop
    • Visual Studio Code or Visual Studio 2022 or later
    • For the optional step only: an Azure Container Registry (ACR)

    Step-1: Create a new ASP.NET Core MVC project

    Create a new ASP.NET Core Web App using the Model-View-Controller (MVC) template. In MVC, a controller handles each request, gets the data (the model) and picks a view, a Razor template that turns the data into HTML.

    From the root of your microservices repository, run:

    dotnet new mvc --no-https -f net10.0 -n admin -o admin

    As in Chapter-4, --no-https leaves HTTPS to whatever runs in front of the container, -n admin names the project admin.csproj with the namespace admin, and -o admin creates it in the admin folder.

    Step-2: List the products on the home page

    The home page of the Admin site lists the products in the catalog.

    The model

    Add Product.cs to the Models folder. It describes a product exactly as the Product API returns it:

    Models/Product.cs
    namespace admin.Models;

// A product as the Product API describes it.
public record Product(int Id, string Sku, string Name, string Description, decimal Price);

    The controller

    Replace Controllers/HomeController.cs with:

    Controllers/HomeController.cs
    using System.Diagnostics;
using Microsoft.AspNetCore.Mvc;
using admin.Models;

namespace admin.Controllers;

public class HomeController : Controller
{
    // Temporary list, so the site works on its own.
    // A later chapter loads the products from the Product API instead.
    private static readonly IReadOnlyList<Product> Products =
    [
        new(1, "MUG-001", "Coffee mug", "Ceramic mug, 350 ml.", 9.99m),
        new(2, "TEE-001", "T-shirt", "Cotton T-shirt with the store logo.", 19.99m),
        new(3, "CAP-001", "Baseball cap", "Adjustable cotton cap, one size.", 14.50m),
        new(4, "BAG-001", "Tote bag", "Reusable canvas tote bag.", 12.00m),
        new(5, "BTL-001", "Water bottle", "Stainless steel bottle, 500 ml.", 24.95m),
    ];

    // GET / : the product list
    public IActionResult Index()
    {
        return View(Products);
    }

    // GET /Home/Runtime : details of the machine or container the site runs on
    public IActionResult Runtime()
    {
        return View();
    }

    [ResponseCache(Duration = 0, Location = ResponseCacheLocation.None, NoStore = true)]
    public IActionResult Error()
    {
        return View(new ErrorViewModel { RequestId = Activity.Current?.Id ?? HttpContext.TraceIdentifier });
    }
}

    Index passes the product list to its view with View(Products). The Privacy action is gone, and the new Runtime action shows a page we add in Step-3. The Error action comes from the template and shows a friendly error page in Production.

    The view

    Replace Views/Home/Index.cshtml with:

    Views/Home/Index.cshtml
    @model IReadOnlyList<Product>

    ViewData["Title"] = "Products";
}

<h1>Store admin</h1>
<p class="text-muted">@Model.Count products in the catalog.</p>

    Step-3: Add a runtime information page

    Let's add a page that shows the .NET version, operating system, CPU cores and memory the site sees. This information is very useful when the site runs in a container, because the container's limits can be quite different from your machine's.

    Create Views/Home/Runtime.cshtml:

    Views/Home/Runtime.cshtml
    @using System.Runtime.InteropServices
@{
    ViewData["Title"] = "Runtime";
    var hostName = System.Net.Dns.GetHostName();
    var ipList = await System.Net.Dns.GetHostAddressesAsync(hostName);
    GCMemoryInfo gcInfo = GC.GetGCMemoryInfo();

    // Container memory comes from the Linux control group (cgroup).
    // cgroup v2 is used by Docker Desktop and current Linux hosts; v1 by older ones.
    string? memoryUsage = ReadCgroup("/sys/fs/cgroup/memory.current")
        ?? ReadCgroup("/sys/fs/cgroup/memory/memory.usage_in_bytes");
    string? memoryLimit = ReadCgroup("/sys/fs/cgroup/memory.max")
        ?? ReadCgroup("/sys/fs/cgroup/memory/memory.limit_in_bytes");
}

<h1>Runtime</h1>

<table class="table table-striped table-hover">
    <tr>
        <td>.NET version</td>
        <td>@RuntimeInformation.FrameworkDescription</td>
    </tr>
    <tr>
        <td>Operating system</td>
        <td>@RuntimeInformation.OSDescription</td>
    </tr>
    <tr>
        <td>Processor architecture</td>
        <td>@RuntimeInformation.OSArchitecture</td>
    </tr>
    <tr>
        <td>CPU cores</td>
        <td>@Environment.ProcessorCount</td>
    </tr>
    <tr>
        <td>Containerized</td>
        <td>@(Environment.GetEnvironmentVariable("DOTNET_RUNNING_IN_CONTAINER") is null ? "false" : "true")</td>
    </tr>
    <tr>
        <td>Memory, total available GC memory</td>
        <td>@GetInBestUnit(gcInfo.TotalAvailableMemoryBytes)</td>
    </tr>
    @if (memoryUsage is not null)
    {
        <tr>
            <td>cgroup memory usage</td>
            <td>@memoryUsage</td>
        </tr>
        <tr>
            <td>cgroup memory limit</td>
            <td>@memoryLimit</td>
        </tr>
    }
    <tr>
        <td>Host name</td>
        <td>@hostName</td>
    </tr>
    <tr>
        <td class="align-top">Server IP address</td>
        <td>
            @foreach (var ip in ipList)
            {
                @ip
                <br />
            }
        </td>
    </tr>
</table>

@functions {
    const long Mebi = 1024 * 1024;
    const long Gibi = Mebi * 1024;

    // Reads a cgroup memory file; returns null when the file doesn't exist.
    static string? ReadCgroup(string path)
    {
        if (!System.IO.File.Exists(path)) return null;
        var value = System.IO.File.ReadAllText(path).Trim();
        if (value == "max") return "no limit";
        return long.TryParse(value, out var bytes) ? GetInBestUnit(bytes) : value;
    }

    static string GetInBestUnit(long size)
    {
        if (size < Mebi) return $"{size} bytes";
        if (size < Gibi) return $"{decimal.Divide(size, Mebi):F} MiB";
        return $"{decimal.Divide(size, Gibi):F} GiB";
    }
}
    • Docker limits a container's memory and CPU with a Linux feature called control groups (cgroups). The page reads the container's memory use and limit from the cgroup files. Docker Desktop and current Linux distributions use cgroup v2 (memory.current, memory.max); older hosts use cgroup v1, so the page tries both.
    • DOTNET_RUNNING_IN_CONTAINER is an environment variable that Microsoft's .NET images set, which is an easy way to tell whether the app runs in a container.
    • Total available GC memory is how much memory the .NET garbage collector believes it may use. .NET reads the container's limit, so this number drops when you give the container less memory, as you will see in Step-6.

    Step-4: Prepare the site for a gateway

    In the finished store, the browser never talks to the Admin site directly. A gateway sits in front of all the services and forwards every request whose path starts with /admin/ to the Admin site (Chapter-15). Two things change for a site behind a gateway, and we prepare for both now. We also add a health endpoint.

    Replace Program.cs with:

    Program.cs
    using Microsoft.AspNetCore.HttpOverrides;

var builder = WebApplication.CreateBuilder(args);

// Add services to the container.
builder.Services.AddControllersWithViews();
builder.Services.AddHealthChecks();

// Behind a reverse proxy, take the original scheme and client address from
// the X-Forwarded-Proto and X-Forwarded-For headers the proxy adds.
builder.Services.Configure<ForwardedHeadersOptions>(options =>
{
    options.ForwardedHeaders = ForwardedHeaders.XForwardedFor | ForwardedHeaders.XForwardedProto;
    // The proxy is another container whose address isn't known in advance.
    options.KnownIPNetworks.Clear();
    options.KnownProxies.Clear();
});

var app = builder.Build();

app.UseForwardedHeaders();

// PATHBASE runs the site under a sub-path, for example /admin. Not set by default.
var pathBase = app.Configuration["PATHBASE"];
if (!string.IsNullOrEmpty(pathBase))
{
    app.UsePathBase(pathBase);
}

// Configure the HTTP request pipeline.
if (!app.Environment.IsDevelopment())
{
    app.UseExceptionHandler("/Home/Error");
}
app.UseRouting();

app.UseAuthorization();

app.MapStaticAssets();

// Liveness: answers 200 while the process is up
app.MapHealthChecks("/health/live");

app.MapControllerRoute(
    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id?}")
    .WithStaticAssets();

app.Run();
    • Forwarded headers. Behind a gateway, every request seems to come from the gateway, over plain HTTP. The gateway adds X-Forwarded-For (the real client address) and X-Forwarded-Proto (https if the browser used HTTPS) to each request, and UseForwardedHeaders applies them, so the app sees the original values. By default ASP.NET Core trusts these headers only from the local machine; the gateway is another container, so we clear that list. Only do this when the app is reachable only through the gateway, as it will be in our store, because anyone who can reach the app directly could otherwise fake the headers.
    • Path base. The gateway sends /admin/... to the Admin site. UsePathBase tells the app it lives under that prefix: it strips /admin from incoming paths and adds it to every link the tag helpers build, such as the menu links and the CSS and JavaScript files. The prefix comes from the PATHBASE setting, and ASP.NET Core reads settings from environment variables too, so a container can set it with -e PATHBASE=/admin. When it isn't set, the site runs at the root, as it does in this chapter.
    • Health endpoint. /health/live answers 200 Healthy while the process is running, just like the two APIs.

    Step-6: Containerize the Admin site

    The Dockerfile

    Create a Dockerfile in the admin folder:

    Dockerfile
    # Build stage: restore and publish with the .NET SDK
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
COPY admin.csproj ./
RUN dotnet restore
COPY . .
RUN dotnet publish admin.csproj -c Release -o /app/publish --no-restore

# Runtime stage: smaller ASP.NET runtime image, non-root user, port 8080
FROM mcr.microsoft.com/dotnet/aspnet:10.0 AS final
WORKDIR /app
COPY --from=build /app/publish .
EXPOSE 8080
USER $APP_UID
ENTRYPOINT ["dotnet", "admin.dll"]

    It is the same two-stage pattern as the Product API's Dockerfile, which Chapter-4 explains line by line:

    • The build stage starts from the .NET 10 SDK image, restores the NuGet packages from admin.csproj alone (so Docker caches them), then copies the source and publishes the site in Release mode to /app/publish. Publishing an MVC app also compiles the Razor views and collects the files under wwwroot, such as Bootstrap.
    • The final stage starts from the smaller ASP.NET Core runtime image, copies only the published output, documents port 8080, switches to the non-root app user with USER $APP_UID, and starts the site with dotnet admin.dll.

    Add a .dockerignore file next to the Dockerfile, so your local build output stays out of the image:

    .dockerignore
    bin/
obj/

    Build the image

    docker build -t sample/admin:1.0 .

    This time we also give the container a memory limit of 512 MiB with -m 512m, so we can see the effect on the runtime page:

    The two warnings are about Data Protection, the ASP.NET Core feature that encrypts things like cookies and form tokens. Its keys are stored inside the container (in the home folder of the non-root app user), so they disappear when the container is removed. That is fine for this lab. A site that relies on cookies, for example once sign-in is added, should keep its keys outside the container, such as in a volume or a key vault; see the Data Protection link in the References.

    Check the user and the health endpoint:

    docker exec admin whoami
# app

curl http://localhost:8080/health/live

    Open http://localhost:8080/ to see the product list, now served from the container, and then click Runtime. (The finished sample in samples/microservices/admin reads the live product list from the Product API since Chapter-14, so on its own it shows a "Product API is not available" banner instead of the list; the Runtime page is the same.)

    Compare it with what you saw when you ran the site with dotnet run. The operating system is now Linux (the .NET image is based on Ubuntu), Containerized is true, the host name is the container's id, and the IP address is the container's own address on Docker's network. The memory numbers show the limit we set: the cgroup limit is 512 MiB, and .NET reduced its own memory budget to fit inside it. Your CPU count, memory use and addresses will differ.

    When you are done, remove the container so that port 8080 is free again:

    docker rm -f admin

    Step-7: Push docker container to ACR

    This step is optional. It pushes the image to Azure Container Registry (ACR), the same way as in Chapter-4; replace the example registry name acr1dev with your own.

    # Azure login
az login

# set the azure subscription
az account set -s "<subscription-name>"

# Log in to the container registry
az acr login --name acr1dev

# Tag and push the image
docker tag sample/admin:1.0 acr1dev.azurecr.io/sample/admin:1.0
docker push acr1dev.azurecr.io/sample/admin:1.0

    Output (example; layer ids and digest differ on your machine):

    The push refers to repository [acr1dev.azurecr.io/sample/admin]
<layer-id>: Pushed
...
1.0: digest: sha256:<digest> size: <size>

    Verify the image and its tag in the registry:

    az acr repository show-tags --name acr1dev --repository sample/admin --output table

    The output lists the tag 1.0.

    Conclusion

    In this chapter, we built the Admin site, a server-rendered ASP.NET Core MVC website that the store's staff use to see the product catalog, with a runtime page that shows what the site sees inside its container. We prepared it to run behind a gateway with forwarded headers and a configurable path base, added a health endpoint, and packaged it into a non-root container image. Running it with a memory limit showed how .NET adapts to the limits of its container.

    In the next chapter, we will build the store's other website, the Storefront, with React.
