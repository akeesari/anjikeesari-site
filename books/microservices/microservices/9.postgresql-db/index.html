    Chapter-9: Create Your Second Database with PostgreSQL

    Sample code

    The complete, tested code for this chapter is in samples/microservices/postgresql. Use it to compare against your own work.

    Introduction

    PostgreSQL, also known as Postgres, is a powerful, open-source relational database management system (RDBMS). PostgreSQL has gained popularity due to its advanced features and capabilities. PostgreSQL is a reliable choice for a wide range of applications, from small projects to large-scale enterprise systems. Its open-source nature, strong adherence to standards, and extensive feature set make it a popular database solution in application development.

    Running PostgreSQL in a Docker container is best suited for development, testing, learning, or quick experimentation scenarios where you need a lightweight, isolated environment that can be spun up or torn down easily; it's not ideal for production use. For production environments you can use a managed service such as Azure Database for PostgreSQL flexible server, which is a fully managed platform-as-a-service (PaaS).

    In this lab, I will guide you through the process of creating a Docker image for the PostgreSQL database of our store, running it with docker run and with Docker Compose, and finally accessing it from the psql command line tool and pgAdmin.

    Technical Scenario

    As an Application Architect, you are responsible for setting up the databases for the microservices of our store. The Order API from Chapter-5 needs its own database, the Order DB, to keep the orders customers place. Your task is to streamline the process of creating development environments for the developers: we will create a separate database project with numbered SQL scripts and a Dockerfile, so that any developer can start an Order DB with the right tables in one command, without worrying about the complexities of installing and configuring PostgreSQL on their local machines. This approach improves productivity, ensures consistency, and enhances the overall development workflow.

    The Order DB uses a different database engine than the Product DB from Chapter-8 on purpose: each service owns its data, so each team can choose the database that fits it. As in Chapter-8, the image holds no password; the password is given when the container starts.

    Objective

    The objective is to establish a local development environment for the PostgreSQL database. To accomplish this, you will create the database scripts, a Dockerfile and a docker compose file, and run them locally.

    In this exercise, our objective is to accomplish and learn the following tasks:

    • Step-1: Setup Git Repository for PostgreSQL database.
    • Step-2: Create Folder Structure for PostgreSQL database.
    • Step-3: Add the database scripts.
    • Step-4: Add Dockerfiles to the Database Project
      • Step-4.1: Docker Build Locally
      • Step-4.2: Docker Run Locally
    • Step-5: Create Docker Compose file
      • Step-5.1: Stop the previous container.
      • Step-5.2: Run PostgreSQL database with docker compose.
    • Step-6: Test the PostgreSQL database connection from psql tool
    • Step-7: Test the PostgreSQL database from pgadmin4 tool
    • Step-8: Push Docker Container to ACR (optional)

    By the end of this lab, you will have the store's order database running in a Docker container, ready for development and testing.

    Step-1: Setup Git Repository for PostgreSQL database

    Setting up a Git repository for your PostgreSQL database project allows you to manage your code effectively, work in teams, and track the changes of your database codebase.

    • Create a new project in Azure DevOps for your database-related work.
    • Create a repository within the project to store your database scripts and Dockerfiles.

    For example to clone an existing repository, run the following command:

    git clone https://dev.azure.com/<organization>/<project>/_git/microservices

    Step-2: Create Folder Structure for PostgreSQL database

    In this step, we'll create a dedicated project or folder for our PostgreSQL database

    Create a new project:

    Inside our Git repository, create a new directory or folder specifically for your PostgreSQL database. This folder will contain all the necessary files for PostgreSQL database, including database scripts, docker compose & Dockerfile and other psql files.

    Here's a suggested folder structure for a larger PostgreSQL database project:

    your-project-name/
│
├── psql/
│   ├── scripts/
│   │   ├── schema/
│   │   │   ├── tables/
│   │   │   │   ├── table1.sql
│   │   │   │   ├── table2.sql
│   │   │   │   └── ...
│   │   │   ├── views/
│   │   │   │   ├── view1.sql
│   │   │   │   ├── view2.sql
│   │   │   │   └── ...
│   │   │   ├── functions/
│   │   │   │   ├── function1.sql
│   │   │   │   ├── function2.sql
│   │   │   │   └── ...
│   │   │   └── procedures/
│   │   │       ├── procedure1.sql
│   │   │       ├── procedure2.sql
│   │   │       └── ...
│   │   └── data/
│   │       ├── seed_data.sql
│   │       └── ...
│   └── migrations/
│       ├── version1/
│       │   ├── up.sql
│       │   └── down.sql
│       ├── version2/
│       │   ├── up.sql
│       │   └── down.sql
│       └── ...
│
├── Dockerfile
├── docker-compose.yml
└── README.md

    Explanation:

    • psql/: This folder contains all SQL-related files for your project.
    • scripts/: Contains scripts for creating database objects like tables, views, functions, and stored procedures.
      • schema/: Contains subfolders for different types of database objects.
      • tables/, views/, functions/, procedures/: Each of these folders contains SQL scripts for the respective database objects.
    • data/: Contains data scripts such as seed data.
    • migrations/: Contains SQL migration scripts for managing database schema changes over time. Each migration version should have an up.sql script for applying the migration and a down.sql script for reverting it.
    • Dockerfile: The Dockerfile for building a Docker image for your PostgreSQL database.
    • docker-compose.yml: A Docker Compose file that defines the services, networks, and volumes for your PostgreSQL container.
    • README.md: Include documentation or instructions for using the repository, such as setup steps, environment variables, or specific details about the database scripts.

    Feel free to customize this structure according to your project's needs. Our Order DB is small, so its folder only needs this:

    postgresql/
├── scripts/
│   ├── 001-schema.sql     # creates the orders and order_items tables
│   └── 002-seed.sql       # adds one example order
├── Dockerfile
├── docker-compose.yml
├── .env.example           # the password variable, with a placeholder
└── .dockerignore

    Dockerfile vs Docker Compose

    A Dockerfile contains a set of instructions and commands used by Docker to automatically build a new container image.

    The docker-compose.yml file is a configuration file used by Docker Compose, a tool for defining and running multi-container Docker applications. With a single command, Docker Compose uses the docker-compose.yml file to create and start all the services defined in the file.

    In this lab I'll show you both approaches for running the PostgreSQL database.

    Step-3: Add the database scripts

    The tables are created by numbered SQL scripts, the same approach as the Product DB in Chapter-8. The official PostgreSQL image makes this easy: on the first start with an empty data folder, it runs every .sql file in /docker-entrypoint-initdb.d, in name order. On later starts the data folder is no longer empty, so the scripts don't run again.

    Create scripts/001-schema.sql with the two tables the Order API needs:

    scripts/001-schema.sql
    -- 001: the Order API's tables.
-- The postgres image runs the files in /docker-entrypoint-initdb.d once,
-- in name order, the first time the container starts with an empty data volume.

CREATE TABLE orders (
    id          uuid          PRIMARY KEY,
    customer_id varchar(100)  NOT NULL,
    status      varchar(20)   NOT NULL,
    total       numeric(10,2) NOT NULL,
    created_at  timestamptz   NOT NULL DEFAULT now()
);

CREATE INDEX ix_orders_customer_id ON orders (customer_id);

-- product_id has no foreign key: products live in the Product API's own
-- database. name and unit_price are a copy taken when the order was placed.
CREATE TABLE order_items (
    order_id   uuid          NOT NULL REFERENCES orders (id) ON DELETE CASCADE,
    line_no    int           NOT NULL,
    product_id int           NOT NULL,
    name       varchar(100)  NOT NULL,
    unit_price numeric(10,2) NOT NULL,
    quantity   int           NOT NULL CHECK (quantity BETWEEN 1 AND 100),
    PRIMARY KEY (order_id, line_no)
);

    The tables follow the order JSON of the Order API: an order has an id, a customer, a status, a total and a creation time, and one row in order_items per product in the order. The index on customer_id makes "list my orders" fast.

    Notice what is not there: product_id has no foreign key to a products table. The products belong to the Product API, in a different database on a different server. That's why each item keeps its own copy of the product name and price, the snapshot from Chapter-5.

    Create scripts/002-seed.sql with one example order, so a new database has something to show:

    scripts/002-seed.sql
    -- 002: one example order, so a new database has something to show.
-- gen_random_uuid() gives it a fresh id on every new database.

WITH new_order AS (
    INSERT INTO orders (id, customer_id, status, total)
    VALUES (gen_random_uuid(), 'anonymous', 'Placed', 34.48)
    RETURNING id
)
INSERT INTO order_items (order_id, line_no, product_id, name, unit_price, quantity)
SELECT id, 1, 1, 'Coffee mug', 9.99, 2 FROM new_order
UNION ALL
SELECT id, 2, 3, 'Baseball cap', 14.50, 1 FROM new_order;

    Step-4: Add Dockerfiles to the Database Project

    To build a Docker image for PostgreSQL, create a Dockerfile in your project's root directory:

    # PostgreSQL for the Order API (chapter 9).
# No password in this image: pass POSTGRES_PASSWORD when the container starts.
FROM postgres:17

# The user and database names are not secrets, so the image sets them.
ENV POSTGRES_USER=orders \
    POSTGRES_DB=orderdb

# The postgres image runs these once, in name order, on the first start with an empty data volume
COPY scripts/ /docker-entrypoint-initdb.d/

    In this Dockerfile:

    • We use the official PostgreSQL 17 image as our base image.
    • POSTGRES_USER and POSTGRES_DB tell the image to create the user orders and the database orderdb on the first start. They are names, not secrets, so they can live in the image.
    • COPY puts our scripts where the image looks for them.
    • There is no POSTGRES_PASSWORD. Anyone who can pull an image can read its ENV values with docker inspect, so a password in the Dockerfile is a password shared with everyone. It is passed when the container starts.

    Add a .dockerignore file, so a local .env file with a password never ends up in the build context:

    .dockerignore
    .env
*.md
docker-compose.yml

    Step-4.1: Docker Build Locally

    Navigate to your project's root directory and build the Docker image locally using the following command:

    docker build -t sample/postgresql .

    # output (trimmed)

    Step-4.2: Docker Run Locally

    To run your PostgreSQL container locally for testing and development, pass the password with -e:

    docker run -d --name postgresql -p 5432:5432 -e POSTGRES_PASSWORD=replaceme sample/postgresql

    This command creates a container named postgresql and maps port 5432 from the container to the host. replaceme is a placeholder for this lab; use your own value and never reuse it anywhere real.

    The logs show the image running our scripts on the first start:

    docker logs postgresql 2>&1 | grep -E "docker-entrypoint-initdb.d|^CREATE|^INSERT"

# output
CREATE DATABASE
/usr/local/bin/docker-entrypoint.sh: running /docker-entrypoint-initdb.d/001-schema.sql
CREATE TABLE
CREATE INDEX
CREATE TABLE
/usr/local/bin/docker-entrypoint.sh: running /docker-entrypoint-initdb.d/002-seed.sql
INSERT 0 2

    List the running container:

    docker ps --filter name=postgresql --format 'table {{.Image}}\t{{.Status}}\t{{.Ports}}\t{{.Names}}'

# output
IMAGE               STATUS         PORTS                                         NAMES
sample/postgresql   Up 5 seconds   0.0.0.0:5432->5432/tcp, [::]:5432->5432/tcp   postgresql

    Step-5: Create Docker Compose file

    Typing the docker run options every time is error-prone. A docker compose file writes them down once. Create a file named docker-compose.yml in your project directory:

    docker-compose.yml
    # PostgreSQL for the Order API, on its own (chapter 9).
# Optional: copy .env.example to .env and set your own POSTGRES_PASSWORD.
# Port 5432 is published only for this lab, so psql and pgAdmin on your machine
# can connect. The compose file for the whole system does not publish it.
services:
  order-db:
    build: .
    image: sample/postgresql
    environment:
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:-replaceme}
    ports:
      - "5432:5432"
    volumes:
      - order-db-data:/var/lib/postgresql/data
    healthcheck:
      # -h 127.0.0.1: during first-start initialization the server only listens
      # on a local socket, so a TCP check passes only once the scripts have run.
      test: ["CMD", "pg_isready", "-h", "127.0.0.1", "-U", "orders", "-d", "orderdb"]
      interval: 5s
      timeout: 5s
      retries: 10
    restart: unless-stopped

volumes:
  order-db-data:
    • build: . builds the image from our Dockerfile, and image: names it sample/postgresql. The user and database come from the image, so the compose file and the Dockerfile can never disagree about them.
    • ${POSTGRES_PASSWORD:-replaceme} reads the password from your environment or from a .env file next to the compose file, and falls back to the placeholder. To use your own value, copy .env.example to .env and edit it. .env is listed in .gitignore, so it never gets committed; .env.example is committed and shows which variables exist, with placeholders only.
    • ports publishes 5432 so the tools on your machine can connect. The services of the store don't need it: they reach the database over Docker's network, and the compose file for the whole store does not publish this port.
    • The named volume order-db-data keeps the data when the container is removed.
    • The healthcheck tells Docker when the database is really ready. In Chapter-12 the Order API waits for it before it starts.
    .env.example
    # Copy this file to .env and change the value. .env is git-ignored; never commit it.
POSTGRES_PASSWORD=replaceme

    Step-5.1: Stop the previous container

    The container from Step-4.2 still holds port 5432 on your machine. If you start compose now, it fails:

    # output (trimmed)
Error response from daemon: failed to set up container networking: driver failed programming external connectivity on endpoint postgresql-order-db-1 (...): Bind for 0.0.0.0:5432 failed: port is already allocated

    So stop and remove the previous container first. -v also removes the anonymous volume the PostgreSQL image created for its data:

    docker stop postgresql
docker rm -v postgresql

    Step-5.2: Run PostgreSQL database with docker compose

    The docker compose up command is used to start and initialize the services defined in a Docker Compose file. The -d flag tells Docker Compose to run the containers in detached mode.

    docker compose up -d

# output (trimmed)
 Network postgresql_default Created
 Volume postgresql_order-db-data Created
 Container postgresql-order-db-1 Created
 Container postgresql-order-db-1 Started

    List the running services and their health:

    docker compose ps --format 'table {{.Name}}\t{{.Image}}\t{{.Status}}\t{{.Ports}}'

# output
NAME                    IMAGE               STATUS                   PORTS
postgresql-order-db-1   sample/postgresql   Up 9 seconds (healthy)   0.0.0.0:5432->5432/tcp, [::]:5432->5432/tcp

    List the volume that holds the data:

    docker volume ls --filter name=postgresql

# output
DRIVER    VOLUME NAME
local     postgresql_order-db-data

    If you open the docker desktop you will notice the new container and volume.

    Ensure that you test the PostgreSQL connection using either the pgAdmin tool or the psql command-line tool.

    Step-6: Test the PostgreSQL database connection from psql tool

    The psql tool is a command-line interface (CLI) provided by PostgreSQL that allows users to interact with PostgreSQL databases directly from the terminal or command prompt.

    To test a PostgreSQL database connection using the psql command-line tool, follow these steps:

    Opening a terminal or command prompt on your computer.

    Use the psql utility to connect to your PostgreSQL database.

    psql -h <hostname> -U <username> -d <database_name>

    Replace the placeholders with your specific information:

    • <hostname>: The hostname of the PostgreSQL server.
    • <username>: Your PostgreSQL username.
    • <database_name>: The name of the PostgreSQL database you want to connect to.

    For our Order DB, connect as the user orders to the database orderdb:

    psql -h localhost -U orders -d orderdb

    If the PostgreSQL server is running on the default port (5432), you don't need to specify the port. However, if it's running on a different port, you can use the -p option to specify the port number.

    If psql is not installed on your machine, run it inside the container instead; no password is needed there, because it connects through the container's local socket:

    docker compose exec order-db psql -U orders -d orderdb

    Provide Password(if required):

    If your PostgreSQL database is configured to require a password for the specified username, you will be prompted to enter the password. Type the password (replaceme, or the value in your .env file) and press Enter.

    Successful Connection:

    If the connection is successful, you should see the psql command prompt, orderdb=#, which indicates that you are connected to the PostgreSQL database. You are now in an interactive session with the PostgreSQL database, and you can run SQL commands and queries.

    Test SQL Commands:

    List the tables that 001-schema.sql created:

    \dt

    # output
           List of relations
 Schema |    Name     | Type  | Owner
--------+-------------+-------+--------
 public | order_items | table | orders
 public | orders      | table | orders
(2 rows)

    Look at the example order from 002-seed.sql:

    SELECT o.id, o.total, i.name, i.unit_price, i.quantity
FROM orders o JOIN order_items i ON i.order_id = o.id
ORDER BY i.line_no;

    # output
                  id                  | total |     name     | unit_price | quantity
--------------------------------------+-------+--------------+------------+----------
 95f05378-959b-4782-80d5-d4450f6c6950 | 34.48 | Coffee mug   |       9.99 |        2
 95f05378-959b-4782-80d5-d4450f6c6950 | 34.48 | Baseball cap |      14.50 |        1
(2 rows)

    Your order id will be different. You can also run a simple SQL query like:

    SELECT version();

    # output
                                                       version
----------------------------------------------------------------------------------------------------------------------
 PostgreSQL 17.12 (Debian 17.12-1.pgdg13+1) on x86_64-pc-linux-gnu, compiled by gcc (Debian 14.2.0-19) 14.2.0, 64-bit
(1 row)

    This query returns the PostgreSQL version, confirming that you can interact with the database.

    Exit psql:

    To exit the psql session and return to your command prompt, you can type:

    \q

    or press Ctrl + D (on Unix-based systems) or Ctrl + Z (on Windows).

    By following these steps, you can connect to a PostgreSQL database using the psql tool and start interacting with the database using SQL commands directly from the command line.

    Create a Database

    Creating a database is really simple. Execute the command below, and the database should be created.

    # command
orderdb=# CREATE DATABASE [databasename];

# example
CREATE DATABASE mydatabase2;

    Step-7: Test the PostgreSQL database from pgadmin4 tool

    pgAdmin is a popular open-source graphical user interface (GUI) administration tool for PostgreSQL. It provides a comprehensive set of features for managing PostgreSQL databases, including creating and managing databases, schemas, tables, indexes, users, and permissions. pgAdmin allows users to interact with PostgreSQL databases visually, making database administration tasks more intuitive and efficient.

    To connect to a PostgreSQL database using the pgAdmin tool, follow these steps:

    Install and Launch pgAdmin 4:

    Download and install pgAdmin 4 on your computer. Once installed, launch the pgAdmin 4 application.

    Log in to pgAdmin

    When you launch pgAdmin for the first time, you'll be prompted to set the master password. Enter the password you want to use to log in to pgAdmin. You can also choose to save the login information for future use.

    Add a Server:

    After logging in, you'll see the pgAdmin interface. To connect to a PostgreSQL server, you need to add a server to pgAdmin. Follow these steps:

    • Right-click on "Servers" in the left sidebar and select "Register > Server..."
    • Configure Server Connection: you'll need to provide the following information:
      • Name: Give your server a descriptive name to identify it within pgAdmin, for example order-db.
      • Host name/address: Specify the hostname or IP address of the PostgreSQL server you want to connect to.
      • Port: Enter the port number where PostgreSQL is running (default is 5432).
      • Maintenance database: Specify the name of a database to connect to initially.
      • Username: Enter the PostgreSQL username you want to use for this connection.
      • Password: Provide the password for the specified username.

    For our Order DB:

    Host name/address - localhost
Port              - 5432
Maintenance database - orderdb
Username          - orders
Password          - replaceme (or the value in your .env file)

    Once you've entered the connection details, click the "Save" button to add the server. You will find the orders and order_items tables under Databases > orderdb > Schemas > public > Tables.

    When you are done, stop the database with docker compose down. The data stays in the order-db-data volume for next time; docker compose down -v removes it too.

    Step-8: Push Docker Container to ACR

    This step is optional. Pushing the image to Azure Container Registry (ACR) lets every developer on the team pull the same development database. The image contains no password, so sharing it does not share a secret.

    Log in to your Azure account using the Azure CLI:

    az login

    Authenticate to your ACR:

    az acr login --name myacr

    Replace myacr with your ACR name.

    Tag your local Docker image with the ACR login server:

    docker tag sample/postgresql myacr.azurecr.io/sample/postgresql:v1

    Push the Docker image to ACR:

    docker push myacr.azurecr.io/sample/postgresql:v1

    Replace myacr and v1 with your ACR name and desired image version.

    Production note

    This image is for development and testing. In production, the Order API uses a managed database such as Azure Database for PostgreSQL flexible server, which takes care of high availability, backups and patching, and the same numbered scripts are applied to it as migrations. You don't run the database container there. Chapter-12 explains this in more detail.

    Conclusion

    You have successfully created a Docker image for the store's order database. The official PostgreSQL image runs our numbered scripts on the first start, the user and database names live in the image, and the password is given only when the container starts. You ran it both with docker run and with Docker Compose, kept the data in a named volume, and connected with psql and pgAdmin.

    The store now has two databases, one per API, each with its own engine. In Chapter-12 we connect the Product API to the Product DB and the Order API to this Order DB.
