    Chapter-15: API Gateway

    Sample code

    The complete, tested code for this chapter is in samples/microservices: the gateway in gateway, compose.yaml, the storefront's vite.config.js and scripts/demo-order.sh. Use it to compare against your own work. The sample code shows the store after Chapter-16, which adds Keycloak: placing orders and changing products there need an access token, demo-order.sh sends one, and the gateway's /admin location has larger header buffers for the sign-in cookie.

    Introduction

    At the end of Chapter-14, the store worked: the Order API priced orders with the Product API, the Admin site managed products, and the Storefront placed real orders. But look at how you reached it. Every service had its own port on your machine (5001 to 5004, from the temporary compose.dev-ports.yaml), and the Storefront's nginx quietly forwarded /api/ to the two APIs. That was fine for testing, but it is not how a real system is reached.

    In this lab, I will guide you through putting an API gateway in front of the store: one nginx container that is the only door into the system. The browser talks to http://localhost:8080 and nothing else; the gateway sends each request to the service that owns its path. Along the way we look at what a gateway should and shouldn't do, the path base problem of a website that lives under /admin, why the gateway hands out request ids, and what the gateway answers when a service is down or a client sends too many requests. At the end, we delete the temporary ports and proxies.

    Technical Scenario

    As a Platform engineer, you have been asked to give the store one public entry point. The team agreed on these rules:

    • One address for everything. Customers, staff and scripts use http://localhost:8080. No service publishes a port of its own, and the databases stay private as before.
    • Routes follow ownership. / is the Storefront, /admin is the Admin site, /api/products is the Product API and /api/orders is the Order API. The gateway removes the /api prefix, so the services keep their own paths.
    • Same origin, no configuration. The Storefront keeps calling relative /api/... URLs, so it needs no API address and no CORS.
    • Plumbing, not business logic. The gateway routes, passes on headers, sets timeouts, creates request ids and limits abusive traffic. It never decides what an order costs or who may see a product.
    • Clear errors. When the gateway can't reach a service, an API client gets a JSON error in the same format as the APIs' own errors, never an HTML error page.

    Objective

    In this exercise, our objective is to accomplish and learn the following tasks:

    • Step-1: Understand what an API gateway does.
    • Step-2: Write the gateway's nginx configuration.
    • Step-3: Add the gateway's Dockerfile.
    • Step-4: Put the gateway in the compose file.
    • Step-5: Remove the temporary ports and proxies.
    • Step-6: Start the store behind the gateway.
    • Step-7: Try it: everything through one address.
    • Step-8: Try it: follow a request id and see the forwarded headers.
    • Step-9: Try it: stop the Product API.
    • Step-10: Try it: hit the rate limit.

    Prerequisites

    Before starting this lab, ensure you have the following prerequisites in place:

    • The store from Chapter-14: compose.yaml, compose.dev-ports.yaml, your .env file and the service folders, in the folder that holds them (samples/microservices in the sample code).
    • The Admin site prepared for a gateway in Chapter-6 (forwarded headers and the PATHBASE setting).
    • Docker Desktop (or Docker Engine 25 or later) with Docker Compose v2 or later.
    • curl and a bash shell (on Windows, Git Bash or WSL).
    • Port 8080 free on your machine. The single-service labs from Chapter-3 to Chapter-11 use it too, so stop them first (docker ps lists what is running).

    Step-1: Understand what an API gateway does

    Without a gateway, every client has to know the address of every service. The Storefront would need the Product API's address and the Order API's address, baked into its JavaScript or passed in at run time. Each API would need CORS headers, because a page loaded from one origin may only call another origin if that origin allows it. Every service would also need its own TLS certificate, its own rate limiting and its own access log format. And every port you publish is one more door to secure.

    An API gateway is a reverse proxy that sits in front of all the services and is the single entry point for clients. Clients send every request to the gateway, and the gateway forwards it to the right service. Here is what our gateway does:

    Job What it means for the store
    Routing /api/orders/... goes to the Order API, /admin/... to the Admin site, and so on. Services can move, split or be renamed without clients noticing
    One origin The websites and APIs share http://localhost:8080, so the browser makes no cross-origin calls and nobody needs CORS
    Header forwarding The gateway tells the services who really called (X-Forwarded-For), over which scheme (X-Forwarded-Proto) and on which host (Host), and passes on Authorization and traceparent
    Request ids Every request gets an X-Request-Id, created at the edge if the client didn't send one
    Timeouts A service that doesn't answer can't hold a client's connection forever
    Rate limiting A client that sends too many orders gets 429 Too Many Requests before the request reaches the Order API
    TLS termination In production, the gateway holds the HTTPS certificate and the services behind it speak plain HTTP on the private network. In this lab everything is plain HTTP on your machine

    Just as important is what a gateway must not do: business logic. As soon as the gateway checks stock, calculates a discount or joins the answers of two services into one, it becomes a service that every team has to change for every feature, and it quietly couples services that should be independent. Keep it boring: routing and cross-cutting plumbing only. (Checking that a request carries a valid token is plumbing; deciding that a customer may only see their own orders is business logic, and stays in the Order API. Chapter-16 comes back to this.)

    You will meet two related ideas:

    • Backend for frontend (BFF). A small backend made for one particular client, for example one for the mobile app and one for the website, that shapes the APIs to what that client needs. It may combine calls and contains client-specific logic, which a general gateway shouldn't. A BFF usually sits behind a gateway.
    • Service mesh. Infrastructure such as Istio or Linkerd that adds a small proxy next to every service and handles the traffic between services: mutual TLS, retries, traffic splitting and telemetry. A gateway handles traffic coming into the system (north-south); a mesh handles traffic inside it (east-west).

    We use nginx because it needs only a configuration file, no new codebase, and works the same whatever language the services are written in. Good alternatives are YARP (a reverse proxy library for .NET, configured in C# or JSON) and, in the cloud, a managed gateway such as Azure API Management or Azure Front Door, which add features like a developer portal, API keys and a global edge network.

    Step-2: Write the gateway's nginx configuration

    Create a folder gateway next to the other service folders, and in it a file nginx.conf:

    gateway/nginx.conf
    # The store's API gateway (chapter 15): the one public entry point.
# The browser talks only to this server; it forwards each request to the
# service that owns the path:
#
#   /               -> storefront:8080
#   /admin          -> admin:8080       (the admin site runs with PATHBASE=/admin)
#   /api/products   -> product-api:8080 (without the /api prefix)
#   /api/orders     -> order-api:3000   (without the /api prefix)

# Keep the caller's X-Request-Id if it looks sane, otherwise use a new id
# that nginx creates for every request ($request_id, 32 hex characters).
map $http_x_request_id $req_id {
    "~^[A-Za-z0-9._-]{1,100}$"  $http_x_request_id;
    default                     $request_id;
}

# Rate limit for placing orders: 2 requests per second per client address,
# tracked in 10 MB of shared memory (enough for about 160,000 addresses).
# Only POST counts: nginx doesn't count a request whose key is empty, so
# reading orders (GET) is never limited.
map $request_method $order_limit_key {
    POST     $binary_remote_addr;
    default  "";
}
limit_req_zone $order_limit_key zone=orders:10m rate=2r/s;

# One access log line per request, with the request id
log_format gateway '$remote_addr "$request" $status ${request_time}s requestId=$req_id';

server {
    # nginx-unprivileged runs as a normal user, which may not open ports below 1024
    listen 8080;
    server_name _;
    server_tokens off;
    access_log /var/log/nginx/access.log gateway;

    # Docker's DNS server (127.0.0.11) looks up the service names when a request
    # arrives, not when nginx starts, so the gateway also starts while a service
    # is down, and finds a container again after it is recreated.
    resolver 127.0.0.11 valid=10s ipv6=off;
    resolver_timeout 2s;

    # Headers for every service behind the gateway
    proxy_http_version 1.1;
    proxy_set_header Host              $http_host;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Request-Id      $req_id;
    # Authorization and traceparent are passed on unchanged, like every other
    # request header, so they need no line here.

    # Send the request id back to the caller, once
    proxy_hide_header X-Request-Id;
    add_header X-Request-Id $req_id always;

    # Give up on a service that doesn't accept the connection within 2 seconds,
    # or doesn't answer within 10
    proxy_connect_timeout 2s;
    proxy_send_timeout 10s;
    proxy_read_timeout 10s;

    limit_req_status 429;

    # Health check for compose: answers without asking any service
    location = /healthz {
        access_log off;
        default_type text/plain;
        return 200 "ok\n";
    }

    # /api/products/1 -> http://product-api:8080/products/1
    location /api/products {
        set $product_api http://product-api:8080;
        rewrite ^/api(/.*)$ $1 break;
        proxy_pass $product_api;
        # Put the /api prefix back into the Location header of a 201 Created
        proxy_redirect ~^(https?://[^/]+)?/products(.*)$ $1/api/products$2;
        error_page 502 @api_502;
        error_page 504 @api_504;
    }

    # /api/orders/ -> http://order-api:3000/orders/
    location /api/orders {
        # Allow short bursts of up to 5 extra requests, then answer 429
        limit_req zone=orders burst=5 nodelay;
        set $order_api http://order-api:3000;
        rewrite ^/api(/.*)$ $1 break;
        proxy_pass $order_api;
        proxy_redirect ~^(https?://[^/]+)?/orders(.*)$ $1/api/orders$2;
        error_page 429 @api_429;
        error_page 502 @api_502;
        error_page 504 @api_504;
    }

    # Any other /api/ path: a JSON 404 rather than the storefront's page
    location /api/ {
        default_type application/problem+json;
        return 404 '{"type":"about:blank","title":"Not Found","status":404,"detail":"There is no API at this address.","requestId":"$req_id"}';
    }

    # /admin/... -> http://admin:8080/admin/... (the path is passed on unchanged)
    location /admin {
        set $admin http://admin:8080;
        proxy_pass $admin;
    }

    # Everything else: the storefront
    location / {
        set $storefront http://storefront:8080;
        proxy_pass $storefront;
    }

    # Errors made by the gateway itself, as problem details (RFC 9457) like
    # the APIs' own errors. Errors that a service sends pass through unchanged.
    location @api_502 {
        default_type application/problem+json;
        return 502 '{"type":"about:blank","title":"Bad Gateway","status":502,"detail":"The service is not available. Try again in a moment.","requestId":"$req_id"}';
    }

    location @api_504 {
        default_type application/problem+json;
        return 504 '{"type":"about:blank","title":"Gateway Timeout","status":504,"detail":"The service did not answer in time. Try again in a moment.","requestId":"$req_id"}';
    }

    location @api_429 {
        default_type application/problem+json;
        return 429 '{"type":"about:blank","title":"Too Many Requests","status":429,"detail":"Too many requests. Slow down and try again in a moment.","requestId":"$req_id"}';
    }
}

    That's the whole gateway. It looks like a lot at first, so let's go through it block by block.

    Where the file goes. The image's main /etc/nginx/nginx.conf includes every file in /etc/nginx/conf.d/ inside its http block, and the Dockerfile in Step-3 copies our file there. That's why the file can define a map, a limit_req_zone and a log_format at the top, outside the server block: they belong to the http level and can be used by any server.

    The request id (map). A map defines a new variable, $req_id, from another one. If the request has an X-Request-Id header that matches the pattern (letters, digits, ., _ and -, at most 100 characters), $req_id is that value. Otherwise it is $request_id, a random 32-character id that nginx creates for every request. It's the same rule the Order API uses (Chapter-14), now applied once, at the edge.

    Why the gateway creates request ids. The gateway is the first part of the system that sees every request, so it's the natural place to give each one an id. From then on, the same id is in the gateway's access log, in the request to the service, in the service's log, in every call that service makes, and in the response to the client. When a customer reports "my order failed", the id from the response finds every log line that belongs to it. The pattern check matters too: the header comes from outside, and a client must not be able to write odd characters or long text into your logs.

    The rate limit zone. limit_req_zone sets up the bookkeeping for a rate limit: requests are counted per client address ($binary_remote_addr, 4 bytes for IPv4), at most 2 per second, in a 10 MB shared memory zone called orders. The zone doesn't limit anything yet; limit_req in the /api/orders location uses it (more on that below). The key comes from a map: for a POST it is the client address, for every other method it is empty, and nginx doesn't count requests with an empty key. So only placing orders is limited; reading your order history never is.

    The access log. log_format gateway writes one short line per request with the client address, the request line, the status, the time it took and the request id. access_log in the server block uses it. The image sends /var/log/nginx/access.log to the container's standard output, so docker compose logs gateway shows it.

    The server. listen 8080 because the gateway runs as the non-root nginx user from the nginx-unprivileged image, like the Storefront in Chapter-7, and a normal user may not open ports below 1024. server_name _ accepts any host name. server_tokens off keeps the nginx version out of the Server header and error pages: no need to tell everyone on the internet which version to look up exploits for.

    The resolver. Every service address in this file is in a variable (set $product_api http://product-api:8080;). With a plain proxy_pass http://product-api:8080;, nginx would look the name up once at start-up and refuse to start if any service were missing. With a variable, nginx asks Docker's DNS server on the store network, 127.0.0.11, when a request arrives, and keeps the answer for 10 seconds (valid=10s). So the gateway starts even when a service is down, and it finds a service again after compose recreates its container with a new IP address. ipv6=off because the store network has IPv4 addresses only. This is the same trick as the temporary proxy in Chapter-14; it now lives in the one place that needs it.

    Headers for the services. The proxy_set_header lines in the server block apply to every location below it:

    • Host $http_host passes on the host and port the browser used (localhost:8080). By default nginx would send the name from proxy_pass instead (product-api:8080), and a service that builds a full URL, such as the Product API's Location header or a sign-in redirect in the next chapter, would build one that only works inside the network.
    • X-Forwarded-For adds the client's address to the list of addresses the request came through, and X-Forwarded-Proto says whether the client used http or https. The Admin site reads both with UseForwardedHeaders (Chapter-6), so it sees the real client and scheme instead of the gateway's.
    • X-Request-Id $req_id sends the request id to the service. The Order API already keeps an incoming id (Chapter-14), and passes it on to the Product API.
    • Authorization and traceparent need no line: nginx passes on every request header it doesn't replace. Authorization carries the access token in the next chapter, Chapter-16, and traceparent (the W3C Trace Context header) carries the trace id that the chapter on observability uses to link the spans of one request across services. A gateway that dropped them would silently break both.

    proxy_hide_header X-Request-Id and add_header X-Request-Id $req_id always send the id back to the client in every response, also in error responses (always), and exactly once: the Order API already returns the header, and without proxy_hide_header the client would get it twice.

    Timeouts. proxy_connect_timeout 2s gives up on a service that doesn't accept the connection within 2 seconds; proxy_send_timeout and proxy_read_timeout give up when sending the request or waiting for the answer stalls for 10 seconds. The Order API's own call to the Product API times out after 2 seconds (Chapter-14), so 10 seconds leaves room for a slow but working request, while a stuck service can't hold the client's connection for nginx's default of 60 seconds. As in Chapter-14: a timeout puts an upper limit on how long one service's problem can slow down another.

    /healthz. A tiny health endpoint that nginx answers itself, without asking any service. Compose uses it in Step-4. It deliberately doesn't check the services: if it did, one service being down would make the gateway unhealthy, and the whole store would lose its entry point, including the parts that still work.

    The API routes. location /api/products matches every path that starts with /api/products, so both /api/products and /api/products/1. The rewrite ... break line removes the /api prefix, so the Product API receives /products/1, the path it has always had. The services don't know that the public address has an /api in front of it, and they don't need to.

    There is one place where that hidden prefix leaks out: the Location header of a 201 Created. The Product API answers a new product with Location: http://localhost:8080/products/7, which is wrong from outside the gateway. proxy_redirect rewrites the Location header of the answer, and puts the /api back. The regular expression handles both full URLs (the Product API) and paths (the Order API sends Location: /orders/<id>).

    The rate limit. limit_req zone=orders burst=5 nodelay applies the orders zone to /api/orders: each client address may place 2 orders per second on average, plus a burst of up to 5 extra requests at once (burst=5), which are passed on straight away instead of being slowed down (nodelay). Anything beyond that is rejected with the status from limit_req_status, 429 Too Many Requests (nginx's default would be 503, which wrongly suggests the service is down). A customer placing an order sends one request; a script hammering the endpoint, or a double-click storm, gets stopped at the gateway before it reaches the Order API and its database. The numbers are an example: pick yours from what normal use of your system looks like. Two things to know about this simple version: the counters are per gateway container, so two gateways allow twice as much, and all requests from your own machine arrive from the same Docker address, so in this lab you share one budget with yourself.

    The JSON errors. Without error_page, nginx answers a service it can't reach with its own HTML page, which an API client can't read. error_page 502 @api_502 replaces it with the named location @api_502, which returns a problem details body (RFC 9457), the same format the APIs use for their own errors, including the request id. The gateway produces three errors itself: 502 Bad Gateway when it can't reach the service (name not found, connection refused), 504 Gateway Timeout when the service doesn't answer in time, and 429 from the rate limit. An error that a service sends, such as the Order API's 503 when the Product API is down, or a 404 for a product that doesn't exist, passes through unchanged: the gateway only speaks for itself. The error_page lines sit in the API locations only, so the websites keep nginx's normal error pages.

    Unknown API paths. location /api/ catches every other path under /api/ and answers with a JSON 404. Without it, /api/typo would fall through to the Storefront and get its index.html with status 200, a confusing answer for an API client.

    The Admin site. location /admin passes the request on unchanged, /admin/Home/Create included. That's deliberate, and the reason for the path base setting in Step-4.

    Everything else goes to the Storefront. location / is the shortest prefix, so nginx uses it only when no other location matches. The Storefront's own nginx does the single-page application fallback (Chapter-7), so addresses like /orders/123 still return the React app.

    Step-3: Add the gateway's Dockerfile

    The gateway needs no build step, only nginx and the configuration file. Create gateway/Dockerfile:

    gateway/Dockerfile
    # The store's API gateway: nginx running as a non-root user on port 8080,
# with the routes in nginx.conf (chapter 15)
FROM nginxinc/nginx-unprivileged:alpine
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 8080
USER nginx

    It's the serve stage of the Storefront's Dockerfile from Chapter-7, without the files of a website. COPY replaces the image's default site with our configuration. Add a gateway/.dockerignore as well, so only the configuration file is sent to the build:

    gateway/.dockerignore
    # Only nginx.conf goes into the image
*
!nginx.conf

    Step-4: Put the gateway in the compose file

    Add the gateway service to compose.yaml, after storefront:

    compose.yaml (excerpt)
      gateway:
    build: ./gateway
    image: sample/gateway
    ports:
      # The store's only published port. 127.0.0.1 keeps it on your machine:
      # nothing signs users in yet, so the admin site must not be on your network.
      - "127.0.0.1:8080:8080"
    depends_on:
      storefront:
        condition: service_healthy
      admin:
        condition: service_healthy
      product-api:
        condition: service_healthy
      order-api:
        condition: service_healthy
    healthcheck:
      # /healthz answers from the gateway itself, without asking the services
      test: ["CMD", "wget", "-q", "--spider", "http://127.0.0.1:8080/healthz"]
      interval: 10s
      timeout: 5s
      retries: 3
      start_period: 10s
      start_interval: 2s
    restart: unless-stopped
    networks: [store]
    • ports publishes the gateway's port 8080 on port 8080 of your machine. It's the only ports entry in the whole file. 127.0.0.1 keeps it reachable from your machine only, like the temporary dev ports were: until the next chapter adds sign-in, anyone who can reach the Admin site can change products.
    • depends_on starts the gateway after the four services it routes to are healthy, so the first request after docker compose up --wait doesn't hit a service that is still starting. As in Chapter-14, this only affects start-up; the resolver and the JSON errors handle a service that goes down later.
    • The health check uses BusyBox wget, like the Storefront's, against /healthz.

    Now the Admin site. Add PATHBASE to its environment:

    compose.yaml (excerpt)
      admin:
    build: ./admin
    image: sample/admin
    environment:
      # The admin site reads and adds products through the Product API (chapter 14)
      PRODUCT_API_URL: http://product-api:8080
      # The gateway sends /admin/... to the site, which then builds every link under /admin (chapter 15)
      PATHBASE: /admin
    # healthcheck, restart and networks as before

    The path base gotcha. A website that runs under a sub-path of someone else's address has two problems, and it's worth seeing both:

    • If the gateway passes /admin/Home/Create on unchanged and the app doesn't know about the prefix, the app looks for a page called /admin/Home/Create, finds none, and answers 404. I tried it: without PATHBASE, http://localhost:8080/admin/ returns 404 Not Found with an empty page.
    • If the gateway removed the prefix instead (as it does for the APIs), the first page would load, but every link the app builds would point to the root: the stylesheet at /css/site.css, the menu at /Home/Runtime, the form posting to /Home/Create. The browser would ask the gateway for those, the gateway would send them to the Storefront, and you'd get a page without styles and links that open the shop.

    UsePathBase, which you added in Chapter-6, solves both: with PATHBASE=/admin, the app strips /admin from every incoming path before routing, and adds it to every link, form address, script and stylesheet that the tag helpers build. That's why the gateway passes /admin on unchanged for the Admin site, while it strips /api for the APIs: the APIs don't build links to themselves for browsers, the website does. The health check in compose still calls /health/live without the prefix, which also works, because UsePathBase leaves paths that don't start with the prefix alone.

    The forwarded headers from Chapter-6 are the other half: behind the gateway, the Admin site sees X-Forwarded-For and X-Forwarded-Proto and uses them as the client's address and scheme. The Chapter-6 code trusts these headers from any address, which is only safe because the gateway is the only way in. Now that the Admin site has no published port, that's true.

    rm compose.dev-ports.yaml      # Windows PowerShell: Remove-Item compose.dev-ports.yaml

    502 or 504

    You may see 504 Gateway Timeout instead, with the same JSON format and "title":"Gateway Timeout". That happens when the gateway still has the stopped container's address from a lookup in the last 10 seconds (valid=10s): it tries to connect, gets no answer, and gives up after proxy_connect_timeout (2 seconds). On a Linux machine, such as the book's CI runner, this is what we saw. Either way the client gets a fast, clear JSON error instead of a hanging request or an HTML page.

    {"type":"about:blank","title":"Too Many Requests","status":429,"detail":"Too many requests. Slow down and try again in a moment.","requestId":"c969176fffdcea0b7a9d07eee914d65f"}

    and the gateway logs it:

    docker compose logs gateway | grep -m 1 'limiting requests'

# output
gateway-1  | 2026/11/16 00:17:01 [error] 30#30: *26 limiting requests, excess: 5.656 by zone "orders", client: 172.20.0.1, server: _, request: "POST /api/orders/ HTTP/1.1", host: "localhost:8080"

    Wait a few seconds and orders pass again. In the Storefront, a refused order shows Your order could not be placed (HTTP 429). and keeps the cart.

    A rate limit at the gateway is a first line of defence, not the whole story. In production you'd limit per signed-in user or API key rather than per address (many users can share one address behind a company proxy), keep the counters in a shared store when you run several gateways, and send a Retry-After header. Managed gateways such as Azure API Management offer all of that as configuration.

    When you are done, stop the store with docker compose down (keeps the data) or docker compose down -v (deletes it).

    Troubleshooting

    Problem What to do
    port is already allocated on 8080 Another container or program uses port 8080, often a single-service lab from an earlier chapter. docker ps lists containers; stop the one that uses it
    curl localhost:5001 (or 5002 to 5004) still answers The services still have their dev ports. Run docker compose up -d --build --wait without -f compose.dev-ports.yaml, so compose recreates them without ports
    /admin/ returns 404 PATHBASE: /admin is missing on the admin service, or the container wasn't recreated: docker compose up -d
    The Admin site loads without styles, or its links open the Storefront The gateway strips /admin, or PATHBASE is wrong. The gateway must pass /admin on unchanged, and PATHBASE must be exactly /admin
    /api/... returns 502 with could not be resolved in the gateway log The service is stopped or not on the store network: docker compose ps and docker compose logs <service>
    A service works again, but the gateway still answers 502 The gateway caches DNS answers for 10 seconds (valid=10s); wait and try again
    The gateway doesn't start: host not found in upstream A proxy_pass uses a service name directly instead of a variable. Use set $name http://...; and proxy_pass $name; with the resolver line
    Orders return 429 You sent more than about 2 orders per second, plus the burst of 5. Wait a few seconds
    npm run dev shows the error message and Vite reports a proxy error Start the store, so the gateway answers on port 8080

    Conclusion

    In this chapter, we put an API gateway in front of the store: one nginx container, the only one with a published port, that routes / to the Storefront, /admin to the Admin site and /api/products and /api/orders to the two APIs, removing the /api prefix on the way. The Storefront and the APIs now share one origin, so the React app calls relative URLs and needs neither runtime configuration nor CORS. The Admin site runs under /admin thanks to PATHBASE and the forwarded headers from Chapter-6. The gateway passes on Host, X-Forwarded-For, X-Forwarded-Proto, Authorization and traceparent, creates a request id for every request that comes without one, limits how long a slow service can hold a client, answers in JSON when it can't reach an API, and stops a burst of orders with 429. The temporary dev ports and proxies from Chapters 13 and 14 are gone.

    We kept the gateway to plumbing on purpose: no business logic, nothing that has to change when a service gets a new feature. One important piece of plumbing is still missing, though: anyone who can reach port 8080 can place orders as anonymous and change the catalog in the Admin site. In the next chapter, Chapter-16: Securing Services with Keycloak, customers and staff sign in with Keycloak, and the APIs check the access token that the gateway now passes on in the Authorization header.
