    Chapter-4: Build the Product API with .NET

    Sample code

    The complete, tested code for this chapter is in samples/microservices/product-api. Use it to compare against your own work.

    Introduction

    Welcome to the first lab where we build a real service for our online store. In Chapter-1 we designed the store as a set of independent services, and in Chapter-3 we built our first image from a Dockerfile. Now we put the two together.

    In this lab we will create the Product API: a RESTful service built with ASP.NET Core Web API on .NET 10. We will create the project, replace the template's sample code with real product endpoints, test them, and finally package the API as a Docker image and run it in a container.

    Technical Scenario

    As a Backend (BE) developer, you have been asked to build the Product API, the service that owns the store's product catalog: every product's SKU, name, description and price. Everything else in the store asks this service when it needs product data:

    • the Storefront shows the products to customers,
    • the Admin site lets staff add, change and remove products,
    • the Order API looks up names and prices when a customer places an order.

    Because the Product API is the only service that owns product data, no other service reads its database directly; they all go through its HTTP endpoints. That is what keeps the services independent.

    In this chapter the API keeps its products in memory, so you can build and run it on its own. A later chapter moves the data to its own SQL Server database without changing the endpoints.

    Objective

    In this exercise, our objective is to accomplish and learn the following tasks:

    • Step-1: Create a new repo in Azure DevOps
    • Step-2: Clone the repo from Azure DevOps
    • Step-3: Create a new .NET Web API project
    • Step-4: Add the product endpoints
    • Step-5: Run and test the Product API
    • Step-6: Containerize the Product API
    • Step-7: Push docker container to ACR (optional)
    • Step-8: Pull docker container from ACR (optional)

    Prerequisites

    Before starting this lab, ensure you have the following prerequisites in place:

    • .NET 10 SDK
    • Docker Desktop (see Chapter-2)
    • Visual Studio Code or another code editor
    • Git client tool
    • curl, to call the API from a terminal (included with macOS, Linux, Git Bash and Windows 10 or later)
    • For the optional steps only: an Azure DevOps organization and project (Chapter-1) and an Azure Container Registry (ACR)

    The following diagram shows what we build in this chapter: the Product API running in its own container, answering HTTP requests on port 8080 and keeping its products in memory.

    The API we are building has these endpoints:

    Method Path Result
    GET /products 200 with the list of products
    GET /products/{id} 200 with one product, or 404
    POST /products 201 with the new product; 400 for invalid input; 409 if the SKU is taken
    PUT /products/{id} 204, or 404; 400 and 409 as for POST
    DELETE /products/{id} 204, or 404
    GET /health/live, /health/ready 200 when the service is up and ready

    A product looks like this in JSON:

    { "id": 1, "sku": "MUG-001", "name": "Coffee mug", "description": "Ceramic mug, 350 ml.", "price": 9.99 }

    Step-3: Create a new .NET Web API project

    Using the ASP.NET Core Web API template, we will create the project that becomes our Product API.

    First, check that the .NET 10 SDK is installed:

    dotnet --version

# output
10.0.114

    Any 10.0.x version is fine. From the root of your microservices repository, create the project:

    dotnet new webapi --use-controllers --no-https -f net10.0 -n productapi -o product-api

    Here is what each option does:

    • --use-controllers uses controller classes instead of minimal APIs. Controllers keep the endpoints of one resource together in one class, which is easy to read when you are starting out.
    • --no-https creates an app that runs without an HTTPS certificate. Inside a container the API serves plain HTTP; TLS is handled in front of it.
    • -f net10.0 targets .NET 10, the current long-term support (LTS) release.
    • -n productapi sets the project name, so the project file is productapi.csproj and the C# namespace is productapi.
    • -o product-api creates the project in a folder called product-api. That is the service's name in our store.

    Step-4: Add the product endpoints

    Now we add the code that makes this the Product API: a model for a product, a place to keep the products, and a controller with the endpoints.

    The model

    Create a Models folder and add Product.cs:

    Models/Product.cs
    using System.ComponentModel.DataAnnotations;

namespace productapi.Models;

// A product in the store's catalog: the JSON the API returns.
public record Product(int Id, string Sku, string Name, string Description, decimal Price);

// The body of POST and PUT requests. The API assigns the id itself.
public class ProductInput
{
    [Required, StringLength(32)]
    public string Sku { get; set; } = string.Empty;

    [Required, StringLength(100)]
    public string Name { get; set; } = string.Empty;

    [StringLength(500)]
    public string Description { get; set; } = string.Empty;

    [Range(0.01, 99_999_999.99)]
    public decimal Price { get; set; }
}
    • Product is a C# record: a small, read-only type that is perfect for data we send as JSON. ASP.NET Core turns the property names into camelCase JSON (id, sku, name, ...).
    • ProductInput is what clients send when they create or change a product. They don't send an id; the API chooses it. The attributes ([Required], [StringLength], [Range]) describe valid input, and ASP.NET Core checks them for us.
    • Prices use decimal, not double, because money must not suffer from floating-point rounding.

    The repository

    The controller should not care where products are stored. We hide the storage behind an interface, so that a later chapter can swap the in-memory list for a database without changing the controller. Create a Data folder and add IProductRepository.cs:

    Data/IProductRepository.cs
    using productapi.Models;

namespace productapi.Data;

// Everything the API needs from its product store. The controller only
// talks to this interface, so the storage can change without touching it.
public interface IProductRepository
{
    IReadOnlyList<Product> GetAll();
    Product? GetById(int id);
    bool SkuExists(string sku, int? exceptId = null);
    Product Add(ProductInput input);
    bool Update(int id, ProductInput input);
    bool Delete(int id);
}

    Then add the in-memory implementation, seeded with the store's five products, in InMemoryProductRepository.cs:

    Data/InMemoryProductRepository.cs
    using productapi.Models;

namespace productapi.Data;

// Keeps the products in memory, starting with five seed products.
// Changes are lost when the app stops.
public class InMemoryProductRepository : IProductRepository
{
    private readonly Lock _lock = new();
    private readonly List<Product> _products =
    [
        new(1, "MUG-001", "Coffee mug", "Ceramic mug, 350 ml.", 9.99m),
        new(2, "TEE-001", "T-shirt", "Cotton T-shirt with the store logo.", 19.99m),
        new(3, "CAP-001", "Baseball cap", "Adjustable cotton cap, one size.", 14.50m),
        new(4, "BAG-001", "Tote bag", "Reusable canvas tote bag.", 12.00m),
        new(5, "BTL-001", "Water bottle", "Stainless steel bottle, 500 ml.", 24.95m),
    ];
    private int _nextId = 6;

    public IReadOnlyList<Product> GetAll()
    {
        lock (_lock) return _products.ToList();
    }

    public Product? GetById(int id)
    {
        lock (_lock) return _products.FirstOrDefault(p => p.Id == id);
    }

    public bool SkuExists(string sku, int? exceptId = null)
    {
        lock (_lock)
        {
            return _products.Any(p => p.Id != exceptId &&
                string.Equals(p.Sku, sku, StringComparison.OrdinalIgnoreCase));
        }
    }

    public Product Add(ProductInput input)
    {
        lock (_lock)
        {
            var product = new Product(_nextId++, input.Sku, input.Name, input.Description, input.Price);
            _products.Add(product);
            return product;
        }
    }

    public bool Update(int id, ProductInput input)
    {
        lock (_lock)
        {
            var index = _products.FindIndex(p => p.Id == id);
            if (index < 0) return false;
            _products[index] = new Product(id, input.Sku, input.Name, input.Description, input.Price);
            return true;
        }
    }

    public bool Delete(int id)
    {
        lock (_lock) return _products.RemoveAll(p => p.Id == id) > 0;
    }
}

    A web server handles many requests at the same time, so every method takes a lock before it touches the list. Without it, two requests adding a product at the same moment could corrupt the list.

    The controller

    Add ProductsController.cs to the Controllers folder:

    Controllers/ProductsController.cs
    using Microsoft.AspNetCore.Mvc;
using productapi.Data;
using productapi.Models;

namespace productapi.Controllers;

[ApiController]
[Route("products")]
public class ProductsController(IProductRepository repository) : ControllerBase
{
    // GET /products
    [HttpGet]
    public IReadOnlyList<Product> GetAll() => repository.GetAll();

    // GET /products/1
    [HttpGet("{id:int}")]
    public ActionResult<Product> GetById(int id)
    {
        var product = repository.GetById(id);
        return product is null ? NotFound() : product;
    }

    // POST /products
    [HttpPost]
    public ActionResult<Product> Create(ProductInput input)
    {
        if (repository.SkuExists(input.Sku))
        {
            return Problem(title: $"A product with SKU '{input.Sku}' already exists.",
                statusCode: StatusCodes.Status409Conflict);
        }

        var product = repository.Add(input);
        return CreatedAtAction(nameof(GetById), new { id = product.Id }, product);
    }

    // PUT /products/1
    [HttpPut("{id:int}")]
    public IActionResult Update(int id, ProductInput input)
    {
        if (repository.GetById(id) is null)
        {
            return NotFound();
        }

        if (repository.SkuExists(input.Sku, exceptId: id))
        {
            return Problem(title: $"A product with SKU '{input.Sku}' already exists.",
                statusCode: StatusCodes.Status409Conflict);
        }

        repository.Update(id, input);
        return NoContent();
    }

    // DELETE /products/1
    [HttpDelete("{id:int}")]
    public IActionResult Delete(int id)
    {
        return repository.Delete(id) ? NoContent() : NotFound();
    }
}

    Let's walk through the important parts:

    • [ApiController] switches on API behaviors. The most useful one: if the request body breaks a validation attribute on ProductInput, ASP.NET Core answers 400 Bad Request with the list of errors before our method even runs.
    • [Route("products")] puts every endpoint of this controller under /products, and {id:int} only matches whole numbers.
    • The controller receives an IProductRepository in its constructor. ASP.NET Core's dependency injection creates and passes it in; we register it in Program.cs next.
    • Each method returns the HTTP status from the contract: NotFound() is 404, CreatedAtAction(...) is 201 with a Location header pointing at the new product, NoContent() is 204, and Problem(...) is an error in the standard problem details JSON format.

    Program.cs

    Finally, replace the contents of Program.cs:

    Program.cs
    using Microsoft.AspNetCore.Diagnostics.HealthChecks;
using productapi.Data;

var builder = WebApplication.CreateBuilder(args);

// Add services to the container.
builder.Services.AddControllers();
builder.Services.AddProblemDetails();
// Learn more about configuring OpenAPI at https://aka.ms/aspnet/openapi
builder.Services.AddOpenApi();
builder.Services.AddHealthChecks();
// One product list shared by every request
builder.Services.AddSingleton<IProductRepository, InMemoryProductRepository>();

var app = builder.Build();

// Configure the HTTP request pipeline.
if (app.Environment.IsDevelopment())
{
    app.MapOpenApi();
}

// Return errors as JSON problem details instead of empty responses
app.UseExceptionHandler();
app.UseStatusCodePages();

app.MapControllers();

// Liveness: the process is up, so it runs no checks.
app.MapHealthChecks("/health/live", new HealthCheckOptions { Predicate = _ => false });
// Readiness: runs every registered check (none yet, so it is always healthy).
app.MapHealthChecks("/health/ready");

app.Run();
    • AddSingleton<IProductRepository, InMemoryProductRepository>() creates one repository for the whole app. If we registered it per request, every request would start again from the five seed products.
    • AddProblemDetails(), UseExceptionHandler() and UseStatusCodePages() make every error, including an unknown URL or an unexpected exception, come back as problem details JSON instead of an empty response. Clients can then handle every error the same way.
    • The OpenAPI document (a machine-readable description of the API) is published only in the Development environment, at /openapi/v1.json. The container runs in Production, where it stays off.
    • The two health endpoints are how a container platform asks a service whether it is alive (/health/live) and ready to take traffic (/health/ready). Liveness runs no checks: if the process can answer, it is alive. Readiness runs every registered check; once the API has a database, a database check goes there.

    Tip

    The template also created productapi.http. Replace its content with the requests from the sample to call every endpoint from Visual Studio, or from VS Code with the REST Client extension.

    Step-6: Containerize the Product API

    Now we package the Product API as a Docker image, so that it runs the same way on every machine.

    The Dockerfile

    Create a file called Dockerfile (no extension) in the product-api folder:

    Dockerfile
    # Build stage: restore and publish with the .NET SDK
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
COPY productapi.csproj ./
RUN dotnet restore
COPY . .
RUN dotnet publish productapi.csproj -c Release -o /app/publish --no-restore

# Runtime stage: smaller ASP.NET runtime image, non-root user, port 8080
FROM mcr.microsoft.com/dotnet/aspnet:10.0 AS final
WORKDIR /app
COPY --from=build /app/publish .
EXPOSE 8080
USER $APP_UID
ENTRYPOINT ["dotnet", "productapi.dll"]

    This is a multi-stage build: the first stage compiles the app with the full SDK, and the second stage keeps only the compiled output. Line by line:

    • FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build starts the build stage from Microsoft's .NET 10 SDK image, which contains the compiler and the dotnet tools. AS build names the stage so we can copy from it later.
    • WORKDIR /src creates the /src folder in the image and makes it the current folder for the next instructions.
    • COPY productapi.csproj ./ and RUN dotnet restore copy only the project file and download the NuGet packages. Docker caches every step as a layer; because the project file rarely changes, the next build reuses the restored packages and skips this slow step.
    • COPY . . copies the rest of the source code.
    • RUN dotnet publish ... -c Release -o /app/publish --no-restore compiles the app in Release mode into /app/publish. --no-restore skips the restore we already did.
    • FROM mcr.microsoft.com/dotnet/aspnet:10.0 AS final starts a fresh stage from the much smaller ASP.NET Core runtime image. It can run the app but contains no SDK, so the final image is smaller and has fewer tools an attacker could use.
    • WORKDIR /app and COPY --from=build /app/publish . copy just the published output from the build stage.
    • EXPOSE 8080 documents the port the app listens on. Since .NET 8, the ASP.NET Core images listen on port 8080 by default.
    • USER $APP_UID runs the app as app, the non-root user that the .NET images include, instead of root. If someone ever broke into the app, they would not have root rights inside the container.
    • ENTRYPOINT ["dotnet", "productapi.dll"] is the command that starts the API when the container starts.

    The container serves plain HTTP only; there is no HTTPS certificate inside it. In the finished store, the gateway is the single entry point in front of the services.

    The .dockerignore file

    When you run docker build, Docker first sends the folder (the build context) to the build engine, and COPY . . copies all of it into the image. The local bin and obj folders that dotnet build created on your machine should not go into the image: they are large, and they would mix your local build output with the clean build inside the container. Create a .dockerignore file next to the Dockerfile:

    .dockerignore
    bin/
obj/

    When you are done, stop and remove the container, so that port 8080 is free for the next lab:

    Because the products live in memory, removing the container also removes the pen we added; a new container starts again with the five seed products.

    Step-7: Push docker container to ACR

    This step and the next are optional. They show how to share your image through a private registry, Azure Container Registry (ACR), so that other machines and environments can pull it. You need an Azure subscription and an existing registry; deploying images from ACR to Kubernetes is covered in the companion book, Building Scalable Kubernetes Infrastructure for Microservices.

    The commands below use the registry name acr1dev and resource group rg-acr-dev as examples; replace them with your own.

    1. Log in to Azure and to your registry:

      # Azure login
az login

# set the azure subscription
az account set -s "<subscription-name>"

# Log in to the container registry
az acr login --name acr1dev

# Get the login server address
az acr list --resource-group rg-acr-dev --query "[].{acrLoginServer:loginServer}" --output table

      The login server is <registry-name>.azurecr.io, for example acr1dev.azurecr.io.

    2. Tag the image with the full name of your registry:

      docker tag sample/product-api:1.0 acr1dev.azurecr.io/sample/product-api:1.0

    3. Push the image:

      docker push acr1dev.azurecr.io/sample/product-api:1.0

      Output (example; layer ids and digest differ on your machine):

      The push refers to repository [acr1dev.azurecr.io/sample/product-api]
<layer-id>: Pushed
...
1.0: digest: sha256:<digest> size: <size>

    4. Verify the image in the registry:

      az acr repository list --name acr1dev --output table
az acr repository show-tags --name acr1dev --repository sample/product-api --output table

      The first command lists sample/product-api among your repositories, and the second lists the tag 1.0.

    Step-8: Pull docker container from ACR

    Pulling an image from ACR is useful when you want to run exactly the image that another machine built, for example while troubleshooting.

    1. Log in to the registry, then pull the image:

      az acr login --name acr1dev
docker pull acr1dev.azurecr.io/sample/product-api:1.0

    2. Run it, exactly as you ran the local image:

      docker run -d --name product-api -p 8080:8080 acr1dev.azurecr.io/sample/product-api:1.0
curl http://localhost:8080/products
docker rm -f product-api

    Conclusion

    In this chapter, we built the first service of our online store. The Product API owns the product catalog and offers it through a small REST API: list, get, add, change and remove products, with validation, clear error responses and health endpoints. We packaged it with a multi-stage Dockerfile into an image that runs as a non-root user, ran it in a container, and tested every endpoint with curl.

    In the next chapter, we will build the Order API with Node.js, the service that lets customers place orders. Later, Chapter-12 moves the products from memory into the Product API's own SQL Server database.
