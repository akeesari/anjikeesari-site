    Chapter-16: Securing Services with Keycloak

    Sample code

    The complete, tested code for this chapter is in samples/microservices: the realm in keycloak/store-realm.json, compose.yaml, .env.example, the token checks in product-api and order-api, the sign-in in admin and storefront, and scripts/test-token.sh. Use it to compare against your own work.

    Introduction

    At the end of Chapter-15, the store had one front door: an API gateway on http://localhost:8080. But anyone who reached that door could do anything. Every order belonged to anonymous, anybody could add or delete products in the Admin site, and the Product API accepted a POST from whoever sent one.

    In Chapter-10 we ran Keycloak in a container and listed what it should do for a microservices system: secure the API endpoints, use JSON Web Tokens, give users single sign-on. In this lab, I will guide you through actually doing that. Customers sign in to the Storefront, staff sign in to the Admin site, and both APIs check the access token on every request themselves. Along the way we look at the ideas behind it (OAuth 2.0, OpenID Connect, access tokens and ID tokens), the one Keycloak setting that trips up almost everyone who runs it in Docker, and how each of our four stacks (.NET API, Node.js API, ASP.NET Core MVC and React) plugs into it.

    Demo users and secrets

    This chapter creates two demo users, alice and bob, whose password is replaceme, and uses replaceme as the Admin site's client secret. They exist so that you can try everything on your own machine. They are demo values only: never use them, or the demo realm, anywhere real.

    Technical Scenario

    As a Security minded developer on the team, you have been asked to put sign-in and access control into the store. The team agreed on these rules:

    • One identity provider. Keycloak signs everybody in and issues the tokens. No service stores passwords.
    • Browsing is public, changing things is not. Anyone may look at products. Placing an order needs a signed-in customer; changing the catalog needs the admin role.
    • Every service checks for itself. The gateway passes the Authorization header on, and each API validates the token's signature, issuer, audience and expiry. Nobody trusts a request just because it came from inside the network.
    • Identity comes from the token. The Order API takes the customer from the token, never from the request body, and customers see only their own orders.
    • Current advice only. Authorization code flow with PKCE for every sign-in; no implicit flow; the password grant only for a test client that the smoke test uses.

    Step-1: Understand authentication, authorization and tokens

    Before we touch any code, let's get the vocabulary straight. Most security mistakes come from mixing up two or three of these words.

    Authentication and authorization. Authentication answers "who are you?": alice proves who she is by signing in. Authorization answers "what may you do?": alice may place orders, but only bob may change products. Keycloak does the authentication and tells our services who the user is and which roles they have. Each service then makes its own authorization decisions.

    OAuth 2.0 and OpenID Connect. OAuth 2.0 (RFC 6749) is a framework for giving an application access to an API, with an access token. It defines four roles, and every one of them exists in our store:

    OAuth 2.0 role Meaning In the store
    Resource owner The person who owns the data and grants access alice, bob
    Client The application that wants to call an API for the user storefront, admin
    Authorization server Signs the user in and issues tokens Keycloak
    Resource server The API that accepts access tokens product-api, order-api

    OAuth 2.0 on its own doesn't tell the client who the user is. OpenID Connect is a thin layer on top of OAuth 2.0 that does: when a client asks for the openid scope, it also gets an ID token about the signed-in user. In short: OAuth 2.0 is for access, OpenID Connect adds sign-in.

    Client types. A confidential client can keep a secret, because its code runs on a server you control. The Admin site is one. A public client can't: anything in a browser app or a mobile app can be read by its user. The Storefront is a public client, so it has no secret at all.

    Three kinds of tokens.

    Token Who it is for What it's for
    Access token The API (resource server) Sent in Authorization: Bearer <token> to call an API. The API checks it on every request
    ID token The client Tells the client who signed in. Its audience is the client itself; never send it to an API
    Refresh token Keycloak Lets the client get a new access token without asking the user to sign in again

    JSON Web Tokens. Keycloak's access and ID tokens are JSON Web Tokens (JWT, RFC 7519): three base64url-encoded parts separated by dots, header.payload.signature. The header says how the token was signed (for example RS256 and the id of the key). The payload holds the claims, and these are the ones that matter most to an API:

    Claim Meaning Our APIs check
    iss (issuer) Who issued the token It is exactly http://localhost:8081/realms/store
    aud (audience) Who the token is meant for It contains product-api (or order-api); a token for someone else must be rejected
    exp (expiration) When the token stops being valid It isn't in the past
    sub (subject) The user's unique id in this realm The Order API stores it as the customer id
    realm_access.roles The user's Keycloak realm roles (Keycloak-specific) The Product API requires admin for changes

    The signature is made with Keycloak's private key. Keycloak publishes the matching public keys as a JSON Web Key Set (JWKS) at /realms/store/protocol/openid-connect/certs. Anybody can read a JWT's payload (it is only encoded, not encrypted), but nobody can change it without breaking the signature. That's why an API can trust a token it has never seen before, as long as it verifies the signature with Keycloak's public key and checks the claims.

    Scopes, roles and audience. A scope is what the client asks for when the user signs in (openid profile email). A role is what the user is allowed to do (customer, admin). The audience is which API the token is for. RFC 9700 recommends restricting access tokens to the APIs that should accept them, so that a token stolen from one service can't be replayed against another.

    The authorization code flow with PKCE. This is how both of our websites sign users in. The user types their password only on Keycloak's own page; the website never sees it.

    sequenceDiagram
  autonumber
  participant B as Browser
  participant C as Client (storefront or admin)
  participant K as Keycloak
  participant A as API
  B->>C: Click "Sign in"
  C->>C: Make a random code_verifier and its SHA-256 hash, the code_challenge
  C->>B: Redirect to Keycloak with client_id, redirect_uri, scope, state and code_challenge
  B->>K: GET /realms/store/protocol/openid-connect/auth
  K->>B: Sign-in page
  B->>K: Username and password (only Keycloak sees them)
  K->>B: Redirect back to redirect_uri with a one-time code
  B->>C: The code
  C->>K: POST /token with the code and the code_verifier (plus the secret, for a confidential client)
  K->>K: Hash the code_verifier and compare it with the code_challenge
  K->>C: Access token, ID token, refresh token
  C->>A: API call with Authorization: Bearer access token
  A->>A: Check signature, iss, aud, exp, then roles
  A->>C: 200, 201, 401 or 403

    PKCE (RFC 7636, "pixie") protects the one-time code that Keycloak sends back through the browser. The client makes a random code_verifier and sends only its hash (code_challenge, method S256) with the sign-in request. When it exchanges the code for tokens, it must send the original verifier. An attacker who steals the code from the redirect can't use it, because they don't have the verifier. RFC 9700, the OAuth 2.0 Security Best Current Practice, says public clients must use PKCE and recommends it for confidential clients too, so we use it for both.

    Flows we don't use. RFC 9700 says clients should not use the implicit flow (tokens returned directly in the browser's address bar), and that the resource owner password credentials grant (the client collects the user's password and sends it to the token endpoint) must not be used: it hands the user's password to the client, teaches users to type it outside the identity provider, and can't support multi-factor sign-in. We use the password grant in exactly one place, a test-only client for the CI smoke test and the curl examples in Step-11, and the realm marks that client as such.

    Why do the APIs check tokens themselves? The gateway could check tokens for everybody, and in many systems it does check something. But if the APIs trusted any request that reached them, a single mistake (a debug port published by accident, a compromised container on the network, a new route that skips the gateway) would open everything. This is zero trust: no request is trusted because of where it comes from, only because of what it proves. Checking in each service is also defence in depth: the gateway can reject obvious junk early, but the service that owns the data makes the final decision. As we said in Chapter-15, checking a token is plumbing, while deciding that alice may only see her own orders is business logic, so it lives in the Order API.

    Step-2: Design the store realm

    A Keycloak realm is an isolated space with its own users, roles, clients and keys. The store gets its own realm, store, so it never mixes with Keycloak's master realm (which is only for administering Keycloak). Here is what goes in it:

    Item Name Settings and why
    Realm role customer Shops in the Storefront
    Realm role admin Manages the catalog in the Admin site
    Client storefront Public (no secret), authorization code flow with PKCE S256, exact redirect URIs http://localhost:8080/ and http://localhost:8080/silent-check-sso.html (plus the same on Vite's port 5173 for npm run dev)
    Client admin Confidential (client secret from .env), authorization code flow with PKCE S256, redirect URI http://localhost:8080/admin/signin-oidc, puts the realm roles into the ID token
    Client smoke-test Test only. Public, password grant only, tokens live 30 seconds. Used by scripts/test-token.sh and the CI smoke test
    Audience product-api, order-api An audience mapper on each client adds both API names to the aud claim of its access tokens
    User alice Role customer, email alice@example.com, password replaceme (demo only)
    User bob Role admin, email bob@example.com, password replaceme (demo only)
    Tokens Realm settings Access tokens live 5 minutes; refresh tokens are rotated (each refresh token works once)

    A few of these choices deserve a word:

    • Exact redirect URIs. After sign-in, Keycloak sends the code only to an address registered for the client. RFC 9700 requires exact string matching, because a wildcard like http://localhost:8080/* would also cover pages you never meant to receive codes, such as /admin/... for the Storefront. Keycloak still lets you register wildcards, so it's on you to list exact addresses.
    • Roles for people, audience for services. customer and admin describe what a person may do; aud says which API a token is for. The APIs check both: the audience on every request, the role where an action needs it.
    • Refresh token rotation. RFC 9700 says refresh tokens for public clients must be sender-constrained or rotated. Keycloak's realm setting Revoke Refresh Token "revokes refresh tokens and issues another token that the client must use", and refreshTokenMaxReuse: 0 lets each one be used only once.

    You could click all of this together in the admin console, as you did in Chapter-10. But then every teammate, every CI run and every fresh docker compose down -v would have to repeat the clicks. Instead, we describe the realm in a JSON file and let Keycloak import it at start-up. The realm becomes code, reviewed and versioned with the services that depend on it.

    Step-3: Write the realm file

    Keycloak imports realm files at start-up when you pass --import-realm: it reads every .json file in /opt/keycloak/data/import, and the file for a realm must be named <realm name>-realm.json. So create keycloak/store-realm.json next to the Chapter-10 files. It starts with the realm settings and the two roles:

    keycloak/store-realm.json (start)
    {
  "realm": "store",
  "displayName": "Store (demo)",
  "enabled": true,
  "sslRequired": "external",
  "accessTokenLifespan": 300,
  "revokeRefreshToken": true,
  "refreshTokenMaxReuse": 0,
  "roles": {
    "realm": [
      {
        "name": "customer",
        "description": "Shops in the storefront and places orders"
      },
      {
        "name": "admin",
        "description": "Manages the product catalog in the admin site"
      }
    ]
  },

    accessTokenLifespan is in seconds, so access tokens live 5 minutes. sslRequired: external is Keycloak's default: HTTPS is required for requests from public IP addresses, but not from your own machine and private networks such as Docker's.

    Then the clients array. The Storefront is a public client, with PKCE and exact redirect URIs:

    keycloak/store-realm.json (the storefront client)
      "clients": [
    {
      "clientId": "storefront",
      "name": "Storefront",
      "description": "The React storefront: a public client (no secret) using authorization code + PKCE",
      "enabled": true,
      "publicClient": true,
      "standardFlowEnabled": true,
      "implicitFlowEnabled": false,
      "directAccessGrantsEnabled": false,
      "serviceAccountsEnabled": false,
      "redirectUris": [
        "http://localhost:8080/",
        "http://localhost:8080/silent-check-sso.html",
        "http://localhost:5173/",
        "http://localhost:5173/silent-check-sso.html"
      ],
      "webOrigins": [
        "+"
      ],
      "attributes": {
        "pkce.code.challenge.method": "S256",
        "post.logout.redirect.uris": "+"
      },
      "protocolMappers": [
        {
          "name": "audience product-api",
          "protocol": "openid-connect",
          "protocolMapper": "oidc-audience-mapper",
          "config": {
            "included.custom.audience": "product-api",
            "access.token.claim": "true",
            "id.token.claim": "false",
            "introspection.token.claim": "true"
          }
        },
        {
          "name": "audience order-api",
          "protocol": "openid-connect",
          "protocolMapper": "oidc-audience-mapper",
          "config": {
            "included.custom.audience": "order-api",

    • standardFlowEnabled is Keycloak's name for the authorization code flow. The implicit flow, the password grant (directAccessGrantsEnabled) and service accounts are switched off.
    • pkce.code.challenge.method: S256 makes Keycloak require PKCE with SHA-256 for this client, so a sign-in request without a code challenge is refused.
    • webOrigins: ["+"] allows cross-origin requests from the origins of the redirect URIs. keycloak-js calls Keycloak's token endpoint from the browser, so Keycloak must send CORS headers to http://localhost:8080. post.logout.redirect.uris: "+" allows the same addresses after sign-out.
    • The two audience mappers add product-api and order-api to the aud claim of access tokens, and not to ID tokens.

    The Admin site is a confidential client. Its secret is not in the file: ${ADMIN_CLIENT_SECRET} is a placeholder that Keycloak fills in from an environment variable when it imports the realm, so the only copy of the secret is in your .env file:

      "clientId": "admin",
      "name": "Admin site",
      "description": "The ASP.NET Core MVC admin site: a confidential client (with a secret) using authorization code + PKCE",
      "enabled": true,
      "publicClient": false,
      "clientAuthenticatorType": "client-secret",
      "secret": "${ADMIN_CLIENT_SECRET}",
      "standardFlowEnabled": true,
      "implicitFlowEnabled": false,
      "directAccessGrantsEnabled": false,
      "serviceAccountsEnabled": false,
      "redirectUris": [
        "http://localhost:8080/admin/signin-oidc"
      ],
      "webOrigins": [],
      "attributes": {
        "pkce.code.challenge.method": "S256",
        "post.logout.redirect.uris": "http://localhost:8080/admin/signout-callback-oidc"
      },
      "protocolMappers": [
        (the two audience mappers, as for the storefront)
        {
          "name": "realm roles in the ID token",
          "protocol": "openid-connect",
          "protocolMapper": "oidc-usermodel-realm-role-mapper",
          "config": {
            "claim.name": "realm_access.roles",
            "jsonType.label": "String",
            "multivalued": "true",

    /admin/signin-oidc and /admin/signout-callback-oidc are the default callback paths of ASP.NET Core's OpenID Connect handler, under the site's /admin path base. The extra realm roles mapper puts realm_access.roles into the Admin site's ID token as well: Keycloak's built-in roles scope puts the roles into the access token only, and the Admin site, as the client, should learn who the user is from the ID token, not by opening an access token that is meant for the API.

    The third client is the one for tests:

    keycloak/store-realm.json (the test-only client, audience mappers left out)
        {
      "clientId": "smoke-test",

    Keep the realm file small

    A realm exported from the admin console has thousands of lines: every built-in client, client scope, flow and setting, with generated ids. Our file lists only what differs from Keycloak's defaults, and Keycloak creates the rest on import. One trap I hit while writing it: as soon as a realm file contains a clientScopes list, Keycloak creates only those scopes, and the built-in ones (profile, email, roles, basic, ...) are missing, so tokens lose claims such as sub and realm_access. The import log warns Referenced client scope 'basic' doesn't exist. That's why the audience mappers sit on each client instead of in a shared client scope. To check what Keycloak made of the file, export the realm (admin console: Realm settings > Action > Partial export) and compare.

    Step-4: Add Keycloak to the compose file

    The Keycloak service is the Chapter-10 compose file with three additions: the realm import, the hostname settings and a health check. Add two services to compose.yaml, before networks::

    compose.yaml (excerpt)
      # Sign-in and tokens for the store (chapter 16). Same image as chapter 10.
  keycloak:
    image: quay.io/keycloak/keycloak:26.4
    # start-dev: HTTP and development defaults, for your machine only.
    # --import-realm: create the store realm from the mounted file on the first start
    command: ["start-dev", "--import-realm"]
    environment:
      KC_BOOTSTRAP_ADMIN_USERNAME: admin
      KC_BOOTSTRAP_ADMIN_PASSWORD: ${KEYCLOAK_ADMIN_PASSWORD:?copy .env.example to .env and set it}

    Step-5: Use one issuer for browsers and containers

    This is the pitfall that catches almost everyone who runs Keycloak in Docker, so it gets a step of its own.

    Every token contains an iss claim, and every service that checks a token compares it with the issuer it expects. Keycloak builds the issuer from the address it was called on. But in our store, Keycloak has two addresses:

    • The browser reaches it at http://localhost:8081, through the published port. That's where the sign-in page is, so tokens from a browser sign-in say "iss": "http://localhost:8081/realms/store".
    • The containers reach it at http://keycloak:8080, by service name on the store network. localhost inside a container is the container itself, so the APIs can't use the browser's address to fetch keys.

    Without any hostname setting, a token that the Admin site gets from http://keycloak:8080 would say "iss": "http://keycloak:8080/realms/store", while a token from the Storefront says localhost:8081. An API can only expect one of them, and whichever it picks, half of the store breaks with 401 and a confusing "issuer is invalid" message.

    Keycloak's hostname options (version 2, the default since Keycloak 25) solve this:

    Setting Effect
    KC_HOSTNAME=http://localhost:8081 The front-channel address, used by browsers: the sign-in page, redirects, and the issuer in every token, whatever address the request came in on
    KC_HOSTNAME_BACKCHANNEL_DYNAMIC=true Back-channel addresses (token endpoint, keys, user info, pushed authorization requests) follow the address of the request instead. Requires KC_HOSTNAME to be a full URL

    You can see both in Keycloak's discovery document, /.well-known/openid-configuration, which lists the realm's issuer and endpoints. From your machine:

    curl -s http://localhost:8081/realms/store/.well-known/openid-configuration \
  | jq '{issuer, authorization_endpoint, token_endpoint, jwks_uri}'

# output

  "authorization_endpoint": "http://localhost:8081/realms/store/protocol/openid-connect/auth",

  "jwks_uri": "http://localhost:8081/realms/store/protocol/openid-connect/certs"

    and from inside the network, with the Order API container's BusyBox wget (start the store as in Step-10 first, or come back here afterwards):

    docker compose exec order-api wget -qO- http://keycloak:8080/realms/store/.well-known/openid-configuration \

    The issuer and the sign-in page (authorization_endpoint) are the same from both sides; the token endpoint and the keys (jwks_uri) point to keycloak:8080 for a caller inside the network. So every service gets its keys from http://keycloak:8080 and expects the issuer http://localhost:8081/realms/store, and the two never conflict. (jq only formats the JSON; without it, look for "issuer" in the raw output.)

    In production

Setting the hostname explicitly also means a request with a forged Host header can't make Keycloak issue tokens under a different issuer.

    Step-6: Protect the Product API (.NET)

    Keycloak puts the realm roles in a nested claim, "realm_access": { "roles": [...] }, while ASP.NET Core's role checks look for flat claims of type ClaimTypes.Role. A small helper copies them over. Create Auth/KeycloakRoles.cs:

    product-api/Auth/KeycloakRoles.cs
    using System.Security.Claims;
using System.Text.Json;

namespace productapi.Auth;

// Keycloak puts a user's realm roles in a nested claim:
//   "realm_access": { "roles": [ "customer", "default-roles-store" ] }
// ASP.NET Core checks roles (User.IsInRole, [Authorize(Roles = ...)]) against
// flat claims of type ClaimTypes.Role, so copy each role into one (Chapter-16).
public static class KeycloakRoles
{
    public static void AddRoleClaims(ClaimsPrincipal? principal)
    {
        if (principal?.Identity is not ClaimsIdentity identity)
        {
            return;
        }

        var realmAccess = identity.FindFirst("realm_access")?.Value;
        if (string.IsNullOrEmpty(realmAccess))
        {
            return;
        }

        using var json = JsonDocument.Parse(realmAccess);
        if (!json.RootElement.TryGetProperty("roles", out var roles) || roles.ValueKind != JsonValueKind.Array)
        {
            return;
        }

        foreach (var role in roles.EnumerateArray())
        {
            if (role.GetString() is { Length: > 0 } name && !identity.HasClaim(ClaimTypes.Role, name))
            {
                identity.AddClaim(new Claim(ClaimTypes.Role, name));
            }
        }
    }
}

    Let's go through it:

    • Authority is the realm's base address inside the network. On the first request with a token, the handler downloads the discovery document from {Authority}/.well-known/openid-configuration and the signing keys from its jwks_uri, and caches them. That's the back-channel from Step-5.
    • ValidIssuer is the browser-facing issuer, http://localhost:8081/realms/store; ValidAudience is product-api. Together with ValidateLifetime and ValidateIssuerSigningKey, the API checks exactly the four things Microsoft's guidance lists for an API: signature, issuer, audience and expiry.
    • ClockSkew. By default the handler accepts a token up to 5 minutes after it expired, to allow for clocks that differ between servers. For tokens that live 5 minutes, that doubles their life; 30 seconds is plenty when Keycloak and the API run on the same machine.
    • MapInboundClaims = false keeps the claim names as they are in the token (sub, preferred_username), instead of renaming some of them to long XML-style URIs. Then NameClaimType makes User.Identity.Name the user name, and RoleClaimType says which claims are roles.
    • RequireHttpsMetadata is true by default and must stay true in production; compose sets it to false because Keycloak speaks plain HTTP on your machine.
    • The CatalogAdmin policy requires a valid token and the admin role. Without the Auth__Authority setting, the API runs as in the single-service labs of Chapter-4 and Chapter-12 and logs a warning at start-up (more on that trade-off below).

    Create src/auth.js, an Express middleware that checks the token and sets req.user:

    order-api/src/auth.js
    // Checks the caller's access token (Chapter-16). Keycloak signs every token with
// its private key; we fetch the matching public keys (the JSON Web Key Set) from
// Keycloak and verify the signature, issuer, audience and expiry ourselves.
import { createRemoteJWKSet, errors, jwtVerify } from 'jose';
import { sendProblem } from './problem.js';

// All three come from the environment; compose sets them:
//   AUTH_ISSUER    http://localhost:8081/realms/store  (the issuer as the browser sees Keycloak)
//   AUTH_JWKS_URL  http://keycloak:8080/realms/store/protocol/openid-connect/certs  (inside the network)
//   AUTH_AUDIENCE  order-api
const issuer = process.env.AUTH_ISSUER;
const jwksUrl = process.env.AUTH_JWKS_URL;
const audience = process.env.AUTH_AUDIENCE ?? 'order-api';

// Without AUTH_ISSUER (the single-service labs of Chapter-5 and Chapter-12)
// nobody signs in and every order belongs to "anonymous", as before.
export const authEnabled = Boolean(issuer && jwksUrl);

// Fetches the keys once, caches them, and fetches again when a token is signed
// with a key it doesn't know yet (Keycloak rotated its keys). Give up after 2 s.
const jwks = authEnabled ? createRemoteJWKSet(new URL(jwksUrl), { timeoutDuration: 2000 }) : undefined;

export function authDescription() {
  return authEnabled
    ? `JWT access tokens from ${issuer}, audience ${audience}`
    : 'OFF, every order belongs to "anonymous" (set AUTH_ISSUER and AUTH_JWKS_URL to require tokens)';
}

// Express middleware: answers 401 unless the request has a valid access token,
// then sets req.user = { sub, email, roles } for the routes.
export async function requireUser(req, res, next) {
  if (!authEnabled) {
    req.user = { sub: 'anonymous', email: undefined, roles: [] };
    return next();
  }

  const [scheme, token] = (req.get('Authorization') ?? '').split(' ');
  if (scheme?.toLowerCase() !== 'bearer' || !token) {
    res.set('WWW-Authenticate', 'Bearer realm="store"');
    return sendProblem(res, 401, 'Sign in first: send an access token in the Authorization header.');
  }

  let payload;
  try {
    ({ payload } = await jwtVerify(token, jwks, {
      issuer,
      audience,
      algorithms: ['RS256'],
      // An order needs to know who placed it
      requiredClaims: ['sub'],
      // Allow 30 seconds of clock difference between Keycloak and this service
      clockTolerance: 30,
    }));
  } catch (err) {
    if (err instanceof errors.JOSEError && !(err instanceof errors.JWKSTimeout)) {
      // Bad signature, wrong issuer or audience, expired, malformed: the caller's problem
      console.warn(`token rejected: ${err.code} ${err.message} requestId=${req.id}`);
      res.set('WWW-Authenticate', 'Bearer realm="store", error="invalid_token"');
      return sendProblem(res, 401, 'The access token is not valid. Sign in again.');
    }
    // Keycloak's keys could not be fetched: our problem, not the caller's
    console.warn(`token check failed: ${err.cause?.code ?? err.message} requestId=${req.id}`);
    return sendProblem(res, 503, 'Sign-in can not be checked right now. Try again in a moment.');
  }

  req.user = {
    sub: payload.sub,
    email: payload.email,
    roles: payload.realm_access?.roles ?? [],
  };
  next();
}
    • createRemoteJWKSet downloads Keycloak's public keys from jwks_uri and keeps them. When a token arrives signed with a key id (kid) it doesn't know, for example after Keycloak rotated its keys, it downloads the set again, but not more often than a cool-down allows (30 seconds by default), so a flood of tokens with made-up key ids can't make it hammer Keycloak.
    • jwtVerify checks the signature with the matching key, then the claims: issuer and audience must match (and must be present), exp must not be in the past, allowing clockTolerance seconds of clock difference. algorithms: ['RS256'] accepts only the algorithm Keycloak uses, so a token can't talk the API into a weaker one (unsigned alg: none tokens are always refused).
    • Two kinds of failure. A token that fails a check is the caller's problem: 401 with WWW-Authenticate, and a log line with the reason, which never goes back to the caller. When Keycloak's keys can't be fetched at all, it's our problem: 503, as for a Product API that is down in Chapter-14.
    • req.user keeps only what the routes need: the subject, the email (for the order confirmation in Chapter-17) and the realm roles.

            // The cookie outlives the access token inside it (5 minutes in the demo realm).
            // Once the token has (almost) expired, end the cookie session: the next page
            // sends the user to Keycloak, which signs them in again without a password
            // while their Keycloak session lasts, and returns a fresh token.
            options.Events.OnValidatePrincipal = async context =>
            {
                var expiresAt = context.Properties.GetTokenValue("expires_at");
                if (DateTimeOffset.TryParse(expiresAt, CultureInfo.InvariantCulture, out var expires)
                    && expires <= DateTimeOffset.UtcNow.AddSeconds(30))
                {
                    context.RejectPrincipal();
                    await context.HttpContext.SignOutAsync(CookieAuthenticationDefaults.AuthenticationScheme);
                }
            };
        })
        .AddOpenIdConnect(options =>
        {
            // The issuer as the browser sees Keycloak: http://localhost:8081/realms/store.
            // Sign-in redirects go here.
            options.Authority = oidc["Authority"];
            // The same metadata, fetched from inside the store network:
            // http://keycloak:8080/realms/store/.well-known/openid-configuration
            options.MetadataAddress = oidc["MetadataAddress"];
            // Plain HTTP is fine on your machine only; production uses HTTPS
            options.RequireHttpsMetadata = oidc.GetValue("RequireHttpsMetadata", true);
            options.ClientId = oidc["ClientId"];
            // From the environment (.env), never from a file in Git
            options.ClientSecret = oidc["ClientSecret"];
            // Authorization code flow with PKCE (UsePkce is true by default)
            options.ResponseType = OpenIdConnectResponseType.Code;
            options.UsePkce = true;
            options.Scope.Add("email");
            // Keep the tokens in the cookie, so the site can call the Product API as the user
            options.SaveTokens = true;
            // Keep the claim names from the token (sub, preferred_username, ...)
            options.MapInboundClaims = false;
            options.TokenValidationParameters.NameClaimType = "preferred_username";
            options.TokenValidationParameters.RoleClaimType = ClaimTypes.Role;
            options.Events.OnTokenValidated = context =>
            {
                // The realm's "admin" client puts realm_access.roles into the ID token;
                // copy the roles into role claims
                KeycloakRoles.AddRoleClaims(context.Principal);
                return Task.CompletedTask;
            };
        });

    builder.Services.AddAuthorizationBuilder()
        // Every page needs an admin, unless it says [AllowAnonymous]
        .SetFallbackPolicy(new AuthorizationPolicyBuilder()
            .RequireAuthenticatedUser()
            .RequireRole("admin")
            .Build());

    // Put the signed-in user's access token on every call to the Product API
    builder.Services.AddHttpContextAccessor();
    builder.Services.AddTransient<AccessTokenHandler>();
    productApi.AddHttpMessageHandler<AccessTokenHandler>();
}

Here is what the main options do:

    • Two schemes. The cookie scheme keeps the session; the OpenID Connect scheme handles the sign-in. When a page needs a user and there is no cookie, the site challenges with OpenID Connect: it redirects the browser to Keycloak.
    • Authority and MetadataAddress: the issuer problem again. The handler reads the discovery document from MetadataAddress, inside the network, so the back-channel calls (pushed authorization request, code for tokens) go to keycloak:8080, while the redirect for the browser goes to the authorization_endpoint in that document, localhost:8081. The ID token's issuer is checked against the document's issuer, which Step-5 made the same everywhere.
    • ResponseType = Code and UsePkce. The authorization code flow with PKCE, which Microsoft recommends for web apps, with a client secret on top because the site can keep one. UsePkce is true by default; setting it makes the intent visible. Since .NET 9 the handler also uses pushed authorization requests (PAR, RFC 9126) when the server supports them, as Keycloak does: the site first posts the sign-in parameters to Keycloak over the back-channel, and the browser's redirect carries only a reference, request_uri.
    • SaveTokens = true stores the access, ID and refresh tokens in the encrypted session cookie, so the site can send the access token to the Product API later.
    • The fallback policy makes every page require a signed-in user with the admin role, unless it opts out with [AllowAnonymous]. A rule that applies by default is safer than remembering an [Authorize] attribute on every new controller.
    • OnValidatePrincipal. The tokens in the cookie don't refresh themselves. This handler ends the cookie session shortly before the access token expires; the next page then goes through Keycloak again, which signs the user in silently while their Keycloak session lasts, and returns fresh tokens. (A form submitted at exactly that moment is lost; refreshing with the refresh token is the next step up.)

    The token handler is a few lines. Create Auth/AccessTokenHandler.cs:

    admin/Auth/AccessTokenHandler.cs
    using System.Net.Http.Headers;
using Microsoft.AspNetCore.Authentication;

namespace admin.Auth;

// Adds the signed-in user's access token to every call the ProductApiClient makes
// (Chapter-16), so the Product API sees who is asking and checks their role itself.
// The token was saved in the session cookie at sign-in (SaveTokens = true).
public class AccessTokenHandler(IHttpContextAccessor httpContextAccessor) : DelegatingHandler
{
    protected override async Task<HttpResponseMessage> SendAsync(
        HttpRequestMessage request, CancellationToken cancellationToken)
    {
        var httpContext = httpContextAccessor.HttpContext;
        if (httpContext is not null)
        {
            var accessToken = await httpContext.GetTokenAsync("access_token");
            if (!string.IsNullOrEmpty(accessToken))
            {
                request.Headers.Authorization = new AuthenticationHeaderValue("Bearer", accessToken);
            }
        }
        return await base.SendAsync(request, cancellationToken);
    }
}

// Starts keycloak-js once. 'check-sso' signs the customer in silently when they
// already have a session at Keycloak, and otherwise leaves them signed out:
// browsing products needs no sign-in. Resolves to true when signed in.
export function startAuth() {
  started ??= keycloak
    .init({
      onLoad: 'check-sso',
      // A tiny page in public/ that a hidden iframe loads to check the session
      silentCheckSsoRedirectUri: `${window.location.origin}/silent-check-sso.html`,
      pkceMethod: 'S256',
    })
    .catch((err) => {
      // Keycloak is not reachable: the shop still works, signed out
      console.warn('sign-in is not available:', err)
      return false
    })
  return started
}

// The signed-in customer's name for the page, from the ID token: the access token
// is meant for the APIs, so the browser doesn't read it.
export function currentUser() {
  if (!keycloak.authenticated) return null
  const { name, preferred_username: username } = keycloak.idTokenParsed ?? {}
  return { name: name ?? username, username }
}

export function signIn() {
  return keycloak.login({ redirectUri: `${window.location.origin}/` })
}

export function signOut() {
  return keycloak.logout({ redirectUri: `${window.location.origin}/` })
}

// Returns an access token that is valid for at least 30 more seconds: if the
// current one expires sooner, keycloak-js first gets a new one with the refresh token.
export async function accessToken() {
  if (!keycloak.authenticated) return null
  try {
    await keycloak.updateToken(30)
    return keycloak.token
  } catch {
    // The Keycloak session has ended: treat the customer as signed out
    keycloak.clearToken()
    return null
  }
}
    • onLoad: 'check-sso' asks Keycloak, without showing anything, whether the browser already has a Keycloak session. If yes, the customer is signed in when the page loads; if not, they stay signed out and can browse. ('login-required' would force everyone to the sign-in page first, which is wrong for a shop.)
    • silentCheckSsoRedirectUri lets keycloak-js do that check in a hidden iframe instead of redirecting the whole page. The iframe loads a tiny page from the Storefront, public/silent-check-sso.html, that passes the answer to the app. Its address must be one of the client's redirect URIs, which is why the realm lists it.
    • pkceMethod: 'S256' is keycloak-js's default; it is set here so that nobody has to look it up.
    • A keycloak-js instance can only be initialized once. React runs effects twice in development (StrictMode), and a second init throws "A 'Keycloak' instance can only be initialized once.", so startAuth keeps the first promise and returns it again.
    • updateToken(30) refreshes the access token when it would expire within 30 seconds. Calling it before every API request is the simplest way to never send an expired token.
    • The user's name comes from the ID token (idTokenParsed). The access token is meant for the APIs; a client shouldn't depend on what's inside it.

    Where do the tokens live? keycloak-js keeps them in JavaScript memory, not in localStorage, so they disappear when the tab closes, and a page reload gets new ones through the silent check. Still, any script running on the page could read them. That's why the current advice for browser apps (RFC 10017, OAuth 2.0 for Browser-Based Applications) strongly recommends a Backend for Frontend (BFF) for business apps and apps that handle personal data: a small server-side part of the app does the OpenID Connect sign-in as a confidential client, keeps the tokens on the server and gives the browser only an HTTP-only cookie, exactly like our Admin site does. Microsoft's ASP.NET Core guidance says the same. We use keycloak-js in the Storefront because it shows the browser side of the flow clearly and needs no extra service; for a real shop, put a BFF in front of it.

    Going to production

    The demo realm is built for learning on one machine. Before anything like it goes live:

    • Never ship the demo realm. No smoke-test client, no password grant, no demo users, no replaceme secrets. Real users sign up or come from your company directory; real secrets come from a secret store such as Azure Key Vault.
    • HTTPS everywhere. Tokens and session cookies are credentials: anyone who reads them can use them. Run Keycloak with start (not start-dev), a real hostname and a TLS certificate, keep RequireHttpsMetadata on, and serve the store over HTTPS. OpenID Connect requires the issuer to be an https URL.
    • Short-lived access tokens. Keep access tokens to minutes and use refresh tokens (rotated, as in our realm) to get new ones. A stolen access token is then useful only briefly.
    • Rotate secrets and keys. Change client secrets regularly (Keycloak's client secret rotation, still experimental in Keycloak 26.4, can keep the old secret valid for a while during the switch), and let Keycloak rotate its signing keys; createRemoteJWKSet and the JWT bearer handler pick up new keys automatically.
    • A BFF for the Storefront. As Step-9 explained, current advice is to keep tokens out of the browser for apps that handle personal data.
    • Fail closed. Remove the "no settings, no sign-in" fallback from the services, so a missing setting stops the service instead of opening it.
    • Consider a managed identity provider. Running Keycloak yourself means patching, scaling and backing it up. Managed services such as Microsoft Entra ID (for staff) and Microsoft Entra External ID (for customers; Azure AD B2C is no longer sold to new customers since May 2025) speak the same OpenID Connect and OAuth 2.0, so the APIs' token checks change only in their settings: authority, issuer and audience.

    Troubleshooting

    Problem What to do
    401 with The issuer '...' is invalid (Product API) or unexpected "iss" claim value (Order API log) The token's issuer differs from Auth__ValidIssuer / AUTH_ISSUER. Check that KC_HOSTNAME is http://localhost:8081 and that you get tokens from localhost:8081, not from keycloak:8080
    401 with The audience ... is invalid or unexpected "aud" claim value The token isn't meant for this API: an ID token, or a token from a client without the audience mappers
    401 right after a token was issued Look at the reason in the API's log or the WWW-Authenticate header. An expired test token (30 seconds) is the most common one
    403 for bob bob lacks the admin role in the token. If you changed the realm file, the import is skipped while the realm exists: docker compose down -v, then start again
    502 Bad Gateway on /admin/signin-oidc and upstream sent too big header in the gateway log The gateway's buffers are too small for the sign-in cookie: add proxy_buffer_size and proxy_buffers to the /admin location (Step-8)
    Keycloak: Invalid parameter: redirect_uri The address the client sent isn't one of the client's exact redirect URIs. Compare it with the realm file
    Keycloak isn't healthy, or the import fails docker compose logs keycloak. The realm file must be named store-realm.json; Referenced client scope ... doesn't exist means a clientScopes list replaced the built-in scopes (Step-3)
    The Storefront shows Sign in, but signing in does nothing Open the browser's developer tools: keycloak-js logs why. Keycloak must be reachable at http://localhost:8081, and PKCE needs a secure context, which http://localhost is, but http://<your-ip> is not
    Orders return 503 "Sign-in can not be checked right now" The Order API can't fetch Keycloak's keys. Is the keycloak service healthy?
    test-token.sh or a sign-in fails with curl: (52) Empty reply from server Keycloak is still starting: the published port takes the connection, but nothing answers yet. Wait until docker compose ps keycloak shows (healthy) and try again. Right after a start, the first token and the first order also take a second or two longer than later ones
    The Admin site sends you to Keycloak every few minutes Expected: the session ends with the 5-minute access token (Step-8). While your Keycloak session lasts, Keycloak sends you straight back without asking for the password

    Conclusion

    In this chapter, we secured the store with Keycloak. The store realm, imported from a small JSON file, has two roles, two demo users and three clients: the Storefront as a public client and the Admin site as a confidential client, both using the authorization code flow with PKCE and exact redirect URIs, and a test-only client whose password grant exists only for scripts. Keycloak's hostname settings give tokens one issuer, http://localhost:8081/realms/store, whether the browser or a container asks, which removes the most common source of 401s in a Docker setup. The Product API checks tokens with ASP.NET Core's JWT bearer handler and requires the admin role for changes; the Order API checks them with jose, takes the customer from the token's sub and shows customers only their own orders. The Admin site signs staff in with OpenID Connect and calls the Product API with the user's token; the Storefront signs customers in with keycloak-js. The gateway simply passes the Authorization header on, because every service checks for itself.

    The store is now a small but complete system: separate services with their own data, calling each other, behind one entry point, with real sign-in. So far, though, every interaction is a synchronous request that waits for an answer. In the next chapter, events and messaging let the Order API announce OrderPlaced to other services without waiting for them, and the customer's email from the token goes into that event.
