    Chapter-12: Data per Service

    Sample code

    The complete, tested code for this chapter is in samples/microservices/product-api and samples/microservices/order-api, with the databases in sqlserver and postgresql. Use it to compare against your own work.

    Introduction

    Welcome to Part III, where the separate pieces of our online store start to work as a system. So far, the Product API (Chapter-4) and the Order API (Chapter-5) keep their data in memory, and the two databases from Chapter-8 and Chapter-9 sit empty next to them. In this lab, I will guide you through connecting each API to its own database.

    That one word, own, is the most important rule of data in microservices. We will look at why it matters and what it costs, wire the Product API to SQL Server with Entity Framework Core and the Order API to PostgreSQL with the pg driver, pass passwords to the containers without putting them in an image or in Git, and prove that the data survives restarts.

    Technical Scenario

    As a Backend (BE) developer, you have been asked to make the store's data permanent: products and orders must survive a restart of the APIs. The team agreed on one rule from the design in Chapter-1: each service owns its data.

    • The Product API is the only service that reads or writes the Product DB (SQL Server).
    • The Order API is the only service that reads or writes the Order DB (PostgreSQL).
    • Any other service that needs products or orders asks the owning API, over HTTP or through an event. Never through the other service's database.

    Why go to that trouble? Because a shared database quietly couples services together:

    • Autonomy. The team that owns a service can change its tables, indexes or even its database engine without asking anyone, because nobody else depends on them. The API is the contract; the tables are an internal detail.
    • Independent deployment. A schema change ships with the service that needs it. With a shared database, one team's migration can break another team's queries, so releases have to be coordinated.
    • Failure isolation. If the Order DB is down or overloaded, customers can still browse products. With one database for everything, one slow query or one outage takes the whole store down.

    The rule has a real cost, and it's better to know it up front:

    • No joins across services. You can't write one SQL query that joins orders with products. The Order API keeps a copy of the product name and price in every order item (the snapshot from Chapter-5), and asks the Product API for anything else.
    • No transactions across services. Placing an order can't update the Order DB and the Product DB in one database transaction. Later chapters handle this with API calls and events, and accept that data in different services is sometimes briefly out of step (eventual consistency).
    • More to run. Two database engines, two sets of backups, two connection strings. Containers make the development side cheap; managed databases make the production side manageable.

    Objective

    In this exercise, our objective is to accomplish and learn the following tasks:

    • Step-1: Keep the schema in numbered scripts.
    • Step-2: Connect the Product API to SQL Server.
    • Step-3: Connect the Order API to PostgreSQL.
    • Step-4: Keep passwords out of images and Git.
    • Step-5: Run the Product API with its database.
    • Step-6: Run the Order API with its database.
    • Step-7: Restart without losing data.
    • Step-8: Stop a database and watch the readiness check.

    Prerequisites

    Before starting this lab, ensure you have the following prerequisites in place:

    • The Product API from Chapter-4 and the Order API from Chapter-5.
    • The database images from Chapter-8 (SQL Server) and Chapter-9 (PostgreSQL).
    • Docker Desktop with at least 4 GB of memory for containers: SQL Server alone needs about 2 GB.
    • curl (see the note on Windows in Chapter-4).

    Stop any container from the earlier chapters that still uses ports 8080, 3000, 1433 or 5432 (docker ps lists them).

    Step-1: Keep the schema in numbered scripts

    Both databases are created by numbered SQL scripts that you wrote in Chapter-8 and Chapter-9:

    Database Scripts Who runs them
    Product DB (SQL Server) sqlserver/scripts/001-schema.sql, 002-seed.sql entrypoint.sh, once per script, recorded in dbo.schema_history
    Order DB (PostgreSQL) postgresql/scripts/001-schema.sql, 002-seed.sql The postgres image, from /docker-entrypoint-initdb.d, on the first start with an empty volume

    Why scripts, and why numbers?

    • The schema is code. It lives in Git next to the service that owns it, gets reviewed like code, and every developer's database is built from the same files.
    • Each change is a new script. When the Product API needs a new column, you add 003-add-product-image.sql; you never edit 001 after it has run somewhere. The numbers fix the order, and a record of which scripts ran (the schema_history table) lets the next start apply only the new ones. This idea is called a database migration, and it's how the same schema change reaches a laptop, a test database and production.
    • First start is idempotent. Starting a container twice must not create the tables twice. The SQL Server entrypoint skips scripts it has recorded; the PostgreSQL image runs its scripts only when the data folder is empty.

    Where to go next with migrations

    Our scripts are deliberately simple so you can see every step. Real projects use a migration tool that does the bookkeeping for you: EF Core migrations generate the scripts from your C# model and track them in a __EFMigrationsHistory table, and Flyway (or Liquibase) runs numbered SQL files like ours against any database and records them in its own history table. Note that the PostgreSQL image runs /docker-entrypoint-initdb.d only on an empty volume, so a 003 script there would not reach an existing database; a migration tool would.

    Step-2: Connect the Product API to SQL Server

    The Product API from Chapter-4 already talks to its storage through the IProductRepository interface. That pays off now: we add a second implementation that uses SQL Server, and the controller doesn't change at all.

    Add the EF Core provider for SQL Server to the project:

    cd product-api
dotnet add package Microsoft.EntityFrameworkCore.SqlServer --version 10.0.15

    The DbContext maps the products table from 001-schema.sql to our Product record. EF Core doesn't create the table here; the scripts own the schema.

    Data/ProductDbContext.cs
    using Microsoft.EntityFrameworkCore;
using productapi.Models;

namespace productapi.Data;

// EF Core's view of the Product API's own database (ProductDb on SQL Server).
// The numbered scripts in samples/microservices/sqlserver/scripts create the
// table; this class only maps it.
public class ProductDbContext(DbContextOptions<ProductDbContext> options) : DbContext(options)
{
    public DbSet<Product> Products => Set<Product>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        var product = modelBuilder.Entity<Product>();
        product.ToTable("products");
        product.HasKey(p => p.Id);
        product.Property(p => p.Id).HasColumnName("id");
        product.Property(p => p.Sku).HasColumnName("sku").HasMaxLength(32);
        product.Property(p => p.Name).HasColumnName("name").HasMaxLength(100);
        product.Property(p => p.Description).HasColumnName("description").HasMaxLength(500);
        product.Property(p => p.Price).HasColumnName("price").HasPrecision(10, 2);
    }
}

    The repository implements the same interface as the in-memory version:

    Data/SqlProductRepository.cs
    using Microsoft.EntityFrameworkCore;
using productapi.Models;

namespace productapi.Data;

// Keeps the products in the Product API's SQL Server database, through EF Core.
// Reads use AsNoTracking: the API only returns the rows, so EF Core doesn't
// need to watch them for changes.
public class SqlProductRepository(ProductDbContext db) : IProductRepository
{
    public IReadOnlyList<Product> GetAll() =>
        db.Products.AsNoTracking().OrderBy(p => p.Id).ToList();

    public Product? GetById(int id) =>
        db.Products.AsNoTracking().FirstOrDefault(p => p.Id == id);

    // The database compares SKUs without regard to case, like the in-memory version.
    public bool SkuExists(string sku, int? exceptId = null) =>
        db.Products.Any(p => p.Sku == sku && p.Id != exceptId);

    public Product Add(ProductInput input)
    {
        var product = new Product(0, input.Sku, input.Name, input.Description, input.Price);
        db.Products.Add(product);
        db.SaveChanges(); // SQL Server assigns the id, and EF Core copies it into product
        return product;
    }

    // ExecuteUpdate and ExecuteDelete run one SQL statement each and
    // return the number of rows they changed.
    public bool Update(int id, ProductInput input) =>
        db.Products.Where(p => p.Id == id).ExecuteUpdate(set => set
            .SetProperty(p => p.Sku, input.Sku)
            .SetProperty(p => p.Name, input.Name)
            .SetProperty(p => p.Description, input.Description)
            .SetProperty(p => p.Price, input.Price)) > 0;

    public bool Delete(int id) =>
        db.Products.Where(p => p.Id == id).ExecuteDelete() > 0;
}

    The methods are synchronous because the interface from Chapter-4 is. In a busy service you would make the interface asynchronous (ToListAsync, SaveChangesAsync) so that threads aren't blocked while the database works.

    A readiness check that asks the database. /health/ready should answer "can this service do its job?", and the Product API can't without its database. The check opens a connection with a short timeout and runs SELECT 1:

    Data/DatabaseHealthCheck.cs
    using Microsoft.Data.SqlClient;
using Microsoft.Extensions.Diagnostics.HealthChecks;

namespace productapi.Data;

// Readiness check: can we open a connection to the database and run a query?
// It opens its own connection with a short timeout instead of going through
// EF Core, whose retries would make the check wait a long time before it
// reports that the database is down.
public class DatabaseHealthCheck(string connectionString) : IHealthCheck
{
    public async Task<HealthCheckResult> CheckHealthAsync(
        HealthCheckContext context, CancellationToken cancellationToken = default)
    {
        var builder = new SqlConnectionStringBuilder(connectionString) { ConnectTimeout = 3 };
        try
        {
            await using var connection = new SqlConnection(builder.ConnectionString);
            await connection.OpenAsync(cancellationToken);
            await using var command = new SqlCommand("SELECT 1", connection) { CommandTimeout = 3 };
            await command.ExecuteScalarAsync(cancellationToken);
            return HealthCheckResult.Healthy();
        }
        catch (Exception ex) when (ex is SqlException or InvalidOperationException)
        {
            return HealthCheckResult.Unhealthy("Cannot reach the product database.", ex);
        }
    }
}

    Program.cs chooses the storage from configuration:

    Program.cs (excerpt)
    var healthChecks = builder.Services.AddHealthChecks();

// Where the products live. With a connection string (environment variable
// ConnectionStrings__ProductDb), they live in the API's own SQL Server database;
// without one, the API keeps the in-memory list from Chapter-4.
var connectionString = builder.Configuration.GetConnectionString("ProductDb");
if (!string.IsNullOrWhiteSpace(connectionString))
{
    builder.Services.AddDbContext<ProductDbContext>(options =>
        // Retry short network or start-up failures instead of failing the request
        options.UseSqlServer(connectionString, sql => sql.EnableRetryOnFailure()));
    builder.Services.AddScoped<IProductRepository, SqlProductRepository>();
    // Readiness now includes a real check: can we connect to the database?
    healthChecks.AddCheck("database", new DatabaseHealthCheck(connectionString));
}
else
{
    // One product list shared by every request
    builder.Services.AddSingleton<IProductRepository, InMemoryProductRepository>();
}
    • The connection string comes from configuration, and ASP.NET Core reads the environment variable ConnectionStrings__ProductDb as ConnectionStrings:ProductDb (the double underscore stands for the : separator). Nothing about the database is compiled into the image.
    • EnableRetryOnFailure makes EF Core retry a query when it hits a short, temporary failure, for example a database that is still starting or a dropped connection. It retries a few times with a growing delay, which covers the first queries after a restart.
    • Without a connection string, the API still runs with the in-memory list, so the docker run commands from Chapter-4 keep working.
    • /health/live stays as it was: it only tells whether the process is up, and must not fail just because the database is down, otherwise an orchestrator would restart a healthy process for nothing.

    Step-3: Connect the Order API to PostgreSQL

    The Order API uses pg, the most widely used PostgreSQL driver for Node.js:

    cd order-api
npm install pg@8

    Chapter-5 kept all the storage code in src/store.js. We move the in-memory version to src/memory-store.js (the same code, with async functions), put the PostgreSQL version in src/pg-store.js, and turn store.js into a switch between them:

    src/store.js
    // Where the orders are kept: in the Order API's own PostgreSQL database when
// DATABASE_URL is set (Chapter-12), otherwise in memory (Chapter-5).
// Both stores offer the same functions, so the routes don't care which one runs.
const store = process.env.DATABASE_URL
  ? await import('./pg-store.js')
  : await import('./memory-store.js');

export const { connect, isReady, saveOrder, getOrder, listOrders, close } = store;

    A connection pool and a retry on start-up. Opening a database connection is slow, so a pool keeps a few connections open and lends one out per query. When the API starts, the database may not be ready yet, so connect() tries again with a growing delay (exponential backoff):

    src/pg-store.js (excerpt)
    import pg from 'pg';

// A pool keeps a few connections open and lends them out per query,
// instead of opening a new connection for every request.
const pool = new pg.Pool({
  connectionString: process.env.DATABASE_URL,
  max: 10,
  connectionTimeoutMillis: 3000,
});

// An idle connection can break (for example when the database restarts).
// Without this handler that error would crash the process.
pool.on('error', (err) => console.error('idle database connection failed:', err.message));

// The database may still be starting when the API starts, so try a few times,
// waiting longer after each failure: 1, 2, 4, 8 and 16 seconds.
export async function connect({ attempts = 6 } = {}) {
  for (let attempt = 1; ; attempt++) {
    try {
      await pool.query('SELECT 1');
      console.log('order store: PostgreSQL');
      return;
    } catch (err) {
      if (attempt === attempts) throw err;
      const delay = 1000 * 2 ** (attempt - 1);
      console.log(`database not reachable (${err.message}); retry ${attempt} in ${delay / 1000}s`);
      await new Promise((resolve) => setTimeout(resolve, delay));
    }
  }
}

export async function isReady() {
  try {
    await pool.query('SELECT 1');
    return true;
  } catch {
    return false;
  }
}

    server.js calls await connect() before it starts listening, and closes the pool when it shuts down. If the database never answers, connect() gives up and the process exits with an error, which is easier to notice than an API that runs but can't save anything.

    One transaction per order, and parameters for every value. An order is one row in orders and one row per item in order_items. Either all of them are saved, or none:

    src/pg-store.js (excerpt)
    // Saves the order and its items in one transaction: either all rows are
// written or none are. Every value goes in as a parameter ($1, $2, ...),
// never pasted into the SQL text, so input can't change the query.
export async function saveOrder(order) {
  const client = await pool.connect();
  try {
    await client.query('BEGIN');
    await client.query(
      `INSERT INTO orders (id, customer_id, status, total, created_at)
       VALUES ($1, $2, $3, $4, $5)`,
      [order.id, order.customerId, order.status, order.total, order.createdAt]);
    for (const [index, item] of order.items.entries()) {
      await client.query(
        `INSERT INTO order_items (order_id, line_no, product_id, name, unit_price, quantity)
         VALUES ($1, $2, $3, $4, $5, $6)`,
        [order.id, index + 1, item.productId, item.name, item.unitPrice, item.quantity]);
    }
    await client.query('COMMIT');
    return order;
  } catch (err) {
    await client.query('ROLLBACK');
    throw err;
  } finally {
    client.release();
  }
}
    • A transaction needs all its statements on the same connection, so we borrow one client from the pool (pool.connect()) and give it back in finally, whatever happens.
    • $1, $2, ... are placeholders. The driver sends the values separately from the SQL text, so a customer id like '; DROP TABLE orders; -- is stored as text, not run as SQL. Never build SQL by joining strings with user input.

    Reading orders back is a join between the two tables, turned into the same JSON as before. Two details from the sample are worth knowing: numeric columns arrive in JavaScript as strings (so no digit is lost), so the code converts them with Number(); and getOrder returns "not found" for an id that isn't a UUID instead of sending it to PostgreSQL, which would reject it with an error.

    Finally, /health/ready asks the store:

    src/app.js (excerpt)
    // Health endpoints: live = the process is up, ready = it can serve requests.
// Ready asks the order store, which runs SELECT 1 when orders are in PostgreSQL.
app.get('/health/live', (req, res) => res.type('text').send('Healthy'));
app.get('/health/ready', async (req, res) => {
  const ready = await isReady();
  res.status(ready ? 200 : 503).type('text').send(ready ? 'Healthy' : 'Unhealthy');
});

    The route handlers in orders.js became async and gained an await in front of saveOrder, getOrder and listOrders.

    Step-4: Keep passwords out of images and Git

    Each API now needs a database password, and so does each database container. Where should those passwords live?

    • Not in an image. Anyone who can pull an image can read its ENV values with docker inspect and its build steps with docker history. That's why the database images from Chapter-8 and Chapter-9 contain no password.
    • Not in Git. A password in a committed file stays in the repository history even after you delete it.
    • In the environment of the running container. Compose reads the values from a file called .env next to the compose file and passes them to the containers when they start.

    Each lab folder has an .env.example file that is committed. It lists the variables, with placeholders only:

    product-api/.env.example
    # Copy this file to .env and change the value. .env is git-ignored; never commit it.
# SQL Server rejects weak passwords: use at least 8 characters from three of
# uppercase, lowercase, digits and symbols, or the database will not start.
# Avoid ; and quotes: the value is also used inside a connection string.
MSSQL_SA_PASSWORD=Replaceme-1a
    order-api/.env.example
    # Copy this file to .env and change the value. .env is git-ignored; never commit it.
# The value is also used inside a URL (DATABASE_URL), so stick to letters,
# digits and - _ . ~ or URL-encode other characters.
POSTGRES_PASSWORD=replaceme

    Why is the SQL Server value different? SQL Server enforces a password policy for the sa login: at least 8 characters from three of the four sets uppercase, lowercase, digits and symbols. With replaceme the database refuses to start. PostgreSQL has no such rule, so the book's usual replaceme placeholder works there.

    Copy each example to .env and put your own values in it:

    cd product-api
cp .env.example .env      # Windows PowerShell: Copy-Item .env.example .env

    Two more files keep .env where it belongs:

    • .gitignore contains samples/**/.env (in your own repository, simply .env), so Git never picks it up. Check it with git check-ignore:

      git check-ignore -v .env

# output
.gitignore:33:samples/**/.env   .env

    • .dockerignore in each API folder lists .env, so it never ends up in an image either, even though the Product API's Dockerfile copies the whole folder (COPY . .) into its build stage.

    Step-5: Run the Product API with its database

    The product-api folder has a small compose file for this lab. It runs the API and its database, and nothing else:

    product-api/docker-compose.yml
    # Lab: the Product API with its own SQL Server database (chapter 12).
# Copy .env.example to .env and set MSSQL_SA_PASSWORD before you start.
# This file is for the lab only; the compose file for the whole store
# arrives in chapter 13.
services:
  product-api:
    build: .
    image: sample/product-api
    ports:
      - "8080:8080"
    environment:
      ConnectionStrings__ProductDb: "Server=product-db;Database=ProductDb;User Id=sa;Password=${MSSQL_SA_PASSWORD:-Replaceme-1a};TrustServerCertificate=True"
    depends_on:
      product-db:
        condition: service_healthy

  product-db:
    build: ../sqlserver
    image: sample/sqlserver
    environment:
      ACCEPT_EULA: "Y"
      MSSQL_SA_PASSWORD: ${MSSQL_SA_PASSWORD:-Replaceme-1a}
    volumes:
      - product-db-data:/var/opt/mssql
    healthcheck:
      # Healthy once the entrypoint has run the scripts and SQL Server answers a query
      test: ["CMD-SHELL", "test -f /tmp/ready && SQLCMDPASSWORD=\"$$MSSQL_SA_PASSWORD\" /opt/mssql-tools18/bin/sqlcmd -S localhost -U sa -C -b -Q 'SELECT 1' > /dev/null"]
      interval: 5s
      timeout: 5s
      retries: 30
      start_period: 30s

volumes:
  product-db-data:
    • ${MSSQL_SA_PASSWORD:-Replaceme-1a} takes the value from .env, with the placeholder as a fallback. The same variable feeds the database and the API's connection string, so they always match.
    • Server=product-db: on the network compose creates, each service is reachable under its service name. The database port 1433 is not published to your machine; only the API can reach it.
    • TrustServerCertificate=True accepts the self-signed certificate of the development container. Against a real server, use a trusted certificate instead.
    • depends_on with condition: service_healthy starts the API only after the database's healthcheck passes. The check waits for the /tmp/ready file the entrypoint writes after the scripts have run, then runs SELECT 1. $$ stops compose from filling in the variable, so the shell inside the container reads it.
    • The named volume product-db-data keeps the database files.
    • To keep the lab short, the API connects as sa, the administrator. In production, each service gets its own login with only the rights it needs.

    Step-6: Run the Order API with its database

    The order-api folder has the same kind of compose file:

    order-api/docker-compose.yml
    # Lab: the Order API with its own PostgreSQL database (chapter 12).
# Optional: copy .env.example to .env and set your own POSTGRES_PASSWORD.
# This file is for the lab only; the compose file for the whole store
# arrives in chapter 13.
# Since chapter 14 the Order API gets names and prices from the Product API,
# so the lab also runs the Product API, with its in-memory product list.
services:
  order-api:
    build: .
    image: sample/order-api
    ports:
      - "3000:3000"
    environment:
      DATABASE_URL: postgres://orders:${POSTGRES_PASSWORD:-replaceme}@order-db:5432/orderdb
      PRODUCT_API_URL: http://product-api:8080
    depends_on:
      order-db:
        condition: service_healthy
      product-api:
        condition: service_started

  product-api:
    build: ../product-api
    image: sample/product-api

  order-db:
    build: ../postgresql
    image: sample/postgresql
    environment:
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:-replaceme}
    volumes:
      - order-db-data:/var/lib/postgresql/data
    healthcheck:
      # -h 127.0.0.1: during first-start initialization the server only listens
      # on a local socket, so a TCP check passes only once the scripts have run.
      test: ["CMD", "pg_isready", "-h", "127.0.0.1", "-U", "orders", "-d", "orderdb"]
      interval: 5s
      timeout: 5s
      retries: 10

volumes:
  order-db-data:

    DATABASE_URL packs user, password, host, port and database into one URL, the form most PostgreSQL drivers and hosting services use. Unlike the Chapter-9 lab, this file does not publish port 5432: the Order API reaches the database over the compose network, and nobody else needs to.

    Step-7: Restart without losing data

    Containers are disposable; data is not. Remove both Product containers with docker compose down and start them again:

    docker compose down

# output (trimmed)
 Container product-api-product-api-1 Removed
 Container product-api-product-db-1 Removed
 Network product-api_default Removed

    The containers and the network are gone, but the volume is still there:

    docker volume ls --filter name=product-api

# output
DRIVER    VOLUME NAME
local     product-api_product-db-data

    Start again (run this in the product-api folder):

    docker compose up -d
docker compose logs product-db | grep entrypoint

# output
product-db-1  | entrypoint: waiting for SQL Server and its databases to come online
product-db-1  | entrypoint: 001-schema.sql already applied, skipping
product-db-1  | entrypoint: 002-seed.sql already applied, skipping

curl http://localhost:8080/products/6

# output
{"id":6,"sku":"PEN-001","name":"Ballpoint pen","description":"Blue ink, refillable.","price":2.50}

    The new database container found its files in the volume, the entrypoint skipped the scripts that had already run, and the pen we added is still there. The same works for the Order API: after docker compose down and docker compose up -d in the order-api folder, curl http://localhost:3000/orders/<your-order-id> still returns your order.

    Warning

    docker compose down -v also removes the volumes, and with them all the data. Use it on purpose, when you want to start from a fresh database.

    Step-8: Stop a database and watch the readiness check

    What happens to a service when its database goes away? Stop only the Product DB (run this in the product-api folder):

    docker compose stop product-db
curl -i http://localhost:8080/health/ready

# output (trimmed)
HTTP/1.1 503 Service Unavailable
Unhealthy

curl -i http://localhost:8080/health/live

# output (trimmed)
HTTP/1.1 200 OK

    The API process is fine (live is 200), but it can't do its job (ready is 503). That difference is exactly what a load balancer or an orchestrator needs: stop sending requests to this instance until it is ready again, but don't restart it. Start the database and readiness recovers by itself:

    docker compose start product-db
# about 15 seconds later
curl -i http://localhost:8080/health/ready

# output (trimmed)
HTTP/1.1 200 OK

    The Order API behaves the same way when you stop order-db. And because the two services don't share a database, stopping the Product DB has no effect on the Order API at all: that is failure isolation. The next chapter shows it with the whole store running.

    When you are done, run docker compose down in both folders (add -v to delete the data).

    Production note

    The database containers in this book are for development and testing. In production:

    • Use a managed database. For example Azure SQL Database for the Product API and Azure Database for PostgreSQL flexible server for the Order API. The provider takes care of high availability, patching and storage, things a database container on its own does not give you.
    • Apply the same scripts as migrations. The numbered scripts, or the migrations of a tool such as EF Core migrations or Flyway, run against the managed database as a step of each release, before the new version of the service starts. The service does not create its schema on its own.
    • Back up, and test the restore. Managed databases take automatic backups with point-in-time restore; check how long they are kept and practise a restore before you need one. A Docker volume is not a backup.
    • Keep passwords in a secret store. Use a service such as Azure Key Vault, or better, a managed identity so that the service needs no database password at all. Give each service its own login with only the rights it needs, never the administrator.
    • Keep one database per service. The ownership rule doesn't change in production. Services can share a database server to save money, as long as each has its own database and login and never reads another's.

    What not to do

    • A shared database between services. If the Order API read the products table directly, the Product API team could no longer rename a column without breaking orders. The two services would have to be deployed together, and you would have a distributed monolith: all the cost of microservices, none of the independence. Ask the owning API instead, or keep a copy of the data you need, as the Order API does with product names and prices.
    • One database for everything. Putting every service's tables into one big database looks simpler, but it brings back the shared failure point and the coordinated releases this chapter is about. One overloaded table slows down every service.
    • Passwords in images or in Git. Keep them in the environment of the running container, from a git-ignored .env file during development and from a secret store in production.
    • Editing a script that has already run. Add a new numbered script instead; otherwise databases that ran the old version and databases that ran the new one quietly drift apart.

    Conclusion

    In this chapter, each API got its own database: the Product API reads and writes SQL Server through EF Core, and the Order API uses PostgreSQL through a pg connection pool, with one transaction per order and parameters for every value. The schema lives in numbered scripts that run once, passwords reach the containers at run time from git-ignored .env files, named volumes keep the data across restarts, and /health/ready tells the truth about the database.

    We still run each service with its own small compose file. In the next chapter, we bring all the services and both databases together in one compose file for the whole store.
