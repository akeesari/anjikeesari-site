    Chapter-8: Create Your First Database with SQL Server

    Sample code

    The complete, tested code for this chapter is in samples/microservices/sqlserver. Use it to compare against your own work.

    Introduction

    Running SQL Server in a Docker container is best suited for development, testing, learning, or quick experimentation scenarios where you need a lightweight, isolated environment that can be spun up or torn down easily. It works well offline, you can run it without any cost, and it is perfect for local development workflows. However, it's not ideal for production use. For production environments you can use Azure SQL Database, which is a fully managed platform-as-a-service (PaaS) offering that's optimized for production workloads. It provides built-in high availability, automated backups, scalability, and security, making it ideal for applications that need global reach, minimal maintenance, and enterprise-grade reliability.

    In this lab, I will guide you through the process of creating a Docker image for the SQL Server database of our store, running it in a container, and finally accessing it with sqlcmd, SQL Server Management Studio (SSMS) and Azure Data Studio.

    Technical Scenario

    As a Backend (BE) developer, you have been asked to create the Product DB, the database that belongs to the Product API from Chapter-4. Every developer on the team needs the same database on their own machine: SQL Server 2022 with the ProductDb database, the products table and the five products the store starts with.

    You will package that database as a container image: the official SQL Server image plus the numbered SQL scripts that create and fill ProductDb. Two rules shape the design:

    • The image holds no password. Anyone who can pull an image can read every ENV value and every layer in it, so a password baked into an image is a password shared with everyone who has access to the registry. The sa password is passed only when the container starts.
    • The scripts run once. The first start creates the database; later starts, with the data kept in a Docker volume, must leave it alone.

    In Chapter-12 we connect the Product API to this database.

    Objective

    The objective is to establish a local development environment for the SQL Server database. To accomplish this, you will write the database scripts and a Dockerfile, and run them locally.

    In this exercise, our objective is to accomplish and learn the following tasks:

    • Step-1: Setup Git Repository for SQL Server database.
    • Step-2: Create Folder Structure for SQL Server database.
    • Step-3: Add the database scripts.
    • Step-4: Add the Dockerfile and the entrypoint script.
      • Step-4.1: Docker Build Locally
      • Step-4.2: Docker Run Locally
    • Step-5: Test the SQL Server database connection using sqlcmd
    • Step-6: Test the SQL Server database connection using SSMS
    • Step-7: Test the SQL Server database connection using Azure Data Studio
    • Step-8: Push Docker Container to ACR (optional)

    By the end of this lab, you will have the store's product database running in a Docker container, ready for development and testing.

    Prerequisites

    Before starting this lab, ensure you have the following prerequisites in place:

    • Docker Desktop: - Docker Downloads. SQL Server needs about 2 GB of memory for the container.
    • SQL Server Management Studio (Windows only) - this will allow you to manage the SQL Server databases
    • Azure Data Studio or the SQL Server (mssql) extension for VS Code - this will allow you to connect to SQL Server databases
    • Basic understanding of Docker and SQL Server.
    • For the optional step only: access to an Azure Container Registry (ACR).

    Verify the docker installation by running following commands:

    docker version
# or
docker --version
# or
docker -v

    Step-1: Setup Git Repository for SQL Server database

    Setting up a Git repository for your SQL Server database project allows you to manage your code effectively, work in teams, and track the changes of your database codebase.

    • Create a new project in Azure DevOps for your database-related work.
    • Create a repository within the project to store your database scripts and Dockerfiles.

    For example to clone an existing repository, run the following command:

    git clone https://dev.azure.com/<organization>/<project>/_git/microservices

    Step-2: Create Folder Structure for SQL Server database

    In this step, we'll create a dedicated project or folder for our SQL Server database

    Create a new database project:

    Inside our Git repository, create a new directory or folder specifically for your SQL Server database. This folder will contain all the necessary files for SQL Server database, including database schema scripts, sample data scripts, the Dockerfile and other sql files.

    Here's a suggestion for a folder structure for a larger SQL Server database project:

    your-project-name/
│
├── sql/
│   ├── scripts/
│   │   ├── schema/
│   │   │   ├── tables/
│   │   │   │   ├── table1.sql
│   │   │   │   ├── table2.sql
│   │   │   │   └── ...
│   │   │   ├── views/
│   │   │   │   ├── view1.sql
│   │   │   │   ├── view2.sql
│   │   │   │   └── ...
│   │   │   ├── functions/
│   │   │   │   ├── function1.sql
│   │   │   │   ├── function2.sql
│   │   │   │   └── ...
│   │   │   └── procedures/
│   │   │       ├── procedure1.sql
│   │   │       ├── procedure2.sql
│   │   │       └── ...
│   │   └── data/
│   │       ├── seed_data.sql
│   │       └── ...
│   └── migrations/
│       ├── version1/
│       │   ├── up.sql
│       │   └── down.sql
│       ├── version2/
│       │   ├── up.sql
│       │   └── down.sql
│       └── ...
│
├── Dockerfile
└── README.md

    Explanation:

    • sql/: This folder contains all SQL-related files for your project.
    • scripts/: Contains scripts for creating database objects like tables, views, functions, and stored procedures.
      • schema/: Contains subfolders for different types of database objects.
      • tables/, views/, functions/, procedures/: Each of these folders contains SQL scripts for the respective database objects.
    • data/: Contains data scripts such as seed data.
    • migrations/: Contains SQL migration scripts for managing database schema changes over time. Each migration version should have an up.sql script for applying the migration and a down.sql script for reverting it.
    • Dockerfile: The Dockerfile for building a Docker image for your SQL Server database.
    • README.md: Documentation for your project.

    You can adjust this structure based on the specific needs of your project. Our Product DB is small, so its folder only needs this:

    sqlserver/
├── scripts/
│   ├── 001-schema.sql     # creates ProductDb and its tables
│   └── 002-seed.sql       # adds the five products
├── entrypoint.sh          # starts SQL Server and runs the scripts once
├── Dockerfile
└── .dockerignore

    Step-3: Add the database scripts

    The database is described by numbered SQL scripts. Each script is one change to the database, and the number fixes the order: the schema first, then the data that goes into it. When the database needs another change later, you add 003-...sql instead of editing a script that has already run. This is the idea behind database migrations, which Chapter-12 explains.

    Create scripts/001-schema.sql. It creates the ProductDb database, a schema_history table that records which scripts have run, and the products table the Product API needs:

    scripts/001-schema.sql
    -- 001: the Product API's database and its products table.
-- entrypoint.sh runs each script once and records it in dbo.schema_history.

IF DB_ID('ProductDb') IS NULL
    CREATE DATABASE ProductDb;
GO

USE ProductDb;
GO

-- Which numbered scripts have already run against this database
CREATE TABLE dbo.schema_history (
    script     nvarchar(200) NOT NULL PRIMARY KEY,
    applied_at datetime2     NOT NULL DEFAULT SYSUTCDATETIME()
);
GO

CREATE TABLE dbo.products (
    id          int IDENTITY(1,1) NOT NULL PRIMARY KEY,
    sku         nvarchar(32)      NOT NULL CONSTRAINT UQ_products_sku UNIQUE,
    name        nvarchar(100)     NOT NULL,
    description nvarchar(500)     NOT NULL DEFAULT '',
    price       decimal(10,2)     NOT NULL CONSTRAINT CK_products_price CHECK (price > 0)
);
GO

    The columns match the product JSON of the Product API. The UNIQUE constraint on sku means the database itself refuses two products with the same SKU, and decimal(10,2) stores prices exactly, without the rounding errors of floating-point numbers.

    Create scripts/002-seed.sql with the products the store starts with:

    scripts/002-seed.sql
    -- 002: the five products the store starts with.

USE ProductDb;
GO

INSERT INTO dbo.products (sku, name, description, price) VALUES
    ('MUG-001', 'Coffee mug',   'Ceramic mug, 350 ml.',                9.99),
    ('TEE-001', 'T-shirt',      'Cotton T-shirt with the store logo.', 19.99),
    ('CAP-001', 'Baseball cap', 'Adjustable cotton cap, one size.',    14.50),
    ('BAG-001', 'Tote bag',     'Reusable canvas tote bag.',           12.00),
    ('BTL-001', 'Water bottle', 'Stainless steel bottle, 500 ml.',     24.95);
GO

    GO is not SQL: it tells sqlcmd where one batch ends and the next begins.

    Step-4: Add the Dockerfile and the entrypoint script

    Unlike PostgreSQL, the SQL Server image has no folder where you can drop scripts to run on the first start. So we add a small shell script, entrypoint.sh, that does the job when the container starts:

    1. starts SQL Server in the background,
    2. waits until SQL Server accepts connections and every database is online,
    3. runs each script in /scripts that is not yet recorded in schema_history, and records it,
    4. waits for SQL Server, and passes on the stop signal from docker stop so SQL Server shuts down cleanly.
    entrypoint.sh
    #!/bin/bash
# Starts SQL Server, runs each /scripts/*.sql that has not run yet (in name order),
# then keeps SQL Server running in the foreground of the container.
# The SA password comes from MSSQL_SA_PASSWORD in the run-time environment;
# it is never stored in the image.
set -uo pipefail

# Each script that ran is recorded here, so a restart never runs it twice.
# 001-schema.sql creates this table.
history_table="ProductDb.dbo.schema_history"

if [ -z "${MSSQL_SA_PASSWORD:-}" ]; then
  echo "entrypoint: MSSQL_SA_PASSWORD is not set. Pass it when you start the container (docker run -e, or an .env file with compose)." >&2
  exit 1
fi

# sqlcmd reads the password from SQLCMDPASSWORD, so it never shows up in a process list.
export SQLCMDPASSWORD="$MSSQL_SA_PASSWORD"
sql() { /opt/mssql-tools18/bin/sqlcmd -S localhost -U sa -C -b "$@"; }

rm -f /tmp/ready
/opt/mssql/bin/sqlservr &
pid=$!

# `docker stop` sends SIGTERM to this script. Pass it on, so SQL Server shuts down cleanly.
stop_server() {
  kill -TERM "$pid" 2>/dev/null
  wait "$pid"
  exit $?
}
trap stop_server TERM INT

# Ready means: SQL Server accepts connections and every database, including one
# that already exists on the volume, can be opened. While SQL Server is still
# starting up, opening a user database fails (error 904), so we keep trying.
ready_check="DECLARE @sql nvarchar(max) = N'';
SELECT @sql += N'SELECT TOP (0) 1 FROM ' + QUOTENAME(name) + N'.sys.objects;' FROM sys.databases WHERE database_id > 4;
IF EXISTS (SELECT 1 FROM sys.databases WHERE state_desc <> 'ONLINE') RAISERROR('Databases are still starting.', 16, 1);
EXEC (@sql);"
echo "entrypoint: waiting for SQL Server and its databases to come online"
for attempt in $(seq 1 60); do
  if sql -Q "$ready_check" >/dev/null 2>&1; then
    break
  fi
  if ! kill -0 "$pid" 2>/dev/null; then
    echo "entrypoint: SQL Server stopped while starting. If the log above mentions the password policy, choose a stronger MSSQL_SA_PASSWORD." >&2
    exit 1
  fi
  if [ "$attempt" -eq 60 ]; then
    echo "entrypoint: SQL Server and its databases were not online within 120 seconds." >&2
    kill -TERM "$pid" 2>/dev/null
    wait "$pid"
    exit 1
  fi
  sleep 2
done

for script in /scripts/*.sql; do
  name=$(basename "$script")
  if ! applied=$(sql -h -1 -W -Q "SET NOCOUNT ON; IF OBJECT_ID('$history_table') IS NULL SELECT 0 ELSE SELECT COUNT(*) FROM $history_table WHERE script = N'$name';" 2>&1); then
    echo "entrypoint: could not read $history_table: $applied" >&2
    echo "entrypoint: stopping SQL Server." >&2
    kill -TERM "$pid" 2>/dev/null
    wait "$pid"
    exit 1
  fi
  if [ "$applied" = "1" ]; then
    echo "entrypoint: $name already applied, skipping"
    continue
  fi
  echo "entrypoint: applying $name"
  if ! sql -i "$script" || ! sql -Q "SET NOCOUNT ON; INSERT INTO $history_table (script) VALUES (N'$name');"; then
    echo "entrypoint: $name failed; stopping SQL Server." >&2
    kill -TERM "$pid" 2>/dev/null
    wait "$pid"
    exit 1
  fi
done

# The compose healthcheck looks for this file: the server is up and the scripts have run.
touch /tmp/ready
echo "entrypoint: database is ready"

wait "$pid"

    A few details are worth pointing out:

    • The password comes from the MSSQL_SA_PASSWORD environment variable of the running container. The script refuses to start without it.
    • sqlcmd lives in /opt/mssql-tools18/bin (it is not on the PATH). -C trusts the container's self-signed certificate, and -b makes sqlcmd exit with an error when a statement fails, so a broken script stops the container instead of leaving a half-built database.
    • The script checks that every database can be opened, not only that SQL Server answers. When the container starts with an existing volume, SQL Server accepts connections a few seconds before ProductDb is ready, and a check that came too early would run 001-schema.sql again.

    Line endings on Windows

    Shell scripts that run inside Linux containers must use LF line endings. If Git on Windows converts entrypoint.sh to CRLF, the container fails with errors such as bash\r: No such file or directory. The sample repository has a .gitattributes file with the rule *.sh text eol=lf, which keeps the file correct on every machine. In VS Code, the line ending is shown in the status bar and can be switched to LF there.

    Now create the Dockerfile:

    Dockerfile
    # SQL Server for the Product API (chapter 8).
# No password in this image: pass MSSQL_SA_PASSWORD and ACCEPT_EULA=Y when the container starts.
FROM mcr.microsoft.com/mssql/server:2022-latest

# The numbered scripts that create and seed ProductDb, and the script that runs them
COPY scripts/ /scripts/
COPY --chmod=755 entrypoint.sh /usr/config/entrypoint.sh

# The base image already runs as the non-root mssql user and exposes port 1433
ENTRYPOINT ["/usr/config/entrypoint.sh"]

    In this Dockerfile:

    • We start with the official SQL Server 2022 image provided by Microsoft. It already runs SQL Server as the non-root mssql user.
    • COPY scripts/ /scripts/ copies the numbered SQL scripts into the image.
    • COPY --chmod=755 copies the entrypoint script and makes it executable. Setting the permission in the Dockerfile matters on Windows, where Git does not keep the executable bit.
    • ENTRYPOINT replaces the image's start command with our script, which starts SQL Server itself.

    Add a .dockerignore file, so a local .env file with a password can never end up in the build context:

    .dockerignore
    .env
*.md

    Why the password is not in the Dockerfile

    An earlier version of this lab set the password with ARG and ENV and created the database during docker build. Don't do that. docker inspect shows every ENV value, and docker history shows the build commands, so anyone who can pull the image can read the password. Secrets belong to the running container, never to the image. The same rule applies to every service in this book.

    Step-4.1: Docker Build Locally

    To build the Docker image, navigate to the sqlserver folder and run:

    docker build -t sample/sqlserver .

    # output (trimmed)
#4 [1/3] FROM mcr.microsoft.com/mssql/server:2022-latest
#6 [2/3] COPY scripts/ /scripts/
#7 [3/3] COPY --chmod=755 entrypoint.sh /usr/config/entrypoint.sh
#8 naming to docker.io/sample/sqlserver done

    The build needs no arguments and no password. Check that the image really holds no password:

    docker inspect sample/sqlserver --format '{{json .Config.Env}}'

# output
["PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin","MSSQL_RPC_PORT=135","CONFIG_EDGE_BUILD=","MSSQL_PID=developer"]

    docker image ls sample/sqlserver

# output
REPOSITORY         TAG       SIZE
sample/sqlserver   latest    1.7GB

    Step-4.2: Docker Run Locally

    SQL Server enforces a password policy and rejects weak passwords, so replaceme will not work here. Choose your own password: at least 8 characters, with characters from three of these sets: uppercase, lowercase, digits and symbols (for example Replaceme-1a, for this lab only). Then start the container:

    docker run -d --name sqlserver -p 1433:1433 \
  -e ACCEPT_EULA=Y \
  -e MSSQL_SA_PASSWORD='<your-password>' \
  -v sqlserver-data:/var/opt/mssql \
  sample/sqlserver
    • -e ACCEPT_EULA=Y accepts the SQL Server license, and -e MSSQL_SA_PASSWORD sets the password of the sa login. Both are given when the container starts, not when the image is built.
    • -v sqlserver-data:/var/opt/mssql keeps the database files in a named volume, so they survive when the container is removed.
    • -p 1433:1433 maps the default SQL Server port to your machine, so the tools in the next steps can connect.

    The container takes about 30 seconds to start the first time. Follow its progress in the logs:

    docker logs sqlserver 2>&1 | grep -E "^entrypoint|rows affected"

# output
entrypoint: waiting for SQL Server and its databases to come online
entrypoint: applying 001-schema.sql
entrypoint: applying 002-seed.sql
(5 rows affected)
entrypoint: database is ready

    On Windows PowerShell, use docker logs sqlserver 2>&1 | Select-String "entrypoint" instead of grep.

    docker ps --filter name=sqlserver

# output (trimmed)
IMAGE              STATUS          PORTS                                         NAMES
sample/sqlserver   Up 36 seconds   0.0.0.0:1433->1433/tcp, [::]:1433->1433/tcp   sqlserver

    Restart the container and look at the logs again. The scripts are recorded in schema_history, so they don't run twice:

    docker restart sqlserver
docker logs --since 30s sqlserver 2>&1 | grep "^entrypoint"

# output
entrypoint: waiting for SQL Server and its databases to come online
entrypoint: 001-schema.sql already applied, skipping
entrypoint: 002-seed.sql already applied, skipping
entrypoint: database is ready

    Note

    If the container stops and the log mentions the password policy, your password is too weak: remove the container and the volume (docker rm sqlserver and docker volume rm sqlserver-data) and start again with a stronger one.

    Step-5: Test the SQL Server database connection using sqlcmd

    The quickest check needs no tools on your machine: run sqlcmd inside the container.

    docker exec -it sqlserver /opt/mssql-tools18/bin/sqlcmd -S localhost -U sa -C -W -d ProductDb \
  -Q "SELECT id, sku, name, price FROM dbo.products; SELECT script FROM dbo.schema_history;"

    Enter your password when prompted:

    Step-6: Test the SQL Server database connection using SSMS

    Testing the SQL Server database connection using SQL Server Management Studio (SSMS) ensures that the database server is accessible and that users can connect to it successfully.

    Launch SQL Server Management Studio (SSMS) and provide the necessary credentials to connect to the SQL Server instance:

    • Server name: localhost,1433
    • Authentication: SQL Server Authentication
    • Login: sa
    • Password: the password you passed with -e MSSQL_SA_PASSWORD
    • If SSMS reports a certificate error, select Trust server certificate.

    SSMS > Login Page

    After you connect, expand Databases > ProductDb > Tables. You will see dbo.products and dbo.schema_history; right-click dbo.products and choose Select Top 1000 Rows to see the five products.

    Step-7: Test the SQL Server database connection using Azure Data Studio

    Azure Data Studio is a cross-platform database tool that offers features similar to SQL Server Management Studio (SSMS) but with additional support for Azure services and extensions.

    Note

    Microsoft has announced the retirement of Azure Data Studio. If it is unavailable to you, use the SQL Server (mssql) extension for VS Code with the same connection settings as above.

    Launch Azure Data Studio and provide the necessary credentials to connect to the SQL Server instance: server localhost, authentication type SQL Login, user name sa, your password, and Trust server certificate set to True.

    Azure Data Studio > Login Page

    As in SSMS, you will find the products table under ProductDb > Tables.

    When you are done with the lab, remove the container. Add docker volume rm sqlserver-data if you also want to delete the data:

    docker rm -f sqlserver

    Step-8: Push Docker Container to ACR

    This step is optional. Pushing the image to Azure Container Registry (ACR) lets every developer on the team pull the same development database. Because the image contains no password, sharing it does not share a secret: each developer passes their own password when they run it.

    Log in to your Azure account using the Azure CLI:

    az login

    Authenticate to your ACR:

    az acr login --name myacr

    Replace myacr with your ACR name.

    Tag your local Docker image with the ACR login server:

    docker tag sample/sqlserver myacr.azurecr.io/sample/sqlserver:v1

    Push the Docker image to ACR:

    docker push myacr.azurecr.io/sample/sqlserver:v1

    Replace myacr and v1 with your ACR name and desired image version.

    Production note

    This image is for development and testing. In production, the Product API uses a managed database such as Azure SQL Database, which takes care of high availability, backups and patching, and the same numbered scripts are applied to it as migrations. You don't run the database container there. Chapter-12 explains this in more detail.

    Conclusion

    You have successfully created a Docker image for the store's product database. It contains SQL Server and the numbered scripts that create ProductDb, but no password: the password is given when the container starts. The scripts run once on the first start, and a named volume keeps the data between restarts.

    In Chapter-9 we create the second database, for the Order API, with PostgreSQL. In Chapter-12 we connect the Product API to this database.
